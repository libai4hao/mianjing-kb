# 首批打标 500 条：词表对齐与落库（2026-11-23）

> 状态：已完成（2026-11-23，提交见 CHANGELOG）

> 结论：首批 500 条中 495 条落库，`other_topic_rate` 从 19.2% 降到 6.6%；
> 拦截原因不是模型乱标，而是 **prompt 与校验用了两套主题词表**。

`--review-list` 打出的 54 条 pending 高度同质：聚簇索引、MVCC、隔离级别、
`delete/truncate/drop`、视图、游标、触发器、`group by` 为什么慢——全是数据库题，
全部 `topic=其他 + review_state=pending`。

## 2 根因：prompt 词表 ≠ 校验词表

- **prompt** 用 `taxonomy.prompt_lines()` 渲染，列出 12 个一级组：Java、**数据库**、
  **缓存与中间件**、计算机网络、操作系统、前端、**AI与大模型**、算法与数据结构、
  **项目与行为**、**工程与质量**、产品与运营、求职与行为；
- **校验** 用 `kb.vocab.topic_vocab()`，来自 `meta/topic_rules.yaml` 三段
  （rules / title_only_rules / folder_topics），是 40 个**产品级**主题（MySQL、Redis、
  Kafka…），**不含 数据库 / 缓存与中间件 / AI与大模型 / 项目与行为 / 工程与质量**。

模型照着 prompt 选“数据库”，校验一看不在词表，`labelspec` 就改写成“其他”并标
pending。这不是标注错误，是**两份词表没对齐**，而且惩罚落在最有价值的那批题上。

## 3 修复（三处，均可回退）

1. `meta/topic_rules.yaml` 新增 `label_topics` 段（只进打标词表，不参与分类/文件名
   规则）：数据库、缓存与中间件、AI与大模型、项目与行为、工程与质量。
   词表 40 → 45。
2. 新增 `topic_aliases` 段 + `kb.vocab.topic_aliases()` + `labelspec.validate_label` 的
   `topic_aliases` 参数：组名与主题不同名时先归一，不再整批改写“其他”。
   `Java→Java基础`、`产品与运营→产品运营`、`求职与行为→HR与求职`、
   `算法与数据结构→算法`。
3. 新增不变式测试 `test_every_taxonomy_group_is_a_legal_topic`：每个一级组必须
   在词表里或可经别名落到词表，否则测试失败——防这类“prompt 有、校验没有”再犯。

## 7 全量批次：分两夜跑（2026-11-23 20:30 起）

拍板方案：先跑 20,000 条上限（`--limit 20000 --resume --concurrency 4`），次日 merge 一批，
次夜补完剩下部分。实测吞吐 **16–17 条/分钟**（`--concurrency` 试过 2/4/8，
8 反而掉到 16 条/分钟，Ollama 单模型串行，多开只加排队开销，所以固定 c=4）。

运行期做的三处优化：

1. **`-u` 无缓冲启动**：之前 `Start-Process` 重定向的 stdout 全在缓冲区，
   `label-night1.log` 一小时都是空的，看不到实时进度；加 `-u` 后按分钟级可见。
2. **`review_note` 记录 pending 原因**：`labelspec` 把词表外主题写成
   `topic_out_of_vocab:<模型原话>`，`batch_label.write_staging` 新增 `review_note` 列写入；
   以后 pending 行能直接看出模型原本想选什么桶，不必再靠题干猜（首批 54 条就是这样猜的）。
3. **长跑防睡眠**：`build/keep-awake.ps1`（`SetThreadExecutionState` 循环，不改电源策略，
   退出即失效），避免夜间系统空闲休眠中断跑批。

后续步骤（次日执行）：备份 `kb.sqlite` → pending 批量 `keep` 归档为"其他" → 残缺/过时行 drop
→ `--merge` → `refresh --reembed` → `status` 核对 → 去掉 `--limit` 续跑剩余约 5,000 条。

## 8 标签维度 P0 优化（2026-11-23 20:45 生效）

起点数据（726 条已落库、5,403 次标签）：

| 指标 | 优化前 | 优化后（新规则产出的首批 22 条） |
|---|---|---|
| 平均标签数/题 | 7.44（上限 8，633 题 ≥7） | **3.77**（上限 4） |
| 维度重复率（topic/组名/qtype/岗位） | **37.8%**（2,044 次） | **0%** |
| 词表命中率 | 17.5% | 口径待全量后重算 |
| 去重后标签种数 | 2,187（单例 69.7%） | 75（单例 89.3%，样本小） |

三处改动：

1. **维度词停用**：`kb.vocab.tag_stopwords()` = 45 个 topic + 12 个一级组名 + 5 个 qtype +
   7 个岗位；`labelspec.normalize_tags(stopwords=…)` 命中即剔除，计数进 `issues`
   （`tag_dimension_dropped:N`）。标签只保留细粒度关键词。
2. **上限 8 → 4**：`meta/label_schema.yaml` 的 `tags.max_items`；prompt 同步改成
   “不要重复 topic/题型/岗位这些已有字段，不要近义堆砌”。改动顺带提升吞吐
   （输出短了，20:45 后稳定 20–22 条/分钟，此前 16–17）。
3. **存量 staging 清洗**：`scripts/clean_staging_tags.py`（默认 dry-run，`--apply` 写回），
   对已跑出但未 merge 的行统一施加同一条规则。当前 4,500 行 dry-run：
   改 4,498 行、剔维度词 7,147 个、截断 10,072 个。**在 merge 前执行**，保证同批口径一致。

回归：`test_tag_stopwords_drop_dimension_duplicates`、`test_staging_keeps_review_note_for_pending`、
`test_every_taxonomy_group_is_a_legal_topic`；全量 pytest 通过。
