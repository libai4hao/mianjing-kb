## 2. ADR 正文

### D-27（建议 D-01）016 与 qnorm 分开验收，禁止直接 apply

**状态**：Accepted / Conditional；生产迁移未执行。

**背景**：016 会改变题目身份、按答案长度去重并删除孤儿变体；qnorm 会改变 `q_norm`、`q_norm_hash`、`q_key`、`simhash` 并迁移 `label_facts`。两者都会改变题池和标签键，不能当成一次普通发布。`migrate_norm.py` 当前摘要只给计数和 `old_to_new`，标签冲突只报数量，不足以支撑人工审计。

**决策**：

1. 一次维护窗口内执行，但 016 与 qnorm 分成两个独立验收阶段，中间保留检查点。
2. 冻结写入：停止 intake、extract、classify、canonical、batch_label、refresh、doc_convert、reconvert、purge_origin、embed 等写操作，并确认没有遗留进程或活跃锁。
3. 生产库热备份：用 SQLite Backup API 备份 `kb.sqlite`，同时备份当前 `面经库.db`；备份必须能打开并通过 `quick_check`。
4. 016 预演：在生产库副本运行，输出可人工审计的重复题报告，至少包含 `old_qid`、`keep_qid`、`doc_hash`、`old_q_norm_hash`、`new_q_norm_hash`、完整题干、原/保留答案长度、保留或删除理由、标签是否冲突。
5. 016 正式执行：审核删除清单后 apply；检查唯一索引、`question_variants`/`canonical` 关联完整性，建立检查点。
6. qnorm 预演：在 016 检查点副本上重新生成 old → new 映射、题目冲突报告和 `label_facts` 新旧 hash 冲突明细；标签合并不能只报数量。
7. qnorm 正式执行：审核冲突明细后 apply；检查标签映射、重复题处理和 `label_facts` 完整性，建立第二个检查点。
8. 重建下游：全量 canonical、检索库、向量；跑 G1–G8 与检索评测；全部通过后才解除写入冻结。

**拒绝条件**：备份无法完成或无法打开；重复题保留策略有未解决争议；`label_facts` 新旧映射存在未解释冲突；副本 `PRAGMA integrity_check` 不通过；canonical/question_variants 出现无法解释的孤儿；正式库 `schema_version` 与预演基线不一致。出现任一条，不允许 apply。

**回滚边界**：016 和 qnorm 各自保留 SQLite 备份/检查点；异常时恢复对应备份，不依靠反向 SQL 逆转归一过程。

**后果**：生产迁移成为受控维护操作；`connect(create=True)` 的自动迁移不能再被视为“无害顺手行为”。需要在实施时增加显式迁移门禁或迁移专用入口。

### D-28（建议 D-02）batch_label 只读分支暂时继续持锁

**状态**：Accepted / Phase 1 active；Phase 2 pending。

**背景**：`batch_label.main()` 在连接数据库前获取 `kb` 写锁，`--check`、`--sample`、`--eval`、`--review-list`、`--manual-template`、`--golden-sample`、`--dry-run` 也会占用写锁。当前保守行为有合理性：`db.connect(create=True)` 可能执行迁移，不能把这些分支简单当成纯读取。

**决策**：

- 第一阶段：维持现有行为，所有分支继续持 `kb` 写锁，先保证数据安全。
- 第二阶段再拆分连接模式：
  - 纯读取：`--check`、`--sample`、`--eval`、`--review-list` 使用 SQLite `mode=ro`，不持写锁。
  - 只读数据库、写工作文件：`--golden-sample`、`--manual-template` 使用 `mode=ro`，输出文件原子写入。
  - 数据库写入：默认打标、`--review`、`--review-resolve`、`--merge`、`--golden-load`、`--manual-import` 持有 `kb` 写锁。
  - `--dry-run`、`--manual-dry-run` 必须使用真正的只读连接，不依赖“调用方不执行 DML”。

**验收标准**：只读操作不触发 schema migration、不改变 journal mode、不持有 `kb` 写锁；写操作仍与 intake/extract/refresh 互斥；读取期间使用 SQLite 一致性快照。

**后果**：短期检查命令可能阻塞生产写入；换来确定性安全。拆分工作单独排期，不与生产迁移混做。

### D-29（建议 D-03）intake 的 hash_collision 必须算失败

**状态**：Accepted / Pending code change。

**背景**：`intake.decide()` 对“16 位短指纹相同但完整 SHA256 不同”返回 `hash_collision`；`run()` 只累加计数并 `continue`，最终 `return 1 if actions["error"] else 0`，因此整批仍可能返回成功。短指纹碰撞概率低，但一旦发生就是身份冲突，不是普通重复。

**决策**：

1. 继续用完整 SHA256 做真实内容比对。
2. 两个不同 SHA256 但短指纹相同，绝不登记为 `duplicate`，不覆盖原记录，不删除任何文件。
3. 保留两个文件的完整 SHA256、路径和冲突记录。
4. 继续扫描其他文件，避免一个冲突阻断整批正常入库。
5. 将该批次标记为 failed，并返回退出码 1；`hash_collision` 进入 S1 正式失败原因码，不再只是 warning。
6. 正常 `duplicate` 仍不失败；`quarantine` 按既定隔离策略处理；普通读取 `error` 仍失败。

**验收标准**：构造两个前 16 位相同、完整 SHA256 不同的文件，intake 退出码为 1；两个文件都出现在冲突记录中；没有文件被删除或覆盖；同批其他正常文件仍完成登记；普通重复文件批次仍返回 0。

**后果**：批次可能“部分成功但整体失败”，调用方必须把非零退出码当成整批失败处理，不能只重跑冲突文件。

### D-30（建议 D-04）embed_questions 崩溃残留 staging 自动清理

**状态**：Accepted / Pending code change。

**背景**：当前 staging 名为 `.{out_db.name}.vec-staging-{pid}.db`；正常结束会清理数据库和 `-wal`/`-shm`，但强杀/断电时 `finally` 不执行，历史残留不会自动清理。PID 不能作为唯一身份，且清理失败被 `pass` 吞掉。`embed_questions.main()` 已持有 `online` 写锁，具备独占清理条件。

**决策**：

1. 所有 embedding 任务必须持有 `online` 写锁。
2. 获取锁后扫描该数据库对应的历史 staging 文件及 sidecar；确认不属于有效运行任务后删除。
3. 历史文件不能只按“PID 不存在”判断；增加任务运行标记/任务锁，避免 PID 重用和绕过标准入口造成误删。
4. 清理失败记录日志并中止新任务，不能假装清理成功。
5. 新任务使用独立 `run_id`；线上旧向量表只在新向量完整验证（数量、维度、`question_set_hash`）后替换。
6. 不保留永久 staging；staging 是可重建临时产物，不是知识库事实源。
7. 状态机固定为 `READY → CLEANUP → ENCODING → VERIFY → COMMIT → DONE`。

**验收标准**：正常完成后 staging 不存在；编码异常后 staging 被清理；模拟强杀后的 staging 能被下次启动清理；另一个 embedding 正在运行时清理器不删其文件；删除 staging 失败时任务 ABORT 且旧向量仍完整。

**后果**：启动阶段多一次扫描；换来崩溃恢复的确定性。

### D-31（建议 D-05）refresh 发布清单采用双层保留

**状态**：Accepted / Pending code change。

**背景**：`refresh._write_publish_manifest()` 每次覆盖 `build/shadow_publish.json`，`--swap-only` 只校验当前清单与当前 shadow 的 SHA256。当前授权能力正确，但历史发布不可追溯。

**决策**：

- 第一层：当前发布授权 `build/shadow_publish.json`。只对应当前 shadow；包含 `build_id`、数据库 SHA256、G1–G5/G8 门禁结果、`shadow_name`、`publishable`。新构建覆盖旧授权；正式发布后标记 `consumed` 或清除。`--swap-only` 必须同时匹配当前清单与当前 shadow 的 SHA256。
- 第二层：历史发布凭证 `build/manifests/refresh/<build_id>.json`。每次构建生成唯一文件，不覆盖历史；记录模型、向量数量、题集指纹、数据库 hash、门禁结果、是否成功发布及对应快照。历史 manifest 不参与 `--swap-only` 授权判断，长期保留，不自动 GC。

**保留策略**：当前 pending manifest 仅 1 份；历史 manifest 长期保留；refresh 日志至少 180 天；SQLite rollback 快照保留最近 3 份；未发布失败 staging 清理但保留失败日志。

**验收标准**：历史 manifest 不能授权旧 shadow；当前授权被覆盖后旧 shadow 的 `--swap-only` 必须拒绝；成功发布后历史文件仍可追溯模型、题集指纹、门禁和快照。

**后果**：增加很小的磁盘占用，换取可审计的发布链。

### D-32（建议 D-06）reconvert 实际写盘复用 kb 写锁

**状态**：Accepted / Pending code change。

**背景**：`reconvert` 会重写 MD 产物，但不修改 `kb.sqlite`，当前未持锁；`intake`、`doc_convert` 已使用 `kb` 写锁。文件系统状态与台账可能交叉变化。

**决策**：`reconvert --dry-run` 不持锁；实际执行持有现有 `kb.lock`，锁覆盖 MD 替换和转换日志更新。不新建 `file.lock`，因为新锁不能保证与 intake/doc_convert 互斥。`doc_convert --one` 继续由父进程持锁，子进程不重复获取，避免死锁。

**验收标准**：reconvert 与 intake/doc_convert/purge_origin 实际写盘互斥；dry-run 不持锁；异常释放锁；转换日志在锁内写入。

**后果**：转换期间写锁时间变长，但避免文件与台账竞争。

### D-33（建议 D-07）purge_origin --apply 全流程复用 kb 写锁

**状态**：Accepted / Pending code change。

**背景**：`purge_origin` 会物理删除导入源文件，安全校验与删除之间存在竞争窗口；当前未持锁，可能与 intake 扫描、reconvert 替换、doc_convert 生成同时发生。

**决策**：`purge_origin` 预览不持锁；`--apply` 从数据库备份开始，到只读连接、扫描、完整 SHA256 校验、删除计划生成、删除前二次校验、实际 `unlink`、删除日志写入结束，全程持有现有 `kb.lock`。不能只在 `unlink()` 前短暂加锁。复用 `kb.lock`，不新建 `file.lock`。

**验收标准**：模拟并发 intake/reconvert 时，purge 删除计划中的源文件不会被另一工具改写或登记；删除前二次 SHA256 不一致必须拒绝；日志完整；dry-run 不持锁。

**后果**：大批量删除吞吐下降，但删除安全边界明确。

### D-34（建议 D-08）建立独立 Golden Query 数据集

**状态**：Accepted / Pending dataset and evaluator。

**背景**：`golden_labels` 验证 LLM 打标准确性（G6b），不能用于检索质量；`eval/demo_queries.yaml` 只有 10 条示例，`eval_retrieval.py` 以 `expect_any` 子串命中为主，`expect_ids` 只有给全相关项才近似严格 recall，尚无 MRR/nDCG/graded relevance。

**决策**：

1. 新建独立 `eval/golden_queries.yaml` 与 `eval/golden_query_schema.yaml`，不复用 `golden_labels`。
2. 首版 50 条人工审核查询：精确技术问题 10、同义改写/口语化 10、多关键词/跨主题 10、短查询/缩写/歧义 8、带筛选条件 6、无答案/不应命中 6。
3. 使用 `q_key` 而不是 `qid` 标注相关项；每条包含 `query`、`topic`、`expect_q_keys`、`relevance`（`q_key` + `grade`）、`category`、`reviewed`。
4. 评测器补齐 Recall@5、MRR@10、nDCG@10、无答案查询误命中率、分主题召回率；首版先建立实际基线，再设门槛。
5. 每条查询的相关题目必须人工审查，不能模型生成查询和答案后自证。
6. 检索策略或模型升级时跑全量 Golden Query；结果接入 refresh 发布门禁。

**验收标准**：数据集有审核人和审核状态；评测可复现；分主题指标不被整体均值掩盖；无答案查询单独统计误命中。

**后果**：需要持续人工标注；但这是 RAG 质量从“有功能”升级到“可验收”的必要成本。

### D-35（建议 D-09）RAG 先精确去重，再做同簇软去重

**状态**：Accepted / Pending code change。

**背景**：`search.rag_contexts()` 直接按检索行返回 contexts，没有跨文档同题去重；同一 `q_norm_hash` 可能在多份文档重复出现。

**决策**：

1. 精确去重：按 `q_norm_hash` 或同一规范化口径的题干 hash 过滤重复题，不能只比较 `qid`/`doc_hash`。
2. 同簇软去重：对相同 `canonical_id`（或稳定簇键）的题目默认只取一个最佳代表；答案内容明显不同时最多保留 2 个有价值变体。
3. 多来源信息聚合到保留代表上，而不是把不同来源全部丢弃。
4. 不同主题的题目不得因聚类或去重被错误合并。
5. 输出保留 `q_key`、来源文档和来源路径，保证答案可追溯。

**验收标准**：相同题干跨文档只出现一次；同簇不同答案保留有价值代表；不同主题不误合并；来源信息聚合；排序不因去重改变相对顺序。

**后果**：contexts 数量减少；需要额外的来源聚合字段和簇键读取。

### D-36（建议 D-10）RAG 增加全局上下文长度预算

**状态**：Accepted / Pending code change。

**背景**：当前 `rag_contexts()` 只限制单题题干 300 字、单题答案 800 字、最多 6 条；没有全局预算，最坏可产生约 6,600 字正文，尚未计其他字段。

**决策**：增加 `max_context_chars=6000` 的全局预算，第一版按字符计，不假装是 token 数；后续确定实际 LLM 后接入对应 tokenizer 再升级为 token budget。超预算时按检索排序保留高相关内容，不能平均截断所有答案；短答案不因预算被不必要丢弃；每份 context 保留 `q_key`、来源文档和路径。默认仍为最多 6 条、题干 300 字、答案 800 字。

**验收标准**：总长度永远不超过预算；相关性排序不因截断改变；短答案保留；每份上下文有来源信息；空答案/超长答案边界有测试。

**后果**：低排序 context 可能被丢弃；换来 prompt 成本可预测。

### D-37（建议 D-11）真实 BGE 模型回归采用独立集成测试

**状态**：Accepted / Pending integration harness。

**背景**：生产使用 `BAAI/bge-small-zh-v1.5`、512 维、20,010 条向量，但当前测试没有真实模型推理覆盖；普通 CI 只跑单元测试，不能证明模型/依赖/embedding 代码改动后语义结果稳定。

**决策**：

1. 单元层：`tests/test_embedding_unit.py` 用 mock embedding，每次 PR 跑；覆盖维度、空输入、批处理、元数据写入。
2. 集成层：`tests/integration/test_bge_real_model.py` 与 `tests/integration/test_bge_retrieval.py`，夜间 CI 或受控发布环境跑；固定模型版本与模型文件指纹，使用真实 fastembed ONNX 推理。
3. 集成断言：输出 512 维；无 NaN/Inf；相同输入稳定；固定小型检索库 top-k 正常；`vec_meta` 的模型与题集指纹正确；记录吞吐和检索耗时。
4. 模型升级门槛采用相对基线：总体 Recall@5 下降不超过 2 个百分点，重点主题不超过 5 个百分点，MRR@10 不明显回退；向量数与题目数一致，`question_set_hash` 一致。
5. 普通 pytest 不联网下载模型；完整 20k re-embedding 只在发布前或模型升级时跑；Golden Query 全量评估在检索策略或模型升级时跑。

**验收标准**：夜间任务可重复；模型缓存缺失时明确 skip 或失败，不静默通过；发布记录包含模型指纹和基线对比。

**后果**：CI 时间和模型缓存成本增加；但模型质量回退可被量化拦截。

## 3. 实施顺序

- **阶段 A（生产安全）**：D-27 生产基线核对与迁移方案、D-29 hash_collision、D-32/D-33 文件锁、所有写入口锁覆盖复核。
- **阶段 B（异常恢复与运维）**：D-28 batch_label 连接拆分、D-30 staging 清理、D-31 发布 manifest 历史化。
- **阶段 C（RAG 质量）**：D-34 Golden Query、D-35/D-36 RAG 去重与预算、D-37 BGE 集成回归。

阶段 A 未完成前，不进行大规模增量抽取或生产迁移；阶段 C 不与生产迁移混在同一次发布。

## 4. 架构原则

事实源、工作产物、发布产物必须有不同的生命周期：

| 数据对象 | 是否可重建 | 保护方式 |
|---|---|---|
| `kb.sqlite` | 不完全可重建 | 热备份、事务、写锁、迁移检查点 |
| 原始文件 | 不一定可重建 | 文件锁、完整 SHA256、删除前复核 |
| Markdown 产物 | 可从源文件重转，但可能有差异 | 原子替换、哈希、转换日志 |
| `labels_staging` | 部分可重建，人工结果可能不可重建 | 备份、断点、人工审核记录 |
| `vec_questions` | 可重建 | staging、题集指纹、原子替换 |
| `面经库.db` | 可重建 | 影子库、门禁、回滚快照 |
| 发布 manifest | 不应依赖重建 | 当前授权 + 不可变历史凭证 |

新增工具评审时必须同时回答两个问题：它有没有修改 `kb.sqlite`；它有没有与 intake、转换、purge 等文件写入工具竞争。
