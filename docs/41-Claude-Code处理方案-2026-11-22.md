# 41 · Claude Code 处理方案（mianjing-kb）

> 状态：现行 · 最后更新：2026-11-22 · 适用版本：无（工具链文档，不涉及方案版本）

## 一、结论先行

这个仓库**不缺信号，缺导航和风险边界**。全量 pytest 76 秒全绿、ruff、privacy_scan、e2e demo 都在跑，CI 双矩阵也在跑——所以 Claude Code（下称 CC）在这里的正确用法，与"从零搭 vibe coding"完全相反：

1. **不要重建验证链路**，只需要给 CC 一条"分三档、耗时可预期"的命令。
2. **上下文才是瓶颈**：67 个模块、17,966 行包代码，`chunker.py` 单个 97 KB。默认"整文件读"必然爆上下文，必须先导航再精读。
3. **这个仓库的破坏半径很大**：生产语料根、`build/` 库、LLM 费用、隐私门禁——护栏要写在 CC 的指令层和 hook 层，不能靠自觉。

## 三、验证分层（核心设计）

一条命令跑全量不是好设计：76 秒的 pytest 挂在每次 Stop 上，会把每次对话结尾拖成灾。分三档：

| 档位 | 何时跑 | 内容 | 实测耗时 |
|---|---|---|---|
| **fast** | 每改一个模块后（AI 自查 / PostToolUse 后手动） | `ruff check` 改动模块 + `pytest tests/test_<模块>.py -q` | 5–15 s |
| **standard** | 每完成一个任务（Stop hook 用这一档） | ruff 全仓 + `privacy_scan` + 相关测试子集（改动模块及其依赖） | 20–30 s |
| **full** | 提交前 / pre-push / 收工 | ruff + `pytest tests -q` + `privacy_scan` + `demo` | ≈ 90 s |

落地成 `.claude/verify.ps1` 带参数：

```powershell
pwsh -NoProfile -File .claude\verify.ps1            # standard（默认）
pwsh -NoProfile -File .claude\verify.ps1 -Fast      # 只检当前改动涉及模块
pwsh -NoProfile -File .claude\verify.ps1 -Full      # 全量 + demo，提交前跑
```

要点：

- Python 解释器固定 `D:\dev\python\python.exe`（3.11.4，已装 pytest 9.2.0 / ruff 0.17.5）。不要依赖 PATH——本机 PATH 里还有 Anaconda 与一个第三方运行时，容易串环境。
- `privacy_scan` 在 standard 档就跑，因为它便宜且是硬门禁；泄露一次代价远高于 30 秒。
- full 档保留 `kb demo`（合成语料，不碰生产库），它验证的是"链路仍能端到端跑通"，这是单测覆盖不到的。

## 四、上下文驾驭（这个仓库最值钱的一节）

### 4.1 硬规则

1. **单文件 > 50 KB 禁止整读**：`chunker.py`、`batch_label.py`、`verify_ledger.py`、`refresh.py` 一律先定位再取段。
2. **先读地图，再读代码**：`docs/33-代码地图与维护索引` 给分层与模块职责；`docs/32-当前口径总表` 给门禁与阈值。这两份是"导航层"，成本远低于读源码。
3. **一次会话只服务一个 T 编号**（台账在 `docs/项目审核报告/待办清单-2026-11-19.md`）。跨任务混聊必然上下文污染。

### 4.2 精确取段的三种手段

```powershell
# 1) 只看函数/类清单（不读正文，几十行输出）
Select-String -Path mianjing_kb\chunker.py -Pattern '^(class|def)\s' |
  ForEach-Object { "{0,5}: {1}" -f $_.LineNumber, $_.Line.Trim() }

# 2) 取某个函数的行号区间，再定点读
Select-String -Path mianjing_kb\batch_label.py -Pattern 'def _apply_budget'

# 3) 结构级浏览（AST 只要签名，大文件也很快）
& D:\dev\python\python.exe -c "import ast,sys;m=ast.parse(open(sys.argv[1],encoding='utf-8').read());[print(f'{n.lineno:5} {type(n).__name__:10} {getattr(n,\"name\",\"\")}') for n in m.body]" mianjing_kb\chunker.py
```

### 4.3 会话开场模板（复制即用）

```
本轮只处理 T-<编号>。
先读：docs/32-当前口径总表（门禁/阈值相关条目）、docs/33-代码地图（对应模块的职责与改动决策）、
      docs/项目审核报告/待办清单（该 T 的验收口径）。
约束：单文件不整读（chunker.py 等 >50KB 的只按函数定位）；先给方案再动代码；
     不得写语料根与 build/；LLM 相关改动必须先说明费用影响。
产出：改动 + tests 增补 + full 档验证结果 + 需要同步回写的文档清单（19/29/待办清单）。
```

## 五、单任务执行循环

```
1. 定位：T 编号 → docs/32 口径 → docs/33 模块职责 → 相关测试文件
2. 方案：先说清"改哪个函数、加什么判据、影响哪些调用方"，等确认（brainstorming 门禁同款）
3. 小步：一次一个函数/一个判据；每步跑 fast 档
4. 任务完成：standard 档全绿 → 冷读评审（code-reviewer subagent）→ 处理 P0/P1
5. 提交前：full 档全绿 → 按仓库规矩三件套同提交（代码 / 19 或 29 / 待办清单）→ commit → push
6. 回写：CHANGELOG 记工程变更；口径数字变化才动 29
```

节奏红线与 my_script 一致：单次 diff ≤ 300 行；同一 bug 修 3 次不过就停手回到"假设层"；连续自主 ≤ 20 分钟。

## 六、风险护栏（写进 CLAUDE.md + hooks）

| 风险 | 硬规则 | 机器化手段 |
|---|---|---|
| 生产语料被改 | `D:\my-resource\面经整理ing` 下**只读**；任何写/改名/删除必须人工 | PreToolUse 拦 `KB_CORPUS_ROOT` 路径 |
| 库被重建/删除 | `build/`、`*.sqlite` 视为生产数据，禁止删除、重建、`reset` | 拦 `rm`/`Remove-Item`/`git reset --hard`；sqlite 文件编辑拦截 |
| LLM 费用失控 | `LLM_PROVIDER=online` 与 `LLM_ALLOW_CONTENT_UPLOAD=1` 双开关，CC 不得擅自开启；`batch_label` 必带 `--budget`，先 dry-run | 拦含 `LLM_ALLOW_CONTENT_UPLOAD=1` / `--budget` 缺失的 `batch_label` 调用 |
| 隐私外泄 | 不得把语料原文、标注内容贴进对话或提交；`privacy_scan` 必过 | standard 档强制跑 privacy_scan；拦 `meta/skip_log.json` 与 `.superpowers/` 入库 |
| 迁移事故 | 改 schema 先跑 `test_db_migrations` + `rehearse_migrate`，再谈真实库 | 改动 `kb/db.py` 或 `migrate_norm.py` 时强制提示 |
| 高危工具误用 | `purge_origin`、`refresh`、`reconvert` 属破坏性，必须 dry-run + 备份 | 拦无 `--dry-run` 的调用 |

## 七、Subagent 分工（省上下文，而非炫技）

| 场景 | 用谁 | 为什么 |
|---|---|---|
| 大文件里找实现位置 | 内置 Explore | 检索输出留在子上下文，不污染主对话 |
| 改动后的冷读评审 | 自定义 `code-reviewer`（只读，P0/P1/P2 分级 + 置信度） | 没参与写码，不受实现思路影响 |
| 追一个跨 5 个模块的调用链 | `general-purpose` 子代理 | 一次把链条画出来，主对话只收结论 |
| 跑全量测试并解释失败 | 子代理执行 | 测试日志动辄几千行，不能进主上下文 |

禁止：让子代理改已有测试断言（hook 层面拦），或让子代理直接 commit。

## 八、度量（每周看）

- **一次通过率**：standard 档首次即绿的比例（目标 > 70%，本仓库测试成熟，应该更高）
- **full 档耗时漂移**：基线 90 秒，超过 130 秒说明测试或依赖出问题
- **privacy_scan 报警**：目标 0；任何一次报警都要复盘是谁把什么带进来的
- **单任务 token**：中继模型按量计费，超过 40k/任务就要怀疑上下文没控住
- **文档三件套合规率**：改门禁/口径的提交里，同步更新 19/29/待办清单 的比例（目标 100%）

## 九、30 分钟落地清单

1. 写仓库根 `CLAUDE.md`（含 §3 三档命令、§4 读法硬规则、§6 风险表、三件套规矩）— 10 分钟
2. 建 `.claude/verify.ps1`（-Fast / 默认 standard / -Full 三档）+ `.claude/settings.json` hooks — 10 分钟
3. 建 `.claude/agents/code-reviewer.md`（只读、分级输出）+ `.claude/commands/task.md`（按 T 编号起流程）— 5 分钟
4. 拿一个 P2 级 T 任务实跑一遍：fast → standard → full，确认三档耗时符合预期 — 5 分钟

**不要一次改多个 T。** 这个仓库的测试密度意味着"一次通过率"很高，但跨任务混改会让 76 秒的全量测试失去定位能力。

## 十、与现有工具的边界

- pre-commit（privacy_scan + ruff）与 pre-push（pytest）**保持原样**，CC 侧不重复实现，只在会话内提前跑，减少提交被拦的次数。
- CI 是最终裁判，本地三档只是"提前发现"。本地 full 绿 ≠ CI 绿（还有 3.12 矩阵与 linux 依赖作业），提交后看 CI 再收工。
- 本文档不定义任何业务口径；涉及方案/门禁/阈值/基线的判断一律回 `docs/32`。
