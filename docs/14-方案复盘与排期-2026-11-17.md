## 4. 问题点（按"会咬人"的程度排序）

### P0 级（不修会持续制造错误数据）

1. **5,192 题无主题**：检索按 topic 过滤、按主题分桶的报表、RAG 路由全部对这 39% 失效。且它们 conf=high，看起来"很可信"，实际主题缺失。
2. **口径漂移的复发机制还在**：`topic=''` vs `'未分类'` 两套值并存，任何"归零"结论都可能再次误判。必须把"空值即未分类"写进 SQL/报表，而不是靠人记。
3. **刷新链手工**：五连跑顺序错一格（比如 build_db 在 embed 前）就会让 vec 与 questions 不同步，而 RRF 融合不会报错，只会**悄悄降质**。

### P1 级（会在特定场景咬人）

4. **vec 与 questions 的一致性无守卫**：`vec_questions` 13,296 = questions 13,296 只是此刻巧合成立，没有断言/测试。增量更新（K2）后极易错位。
5. **4B 打标的 qtype 准确率只有 0.55-0.65**：全库 1.3 万题批量打完，错误标签会污染库本身（打标前必须先过 L6 抽检，不能直接全量）。
6. **桌面单点**：桌面关机/重启 = 笔记本与所有自动化失去 LLM。L2 若做，必须配 L1 自启，否则远程调用全是超时。
7. **Ollama 零鉴权**：一旦 Tailscale 配错（如绑到公网网卡或防火墙没锁），等于把 1.3 万题的内网服务敞开。这是不可逆泄露风险。

### P2 级（成本/体验问题）

8. **8B 只能批跑**：40h 级，意味着"高质量打标"实际不可迭代——改一次 prompt 就要重跑 40h。结论：**打标必须用 4B**，8B 只做抽样复核。
9. **C 盘曾 0 字节**：工具链全瘫的那次事故根因是"模型 blob 默认落 C"。现在靠 `OLLAMA_MODELS` 环境变量兜着，但**它是用户级变量，换机器/换用户就失效**。需要写入 SOP + 启动脚本自检。
10. **新增文档会触发全量重编码**（现 191s）：量小时无感，一旦补录 500 篇就会变成小时级。
11. **350 道 127/128 页两版并存**：不拍板就一直有"同一题两个来源"的隐性重复。

### 5.1 D3 结论与证据（2026-11-17 实测）

两版均为《整理的多家公司常见面试题库350道》，同一文档的两个文件：

| | A `12-综合题库\整理的多家公司常见面试题库350道.pdf` | B `12-综合题库\JAVA常见面试题库\整理的多家公司常见面试题库350道.pdf` |
|---|---|---|
| 页数 | **127** | **128** |
| 字节 | 2,460,938（2.35MB） | 2,876,687（2.74MB） |
| MD5 | fa027f17e77c | 831b53e46262 |
| 修改时间 | 2025-02-17（较新） | 2023-07-27 |
| 文本层字符 | 78,744 | 79,449 |
| 首/末页 | 完全相同（目录页 + memcached 末题） | 完全相同 |
| 题号出现数 | 311 | 311 |

**逐页 difflib 比对结果**：除 4 处仅"空格/编码微差"的页外，唯一结构差异是 **B 在第 127 页位置多插入了 1 页近乎空白页**（文本层仅 5 个乱码字符 `T昹醄̃f朾`，无题目内容）。A 无空页。

**结论**：A 与 B 内容等价，B 多出的 1 页是垃圾空白页。**保留 A**（更新、更小、无空页），B 判定为 superseded 删除。

**附带发现（重要）**：A 的 OCR 文本已存在（`build\ocr_text\12-综合题库\整理的多家公司常见面试题库350道.pdf.txt`，124,696 字符，乱码率 0.0‰），但 **该文档在 `doc_contents` 里查不到、库里无对应题**（`md_rel LIKE '%整理的多家%'` 与 `'12-%'` 均为空；`20-题库MD\题库\综合` 下也无 350 的 md，只有 images 残留）。即：**这份 350 题从未真正入库**，不是"保留哪版"的问题，而是"这一份漏了入库"。
按 D3 结论执行 = 保留 A → 直接用已有 OCR 文本转 md 入库（**零 OCR 成本**，原估 127 页 OCR 可省），B 进 99 区。此项并入 K11 同批处理，单列 **K13（350 道补录，0.5h）**。
