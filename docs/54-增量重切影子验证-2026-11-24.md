## 2. 候选怎么分层（按"会丢什么"分，而不是按题多题少）

## 3. 工具改动：`extract --doc-list`

原来没有"只重切指定文档"的入口，新增一个最小开关（`mianjing_kb/extract.py`）：

- 每行一个 `doc_hash`，空行与 `#` 注释忽略；
- 只处理清单与题池的交集；清单里不存在/被 gate 拦掉的 hash 计入 `skipped_doc_list_missing`；
- **自动跳过孤儿清理**（`purge_skipped="doc-list"`），否则未处理文档的题会被误删——和 `--limit` 同一个坑；
- 不动 `--limit` / `--incremental` / `--allow-empty-overwrite` 的原有语义。

测试：`tests/test_extract.py::test_doc_list_processes_only_listed_docs`（只切清单内的 doc、孤儿哨兵行不被清、未知 hash 只计数不报错）。

## 5. 新增题抽样（影子独有 928 个 hash 的 30 条）

绝大多数是真面试题：

- 「什么是JRE?」「索引覆盖是什么?」「Springcloud核心组件?」「Mybatis的核心组件有哪些?」

## 6. 代价与风险（落生产前必须知道的）

1. **11 个旧题干消失**：都来自 B 档被替换的 1~6 条旧题；`ok` 状态的答案行从 14,645 → 14,586（-59）。
   当时若要绝对零损失，可先只落 A 档（50 篇、312 题），B 档单独评审；B 档随后已上线，见 `docs/56`。
2. **1,789 条新题未治理**：不跑 `answer_state` 就是 NULL 状态，不进 G 门禁口径；不补答则空答案 +164。
3. **检索库要重建**：`refresh --reembed` 才会把 1,789 题和向量同步到 `面经库.db`，否则检索侧看不见新题。
4. **重复度**：1,789 行只有 928 个新 hash（跨 doc 重复 1.93 倍），落库后 `question_freq` 会变，
   但 canonical 合并仍留给后续。
