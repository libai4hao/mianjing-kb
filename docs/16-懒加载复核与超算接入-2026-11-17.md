# 16-懒加载复核、超算互联网接入与并行排期（2026-11-17）

> 对应问题：① 超算互联网的 DS V4.1 Flash key 能否用；② 图片懒加载是否是"匹配不到"的原因；③ 打标的 token 与耗时；④ 出现问题的兜底；⑤ 当前进度；⑥ 哪些任务能并行。

## 1. 懒加载复核：**不是原因**（但挖出一个真 bug）

### 1.1 懒加载做了什么

`tools/lazy_images.py` 只把 md 里的 `![](./images/xxx.png)` 改写成 `<img src="..." alt="..." loading="lazy" />`，**只动图片引用行，不删任何文字**。它发生在 2026-11-17 15:34，`extract` 在 15:58 之后跑的，也就是说**现有库就是"懒加载之后"跑的**，如果懒加载是元凶，问题会稳定复现——但复现不了，因为：

- `extract.doc_pool` 里 md 镜像的 `doc_hash` 已经是**按路径**算的（`sha256("md-mirror:"+rel)`），源码注释写明"OCR 合并/懒加载每改一次 md 就会产生孤儿行，2026-11-17 修复"。路径没变 → hash 不变 → **懒加载改写不会造成"匹配不到"**。
- 懒加载是渲染层优化（浏览器/编辑器按需加载图片），与入库切题无关。

### 1.2 复核实测（415 个 md 逐个对比）

| 组 | 数量 | 现象 |
|---|---|---|
| 正常切题 | 320 | 有题且 md 剥标题前后都能切 |
| **因剥标题整篇丢光** | **46** | 原始 md 能切出题，走 `text_of()` 后 **0 题** |
| 本身切不出 | 49 | 原始也 0 块（图片型/纯叙述） |

决定性一条：`专题笔记/JVM/JVM问题排查分析-案例实战.md` 原始 md 切出 **38 块**，经 `extract.text_of()` 处理后 **0 块**。

原因在 `extract.py:44`：

```python
return re.sub(r"(?m)^\s{0,3}#{1,6}\s+", "", text)   # 把 "### 标题" 变成 "标题"
```

chunker v2 **依赖 `#` 标题层级来识别"标题+讲解"型题目**。标题符号被剥掉后，这类文档退化成纯叙述文本 → 一个题都切不出来。**这是真 bug，与懒加载无关。**

### 1.3 但 42,598 这个数字不能直接当"丢失题数"

用 `chunk_v2` 对原始 md 全量跑，得到 48,143 块，而现有管线产出 5,545 块（差 42,598）。抽样看这 48,143 块里混着大量噪声：

| 原文片段 | chunker 判为"题"的内容 | 是否真题目 |
|---|---|---|
| `ing msjl 9.md` | "今晚上任务" / "20号" / "实习-笔试 一般考" | ✗ 叙述碎片 |
| `2020面试题总结JAVA基础篇.md` | "配图（5张）" | ✗ 图片占位 |
| `MySQL常见错误及解决方案.md` | "问题 1：使用 MySQL Command Line Client，出现闪一下…" | ✓ 真题目 |

结论：**"46 篇丢光"是真的，"损失 42,598 题"是假的**——chunker 在无标题叙述文本上会过度切分。正确做法是先做 200 块人工判定，再决定 `text_of` 怎么改（保留 `#` 还是只剥首层）。

### 1.4 那 487 篇"无题"的真实原因（三类，已逐类验证）

| 类型 | 数量 | 机制 | 修法 |
|---|---|---|---|
| A. 根本没转 md | **356** 篇（仅 8 篇有 OCR 文本） | PDF/docx 未走转换/OCR，池里没有它 | 补跑转换 + OCR，落 md |
| B. 有 md 但剥标题后切不出 | **46** 篇（含在 97 里） | §1.2 的 bug | 修 `text_of`，改完重切 |
| C. 有 md 但本身是图片型/叙述型 | 49 篇 | 正文在图片里（如《高性能 MySQL》73K 字配 800 图 → 只出 1 块）；或纯叙事无题目 | 图片型走 OCR 补正文；叙述型标 `no_question` 进 `skip_log` |

> 另有 34 篇是"镜像有题但源 doc_hash 对不上"的映射问题——这类不是丢题，是索引口径问题，由 G1 门禁统一改用路径 hash 解决。

**懒加载与这三类原因都没有因果关系。** 它唯一的影响是：如果 chunker 的"图片占位归属"规则只认 `![]()` 而不认 `<img loading="lazy">`，图片的归属会变（不影响题目识别，影响"图片属于哪个题块"）。这条一并进 G2 门禁。

## 2. 超算互联网（SCNet）的 DS V4.1 Flash key：**能用，但接之前必须验三个点**

### 2.1 可用性

| 项 | 结论 |
|---|---|
| 端点连通性（实测） | `api.scnet.cn:443` **TCP 直连可达**（不需要 7890 代理） |
| 协议 | OpenAI 兼容：`base_url = https://api.scnet.cn/api/llm/v1`，`Authorization: Bearer <API Key>` |
| 模型覆盖 | 平台已接入千问、DeepSeek、Kimi、GLM、MiniMax 等；**具体模型 ID 以"控制台 → 模型列表"为准**，需确认是否已上架 DeepSeek-V4.1-Flash |
| 计费形态 | 按量计费 / Token Plan / Coding Plan 三种都走同一 base_url |

### 2.2 三个必须验的坑（官方文档已声明其一，另两个要实测）

1. **system 提示词走独立字段**：SCNet 文档明确写"系统提示词需通过 `system` 字段传递，**而非 messages 中的 system 角色**"。我们的 T2 打标正是靠 system 提示词锁枚举，**不改就会被静默忽略**，直接导致 json 输出跑偏。
2. **`max_tokens` 为必填**（DeepSeek 官方是可选的）。
3. **JSON 模式未在文档中声明支持**：`response_format={"type":"json_object"}` 需实测；若不支持，退化为"提示词强约束 + 解析失败重答一次"。

### 2.3 接入跑通的最小验收（5 分钟）

```powershell
# 1) 列模型（确认确有 V4.1 Flash 的 model id）
curl -s -H "Authorization: Bearer $env:SCNET_KEY" https://api.scnet.cn/api/llm/v1/models
# 2) 5 题冒烟：看 json_ok / 延迟 / 是否遵守 system 字段
python tools\llm_smoke.py --provider scnet --model <控制台里的id> --n 5 --tasks t2
```
三个验收点：`json_ok≥0.9`、`qtype` 落在枚举内、延迟 ≤5s/题。

### 2.4 与 DeepSeek 官方的选择建议

| | SCNet | DeepSeek 官方 |
|---|---|---|
| key 现状 | **你已经有**（省去注册） | 需新注册 |
| 价格 | 平台计费，以控制台为准 | 闲时 ¥1/¥4 每百万 token |
| 兼容坑 | 3 个（system 字段 / max_tokens / json 未声明） | 无（标准 OpenAI 兼容） |
| 建议 | **先用你的 key 跑通 5 题**；能过就全程用它，过不了再换官方 | 备选 |

代码层不需要二选一：`llm_client.py` 抽象 `LLM_PROVIDER`，SCNet / DeepSeek / 本地 ollama 都是 `base_url + key + model` 三个变量，**换一家改一行环境变量**。

## 3. token 与耗时预估（基于库内真实长度）

基准：待打标 4,011 题（topic 为"综合"级）；平均题干 56 字、答案 908 字（裁到 300 字入 prompt）。

| 批次 | 输入 tokens | 输出 tokens | 闲时成本（¥1/¥4 每 M） | 8 并发耗时 |
|---|---|---|---|---|
| **4,011 题（本轮）** | ≈1.68M | ≈0.16M | **≈¥2.3** | **≈20–30 分钟** |
| 全库 13,296 题（若重打） | ≈5.6M | ≈0.52M | ≈¥7.6 | ≈1.5–2 小时 |
| 487 篇补录后新增题（估 1–2k 题） | ≈0.5M | ≈0.05M | ≈¥0.7 | ≈10 分钟 |

耗时口径：单题往返 2–5s（420 输入 token），8 并发 → 每秒约 2–4 题 → 4,011 题 20–30 分钟。**如果 SCNet 限流更低（如 4 并发），时间翻倍到 40–60 分钟，仍是一次夜间手到擒来的量。**

## 4. 出问题怎么兜底（四层，从便宜到贵）

| 层 | 触发 | 动作 | 代价 |
|---|---|---|---|
| L1 重试 | 429 / 5xx / 超时 | 指数退避重试 3 次（2s/8s/30s） | 可忽略 |
| L2 换模型 | 单题 3 次失败 / json 解析失败 2 次 | 同 provider 换备用 model（如 flash→pro），或 provider 降级 SCNet→DeepSeek 官方 | 单价上浮，量小 |
| L3 落本地 | provider 整体不可用（鉴权失败/欠费/网络断） | 自动切 `LLM_PROVIDER=local`，Qwen3-4B 串行跑（3.2s/题） | 11.8h 级，只跑残量 |
| L4 挂起 | 预算超限 / 连续失败率 >5% | **熔断停止**，已完成部分 flush 落盘，写 `label_run_*.json` 记录断点 | 零成本，次日续跑 |

硬保障：

- **写 staging 不写生产**：结果进 `labels_staging`，G6 质量门禁过才 merge；失败整批回滚
- **断点续跑**：每 200 题 flush `labels_<date>_<shard>.jsonl`，`--resume` 按已完成 qid 跳过，重打成本＝0
- **预算熔断**：`--budget 10`（元），按返回的 usage 累计，超限即停
- **并发自适应**：遇到 429 自动把并发减半（8→4→2），不再触发二次限流
- **费用与耗时记账**：每批写 `tokens_in / tokens_out / cost / elapsed / failed`，进 `docs/` 月度账

## 6. 哪些能并行（一张矩阵）

| 任务 | 资源 | 可并行的对象 | 不可并行 |
|---|---|---|---|
| 线上 API 打标（4,011 题） | 网络 + 远端算力 | **与任何本地任务并行**（OCR、写代码、文档修订） | — |
| 本地 OCR（356 篇补录） | CPU 8 核 + 磁盘 | 与线上打标并行；与写代码并行 | **与本地 4B 推理抢 CPU**（PaddleOCR 会把 4B 挤到 10 tok/s 以下） |
| 写门禁脚本 / refresh / llm_client | 人脑 + 编辑器 | 与打标、OCR 并行 | — |
| 文档修订（README/04/00/09） | 无 | 与一切并行 | — |
| 本地 4B 推理（对照抽检） | GPU 8GB | 只能单跑 | 与 OCR、与其他 GPU 任务并行会掉速 |
| 向量增量重建 | 磁盘 + CPU | 与线上打标并行 | 与 OCR 并行会互相拖慢（同吃磁盘） |

## 7. 与 docs/15 的衔接（方案增量）

1. 门禁新增两条规则（G2 扩容）：
   - **G2-a 图片占位一致性**：chunker 的图片归属必须同时识别 `![]()` 与 `<img loading="lazy">`（懒加载副作用兜底）
   - **G2-b 结构依赖告警**：某文档"原始 md 能切 N 块、经 `text_of` 后 0 块"→ 直接报 `structure_loss`，不许静默 0 题
2. `text_of` 改法先进 `--dry-run`，用 200 块人工抽检确认再全量重切（避免 42K 噪声进库）
3. SCNet 接入沿用 `llm_client.py` 的 provider 抽象，**不单写一套**
4. 补录优先级按 §1.4 三类分开：B 类（46 篇）改代码即得，成本最低、收益立现 → 排第一
