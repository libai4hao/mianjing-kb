# 15-检验门禁与线上打标方案（2026-11-17）

> **状态**：现行（门禁规格） · **最后实质更新**：2026-11-19 · **适用方案版本**：v2-R3
> 文档索引与版本规则见 `docs/README.md`；流程以 `docs/19` 为准，数字以 `docs/29` 为准。

> 本轮不改代码，只落方案。触发原因：`350道` 台账状态是 `classified`（可入库），但检索库里既无文档也无题；顺着这条线做跨库对账，发现了比单个文档更严重的系统性问题（见 §1）。

## 1. 先看缺口实况（跨库对账实测）

> **时点说明**：本节是 2026-11-19 01:36（P0-1 重跑前）的对账快照，用于说明"门禁为什么必须存在"；
> 当前数字见 `docs/29`（题行 20,984，镜像题行已清零）。不要把本节 32,087/487 当成现状。

对照两张表：台账 `kb.sqlite:source_documents`（1,515 行）vs 检索库 `面经库.db`（**当时旧库**：`doc_contents` 415 行 / `questions` 13,296 行；2026-11-19 重建后为 1,434 / 20,984）。

| 口径 | 数量 | 含义 |
|---|---|---|
| 台账 `status='classified'`（判定"可入库"） | **1,392** | 声称该进的都该进 |
| 其中检索库无 `doc_contents` 行 | **1,031** | 转换产物/正文根本没进库 |
| 其中检索库**没有任何题目** | **487** | 入了库也没题，等于白入库 |
| 487 篇里：磁盘上找不到同名 md | **356**（其中仅 8 篇有 OCR 文本） | 卡在「转换/OCR 没产出 md」 |
| 487 篇里：有 md 但没进库 | **131** | 卡在「md→doc_contents→拆题」 |

无题文档按类型：题库 211 / 面经 121 / 真题 110 / 专题笔记 45；按扩展名：pdf 252 / docx 199 / md 26 / txt 10。

**结论：真正的病不是「选哪版」，是「台账说入库了，实际没入库，而且没有任何机制会发现」。** 所以先做门禁，再补数据。

## 2. 门禁设计（9 道：G1–G8 + G6b，每道都对应一次真实事故）

统一入口 `mianjing_kb/verify_ledger.py`，输出 `build/gate_report.json` + `build/gate_report.md`，任一 FAIL 即非 0 退出。分层：**硬门禁（FAIL 阻断入库）/ 软门禁（WARN 记录）**。

| ID | 门禁 | 判定规则 | 现状 | 级别 |
|---|---|---|---|---|
| **G1** | 源-库全覆盖 | 内容池每篇（`classified / processing / processed`）必须满足「`doc_contents` 有行 **且** 有题」；否则必须在 `skip_log` 有明确原因（`no_text_layer` / `garbled` / `converted_only` / `duplicate_of` / `no_question` / `chunker_no_split` / `no_md_artifact`） | 2026-11-19 起按内容池三态判定（Q-3）；优先精确源→md 映射，找不到才退同名族 | 硬 |
| **G2** | 转换链闭环 | 有 md 却无 `doc_contents` → FAIL；有 `ocr_text` 却无 md → FAIL；有 md 却 0 题且未标 `no_question` → FAIL | **FAIL**：131 篇有 md 未入库；350 道有 OCR 文本无 md | 硬 |
| **G3** | 主题唯一口径 | `topic` 空串/`'未分类'` 计数必须为 0，或全部落在 `review` 桶并已登记；两种值只允许一种表示 | **FAIL**：5,192 空串 | 硬 |
| **G4** | 索引一致性 | `vec_questions` 行数 = `questions` 行数 **且 qid 集合相等**；FTS 同步同数同 rowid | 2026-11-19 PASS；未建向量表 WARN，表在但 `sqlite_vec` 不可加载 → FAIL | 硬 |
| **G5** | 台账-磁盘一致 | `dispatch`：classified→文件确实在库（空 `src_path` 一律视为缺失）；superseded→在 99 区或已删且 `retire_log` 有**完整相对路径**（或 note 含退役/乱码/替代等语义留痕）；99 区每件都能在台账找到；**且每行 `converted_to`（含历史裸格式）都能解析到一条未退役的后继记录**（后继仍是 superseded 时按 ≤3 跳追链） | 当前通过（3 件均有记录） | 硬 |
| **G6** | 打标质量 | schema/枚举/长度合格率 ≥0.95（topic≤40、qtype 枚举、difficulty 1-5、tags JSON；T21 增 position/quality 有值时合法、canonical_q 有值时≤60）；抽检 50 题人工准确率 ≥0.8；qtype/topic 分布相对基线漂移 >15% → WARN；新维度覆盖率与标签归一命中数进 detail | 未启用（staging 空 → SKIP） | 硬 |
| **G6b** | 金标抽检 | `golden_labels` 金标集准确率 ≥0.8；**样本 <50 则 WARN**（n=20 时真实 .70 有 ~24% 概率观测≥.8，统计效力不足），weak_topics 最少 5 条样本 | 2026-11-19 落地（T21 批次二），报告含 Wilson 95% 下界 | 硬 |
| **G7** | 文档一致性 | README 的 docs 清单 vs `docs/` 实际文件；README 声称的测试数 vs `pytest --collect-only` 实际；「未实现清单」不得列已存在的脚本 | **FAIL**：README 缺 07-14、称 cluster/dispatch/extract "未实现"（实际已有）、测试数写 36（实际 74 个用例/81 通过） | 软 |
| **G8** | 单身份（双份检测） | 有源回链的 md 产物（`doc_contents.doc_hash` 非空），其 `md-mirror:` 身份下不得再有题行；孤儿 md 不计 | 2026-11-19 落地（`27` P0-1）；未修数据会在 refresh 阻断 | 硬 |

### 2.1 关键设计点

1. **影子库 + 原子切换**：`refresh.py` 先建 `kb_shadow.sqlite`，全部步骤跑完、G1–G5 全 PASS 后才替换线上库。门禁失败→删影子库，线上不动。**这样门禁才有阻止力，而不是"报个警就继续"。**
2. **`skip_log` 是一等公民**：任何"故意不入库"的文档必须写一条带原因的 skip 记录，没有记录就是 FAIL。禁止用"没题就算了"糊过去。
3. **门禁即清单**：G1/G2 的输出直接生成 `build/backfill_plan.csv`（待补 487 篇 + 原因分类 + 预估 OCR 页数），补录任务不用手工造清单。
4. **每次刷新必跑**：`refresh.py` 内置 G1–G5 + G8；G6 在打标后跑；G7 在 `git commit` 前的 pre-commit 钩子（或手动 `verify_ledger --docs`）。
5. **门禁结论必须带 SQL**：每份报告记录查询与口径，杜绝"归零"类结论凭空出现。

### 2.2 门禁的验收

- 拿 `350道` 做回归样本：G2 必须报它（OCR 文本有、md 无）；补录后必须转 PASS
- 人为造 3 个故障（删一条 doc_contents / 删一条 vec 行 / 手改一个 topic 为空）→ 门禁必须各自报警
- 门禁自身要有测试：`tests/test_verify_ledger.py`，6 条以上

### 2.3 阈值口径（两套数，分别管什么）

| 口径 | 用途 | 阈值 | 代码位置 |
|---|---|---|---|
| 三态报告 `pass/review/fail` | 决定哪些件能进转换 / 抽题 | 异常字符比 **≥0.02** → fail；CJK 比 **<0.15** → review；字符数 **<100** → fail | `gate.py`：`TH_BAD/TH_CJK/TH_MIN` |
| 四态台账 `gate_results` | 记录文本质量分档 | 乱码比 **>0.01**；有效字符比 **<0.90**；可见字符 **<800** | `kb/config.py`：`GATE_GARBLED_MAX/GATE_VALID_MIN/GATE_MIN_VISIBLE` |

**这不是重复配置**：前者回答"这批件要不要继续处理"，后者回答"这份文本质量属于哪档"；指标也不同
（异常字符比 vs 乱码比、字符数 vs 有效字符数）。**唯一必须单源的是 CJK 下限 0.15**
（`gate.py` 的 `TH_CJK` 直接引 `config.GATE_CJK_MIN`）。调参只改上述两处，脚本里不得再写第三套数。

### 2.4 99 区可删 gate（`cluster.py`，2026-11-19 复核收紧）

99 区文件的 `strong` 现在是**文件级**结论，不再是"一条题命中、整份可删"：

- 每条 99 题必须与资源池某题**直接** Jaccard ≥ `auto(0.92)`，不从 single-linkage 簇继承；
- 池样本账本状态必须 `classified/processing/processed`，`rejected/superseded/quarantined`
  或 `gate_result=garbled/empty_docx` 不能当删除见证；
- 每条匹配都要做**单向答案覆盖**：99 有答案而池答案缺失/不相似 → `manual`（不再"一方短则无冲突"）；
- 文件级 `matched/total ≥ 90%`、无 pending/冲突、答案覆盖 >0、题块字符/原文 ≥0.10 才 `strong`；
- 其余 `manual`；无任何匹配 `none`。逐件明细写 `verdict_detail`（ratio/coverage/reasons）。

调依赖：`--limit` 只写 `cluster_result_limitN.json`，结果带 `complete=false/limit`；抽取失败会
`failed=true` 并另写 `cluster_result_incomplete.json`，消费方一律拒收不完整结果；缓存 key 带
`CACHE_VERSION`，抽取失败不再写 `[]`，Word 锁文件 `~$*` 与 `.tmp` 原子落盘一并处理。

## 3. 线上模型夜间打标

### 3.1 可行性（已实测）

| 检查项 | 结果 |
|---|---|
| 6 个国内 API 域名 TCP 443 直连 | **全部可达**（deepseek / dashscope / bigmodel / siliconflow / volces-ark / moonshot） |
| 是否需要 7890 代理 | **不需要**，直连即可（代理只用于访问 ollama.com / GitHub 这类境外站） |
| 本机已配置的 API Key | **一个都没有**（DEEPSEEK/DASHSCOPE/ARK/SILICONFLOW/MOONSHOT/ZHIPU/OPENAI 全未设）→ 需你注册后设用户级环境变量 |

### 3.2 为什么建议用线上而不是本地 4B

| | 本地 Qwen3-4B | 线上 flash 类 |
|---|---|---|
| qtype 准确率（实测同批 20 题） | 0.55 | 未测，同类任务通常 ≥0.85 |
| 4,011 题耗时 | 3.2s/题串行 ≈ **3.6h**（GPU 只能跑 1 路） | 8 并发 ≈ **10-15 分钟** |
| 成本 | 0（占电） | **≈¥3**（估算见 §3.5） |
| 副作用 | 占满桌面 GPU，影响交互 | 无 |
| 隐私 | 不出本机 | 需上传题目文本（公开面试题，风险低；个人面经段落要脱敏） |

### 3.3 模型推荐（按"打标这活"排，不是按跑分排）

| 顺位 | 模型 | 理由 |
|---|---|---|
| **首选** | **DeepSeek `deepseek-flash`（V4.1 Flash）** | 原生 JSON Output、并发 2500、闲时 ¥1/¥4 每百万 token；结构化抽取这类任务足够 |
| 备选 | 阿里百炼 `qwen-plus` | OpenAI 兼容、中文稳、额度大；换 provider 只改 base_url |
| 兜底 | 智谱 `glm-4-flash`（有免费额度）/ SiliconFlow 托管 Qwen3-8B | 零成本试跑、或本地没 key 时用 |
| 不推荐 | `deepseek-v4-pro` | 贵 3 倍，1M 上下文对"一题一判"纯浪费 |

> 关键点：**打标任务是"给定题干+答案片段 → 输出受约束 JSON"，不需要长上下文、不需要推理链**。选模型的标准是「JSON 稳定 + 便宜 + 并发高」，不是「榜单分数高」。

### 3.4 接入方式（一份代码，两种 provider）

沿用 docs/13 §5 的接入层，只加 provider 抽象：

```
LLM_PROVIDER = local | online        # 决定默认 base_url 与超时
LLM_BASE     = http://127.0.0.1:11434/v1  或  https://api.deepseek.com/v1
LLM_KEY      = (空/本地无需)         或  sk-xxx（用户级环境变量）
LLM_MODEL    = qwen3-4b             或  deepseek-flash
LLM_CONCURRENCY = 1（本地）/ 8（线上）
```

- 两者都是 OpenAI `/v1/chat/completions`，`llm_client.py` **一套代码**，切 provider 只改环境变量
- 线上走 `response_format={"type":"json_object"}`；本地走"提示词里锁枚举"（小模型不支持强制 JSON schema）
- 重试：429/5xx/超时 → 指数退避 3 次；单题 3 次失败落 `failed.jsonl` 不阻塞整批
- 断点：每 200 题 flush 一个 `labels_<date>_<shard>.jsonl`；`--resume` 按已完成 qid 跳过

### 3.5 成本估算（基于库内真实长度）

无 topic 的 5,192 题：平均题干 56 字、答案 908 字；打标只需题干 + 答案前 300 字裁切。

| 项 | 单题 | 4,011 题（"综合"级待打标） |
|---|---|---|
| 输入 | ≈420 tokens | ≈1.68M tokens |
| 输出 | ≈40 tokens | ≈0.16M tokens |
| 闲时价（DeepSeek V4.1 Flash） | — | 输入 ¥1.68 + 输出 ¥0.64 ≈ **¥2.3** |
| 预算建议（含重试/失败重跑） | — | **¥10 封顶**（`--budget 10`，超了自动停） |

全库 13,296 题重打一遍也只要 ≈¥8。**成本不是问题，成本这一项可以从决策里划掉。**

### 3.6 调度（Windows 计划任务，夜间）

```
22:05  计划任务触发 → batch_label.ps1
       1) health 检查（provider 可达 / key 有效）
       2) batch_label.py --provider online --concurrency 8 --budget 10 --resume
       3) 写 build/label_run_<日期>.json（条数/耗时/费用/失败数）
       4) 自动跑 G6 打标质量门禁 → PASS 才 merge 进 questions；FAIL 留 staging
       5) 次日 08:00 若未完成，续跑（jsonl 断点，不重打已完成）
       6) merge 后跑 refresh.py --reembed——检索库 topic 是 build_db 快照，
          merge 只写 kb.sqlite，不 refresh 检索层不生效（2026-11-19 B2 修复补链）
```
- 为什么定 22:05：DeepSeek 闲时 = 非工作时段（9–12、14–18 之外），22 点价格是峰值的一半；同时本机 GPU 空出来给日间交互
- 打标结果**先进 `labels_staging` 表**，不直接改 `questions`；G6 通过后一次性 merge，失败可整批回滚
- 若你只在笔记本上、桌面没开机：计划任务跑在桌面（库在这台），笔记本不承担批处理

### 3.7 脱敏（上传前必做）

正则遮罩后发送：手机号、邮箱、微信/QQ 号、身份证号、`http(s)://` 个人链接。命中即替换为 `[联系方式]`，并记 `redacted=true`。个人面经（121 篇无题的那批里含个人叙述）一律先脱敏再打标。

**密钥脱敏**（与内容脱敏分开）：`LLM_KEY` 只放请求头；`llm_client.scrub_secret()` 在 HTTPError 响应体、
URLError 文本、重试汇总和最终 `RuntimeError` 出口统一替换为 `[LLM_KEY]`，同时兜底 `sk-*` 与
`Authorization: Bearer ...`。调用方打日志前不需要再手写脱敏。

### 3.8 金标层与复核层（2026-11-19 批次二/三落地）

打标质量从"单次 G6"升级为三层闭环：**词表锁 → LLM 预审 → 金标抽检 → 人工终审**。

**封闭词表（防主题碎片化）**：`mianjing_kb/kb/vocab.py` 从 `meta/topic_rules.yaml` 三段（rules/title_only_rules/folder_topics）取 topic 并集，剔除"未分类"、补"其他"兜底。词表非空时 SYSTEM 换锁枚举版（topic 必须从词表选恰好一个）；落表兜底——模型仍给词表外主题时改"其他"并置 `review_state='pending'`。G6 漂移基线随之改词表（`drift_baseline='vocab'`），首批打标误报 WARN 一并消除。

**金标层（G6b 门禁——§2 承诺的 ≥0.8 抽检有了实现载体）**：

```
python mianjing_kb/batch_label.py --golden-sample 50     # staging 按 topic 分层抽样 → build/golden_todo.json
# 人工填 items[].topic_gold / qtype_gold / difficulty_gold
python mianjing_kb/batch_label.py --golden-load build/golden_todo.json
python mianjing_kb/batch_label.py --eval                 # G6b：topic 准确率 ≥0.8 PASS；<0.8 FAIL 列弱项主题+混淆矩阵
```

- 金标以 `q_norm_hash` 为主键（跨 extract 重切存活）；与 staging 交集 <20 条时 **WARN**（样本不足、未判，不阻断，但显式标注，避免被读成"通过"）
- `--merge` 时 G6b FAIL 拒绝合并（硬门，staging 保留）；核账 summary 同样计硬门 FAIL——修标签或补金标后重试
- 防覆盖：已有未回灌的 `golden_todo.json` 时 `--golden-sample` 拒绝重抽；`--golden-load` 成功后把清单改名 `golden_todo.loaded-<ts>.json` 留档（此后可自由重抽）

**复核层（LLM 预审 + 人工终审）**：

```
python mianjing_kb/batch_label.py --review               # 三类可疑标签：词表外(含"其他") / conf low|none / 金标弱区
python mianjing_kb/batch_label.py --review-list          # disagree 优先打印待终审清单
python mianjing_kb/batch_label.py --review-resolve "12:keep 33:suggest 44:drop"
```

- `--review` 只产出 agree/disagree：agree 落 `review_state='agree'`；disagree 把建议 JSON 存 review_note，**merge 不落库不删**（输出 `n_review_hold`），人工终审后放行
- `--review-list` 打印建议摘要（review_note 前 80 字）；题干已失效的分歧孤儿行也列出（标"(题干已失效)"）——分歧行不算孤儿，`--merge --drop-orphans` 不会误删人工分歧
- `--review-resolve`：keep=维持原标签；suggest=把 review_note 建议应用到标签列再 agree；drop=删行——这是分歧行的唯一出口（防 merge 死锁）
- 单题失败落 `build/review_failed.jsonl` 不阻塞整批；`--limit/--budget` 与打标共用

**num_ctx 透传**：`LLM_NUM_CTX=8192`（正整数，缺省不透传）——docs/13 §5 接口契约的实现半边；`keep_alive` 保持服务端部署项（`OLLAMA_KEEP_ALIVE`），客户端不实现。

## 4. 先做 / 空闲做（排期分层）

### 4.1 立即做（阻塞正确性，不做则后续全是脏活）

| 顺序 | 任务 | 工时 | 为什么是现在 |
|---|---|---|---|
| 1 | **G1–G5 门禁脚本 + 影子库切换** | 4h | 先有"发现问题的能力"，否则补完还是不知道漏没漏 |
