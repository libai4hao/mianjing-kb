# 决策记录（ADR）

按时间顺序记录"拍过的板"与"还没拍板"的。每条都写理由，避免下次重新论证一遍。

---

## D-01 主线：先把方案打磨到可执行，暂不跑批处理
**决策**：产出并迭代《部署方案》v1 → v2 → v2-R1，先审核再执行。
**理由**：实测已推翻 v1 的三条假设（语料规模、扫描件占比、OCR 判据），先改方案比先跑批处理省钱。

## D-02 云 OCR 预算整条删除，改本地 PaddleOCR-json
**决策**：本地 `PaddleOCR-json v1.4.1`（Umi-OCR 内），0.72–0.80 s/页，score 多 0.92+。
**理由**：实测可用且质量达标，原方案 ¥600–3000 的云 OCR 预算不再需要。

## D-03 门禁替代"文本层检测"
**决策**：判据改为 CJK ≥ 0.15、乱码率 < 1%、有效字符率 ≥ 0.90、可见字符 ≥ 800。
**理由**：15 篇转换失败件**都有文本层**，只是字体编码坏了；"有没有文本层"在本语料上失效。
**验证**：`gate.py` 在 397 个 md 上复现了 JavaGuide v1.0/V1.1/v2.0、Leetcode-Go、Nginx、剑指Offer 等"假成功"。

## D-04 判重先于 OCR（R1 §3.3）
**决策**：superseded 免 OCR、部分 OCR、全 OCR 三段式。
**理由**：JavaGuide 三个版本可省 791 页；OCR 最坏总量 4,031 页 ≈ 52 分钟。

## D-05 目录名的用途：不是 topic，而是 collection
**决策**：目录名只用于 `collection`（来源集）与结构位（category / source_trust），topic 仍由文件名 + 顶层主题目录判定。
**理由**：444 条里 313 条目录深度 ≥3，但把深层目录名当 topic 只能救回 **2 条**；而 `面向字节系列` 35 篇若无 collection，会被算成 35 个独立来源，见证数虚高 35 倍。

## D-06 "未分类"是正式取值，不是兜底
**决策**：`category=未分类` + `topic_source=none`，`TOPIC_BY_FOLDER` 未命中不再返回"综合"。
**理由**：现网 `detect_topic` 兜底"综合"，导致未知目录的件被静默判成"题库/综合"，`topic=综合` 变垃圾桶。

## D-07 先分类，再处理（流水线顺序不可逆）
**决策**：`pending_classify → classified → processing → processed`，只有 classified 才进 convert。
**理由**：① 88 个未登记文件里 45 个本不该解析；② `category` 决定拆题策略；③ `collection` 决定排序权重。
**防矛盾条款**：解析器只由 `ext` 决定，分类不参与选解析器 → 分类错最多重跑拆题，不重跑 OCR。

## D-08 只做两个增量时点（现在 / 上线后）
**决策**：不做 S1–S5 中途插入的增量分支。
**理由**：中间态最多几周，维护分支成本高于全量重跑；单批 ≥50 件直接走全量。

## D-09 仓库建在 `<REPO_ROOT>`
**决策**：按用户指定，项目目录建在 `vibe-work` 下，`vibe-work` 本身是共用工作区而非仓库根。
**理由**：本工程数据留在 D 盘（语料 6.27 GB + 后续产物），代码与数据同盘便于路径校验；
且 `vibe-work` 下已有无关项目（`公开课视频转文档`、`ilprobe.exe`），共用一个仓库根会互相污染。
**代价**：与用户既有 `<REPO_BASE>` 约定不一致，属有意偏离。

## D-10 原文档表是唯一事实源
**决策**：`source_documents` 主键 `doc_hash`，`registry.json` 降级为扫描快照。
**理由**：判重必须是索引查找而非全表比对；删除只改 status，行永久保留，所以"删掉又下载回来"能被认出。
**实测**：444 件 sha256 全量 2.93 s（860 MB/s），成本可忽略，不需要任何缓存优化。

## D-11 同批内重复必须当场识别
**决策**：intake 逐条立即落库，不再"攒到最后统一写入"。
**理由**：首次真实登记时发现 497 个 added 实际只有 496 行——同批第 2 份相同文件被覆盖。立即落库后，批次内重复会被判 `duplicate`。

## D-12 副本与隔离区不得"夺主"（原件存活判定）
**决策**：判 `moved`/`renamed` 之前先看记录里的绝对源路径是否还在；还在就判 `duplicate`，只刷 `last_seen_at`。
**理由**：真实数据里 `设计模式面试专题.md` 在 `12-综合题库/...` 与 `99-重复文件待删/...` 各一份、字节相同。
旧逻辑先扫到哪份就把路径写成哪份，结果库内正式件被隔离区副本改写，还被算进可入库清单。
**代价**：`Path.exists()` 每命中一次重复多一次 stat（实测 497 件整体 3.2–3.9 s，可忽略）。

## D-13 可入库清单落地为视图 + CSV，而不是新表
**决策**：`ingest_queue` 作为视图（`status='classified'`），由 `tools/ingest_queue.py` 导出 `build\ingest_list.csv`。
**理由**：清单是"状态机的投影"，做成实表就要维护同步；视图永远与 `source_documents` 一致。
**产物**：481 行、hash 唯一 481；字段 `doc_hash, file_name, parent_dir, dir_path, ext, size_bytes, category, topic, collection, source_trust`。

## D-14 非内容目录拒收：简历模板 / 学习路线 / 图解课件
**决策**：`folder_rules.yaml` 增 `reject_patterns`，命中 → `category=非内容`、`status=rejected`，只留台账不入库。
**理由**：`11.3-专题总结包` 下的 `简历模板`（8 个 docx/doc）、`Java学习路线`（4 个 pdf）、
`各种技术学习路线`（含 `测试.pdf`/`游戏.pdf`）原来被按目录结构位判成"专题笔记/题库"，会污染题库。

## D-15 `queue.py` 改名 `ingest_queue.py`
**决策**：模块名不用 `queue`。
**理由**：`queue` 与标准库同名，放进 `sys.path` 会遮蔽 stdlib，任何间接依赖 `import queue` 的库都可能被带偏。

## D-19 书签扫描的源边界判据：只认"L1 标题形如文件名"
**决策**：`tools/bookmarks.py` 把满足 `.*\.(pdf|docx|doc|md|pptx|txt)$` 的 L1 书签当作源边界，
条数即 `source_count`；没有这类 L1 时按单源处理并写 `from: fallback_no_source_toc`。
**理由**：干跑把"L1 条数"一律当源数，291 份 PDF 被算成 119 份合并版 / 3,338 个源——
普通 PDF 的 L1 是章节标题。合并工具写入的 L1 恰好就是源文件名，这才是可靠的判据。
**验证**：291 份 PDF、1.9 s；合并版 23 / 源 110；JVM 11 段、Mongo 4 段与审核页区间完全一致；
32 tests passed。**删 99 区的前置 gate 已完成一半**（另一半是 cluster 完成）。

## D-20 收件箱按"内容性质"建子目录；`dir_path` 一律相对语料根
**决策**：①`31-收件箱` 下固定三个语义子目录 `面经/`、`笔试/`、`面试题/`，批次目录
（日期+来源）放在其下；`folder_rules.yaml` 三条结构位规则钉在这三个目录上
（面经→面经/low、笔试→真题/high、面试题→题库/medium），批次名不携带语义。
②`intake.iter_files` 的 rel 基准从 `--root` 改为 `scan_base(root)`：root 在语料根内时
一律相对**语料根**登记（`--root 31-收件箱` 也写全 `31-收件箱/面经/...`），root 在语料外
（外部目录导入）时退回自身。
**理由**：`pipeline.py` 默认 `--root 31-收件箱`，旧逻辑把 `dir_path` 写成 `面经/2026-11-17-.../阿里/...`，
丢掉前缀后所有以 `31-收件箱/` 开头的结构位规则永久失配 —— 本轮 771 件整批判成未分类、
topic 723 条 none 就是这个根因；给收件箱加"无前缀版"规则等于把同一语义写两遍，
换根就再漏一次，不如把路径口径统一到语料根。
**验证**：①全量重扫 root=语料根 → `added` 771（面经 156 / 真题 392 / 题库 223）、`duplicate` 27；
27 件逐一核对为 `3-面经分享` 与 `11.1-公司面经故事` 的同内容副本。②修复后 `--root 31-收件箱 --dry-run`
报 `duplicate 798 / moved 0 / renamed 0`，证明同一文件两种扫法得到同一 `dir_path`。
③`tests/test_intake.py::test_subdir_scan_keeps_corpus_prefix` 锁死该口径，33 tests passed。
**数据修补**：把首跑写入的 771 行（`dir_path` 缺前缀）按"`src_path` 在收件箱但 `dir_path` 不带前缀"
条件删除后重登，零残留；`数据库面试题笔试题` 顶层 16 行的 `collection` 手工改回目录名
（该段含"数据库/SQL"主题词，被 `_is_topic_like` 剔除后落到了批次目录）。
