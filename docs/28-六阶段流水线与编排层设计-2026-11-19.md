# 28 - 六阶段流水线与编排层设计（2026-11-19）

> **状态**：现行（流程设计，对应 `docs/27` P1-1） · **最后实质更新**：2026-11-19 · **适用方案版本**：v2-R3
> 承接 `docs/27-方案与流程评审-2026-11-19.md` 的 P1-1（缺产物状态）。本设计只新增**编排层**
> 与**阶段登记**两块，现有 34 个独立子命令、事实源表、影子库切换、门禁全部保留不动。
> 目标：让"下一步该跑什么"可查询，让"跑到一半崩了"可续跑，让"检索库是否过期"有机器判定。

## 0. 结论

- 流程按 **S1 接入 → S2 标准化 → S3 质量治理 → S4 知识加工 → S5 发布构建 → S6 验收发布** 划分，
  与现有工具一一对应（§1 映射表，无一个阶段需要新写业务逻辑）。
- 每个阶段统一七项契约：输入清单 / 执行状态 / 成功-失败-跳过数 / 失败原因码 / 断点键 / 产物版本与哈希 /
  下一步建议。落两张表（`stage_runs`、`stage_failures`）+ 一份 `meta/reason_codes.yaml`。
- 落地节奏：**先 `kb status`（只读，不建表也能出六成信息）→ 再补 run 登记 → 最后 `kb run --stage/--until`**。
- 明确不做：任务队列、守护进程、分布式调度、事件总线、把六阶段塞进一个巨型 `pipeline()`。

## 1. 阶段与现有工具的映射

| 阶段 | 负责工作 | 现有工具（不改行为） | 核心产物 | 出口校验 |
|---|---|---|---|---|

| **S3 质量治理** | 文本质量三态、分流、人工复核 | `gate` `dispatch` `review_cli` | `gate_results`、`dispatch_plan.csv`、复核留痕 | 三态计数、`dispatch` 六路由闭合 |
| **S4 知识加工** | 切题、去重、聚簇、标签 | `extract` `question_freq` `canonical` `cluster` `batch_label` `taxonomy` | `questions`、`canonical_questions`、`labels_staging` | 覆盖率、G8 双份、G6/G6b（标签出口） |

| **S6 验收发布** | 检索评测、原子切换、回滚 | `eval_retrieval` `refresh --swap-only` `verify_ledger --docs` | 线上 `面经库.db` + 回滚快照 | hit@k 不回退、`quick_check`、行数一致 |

三条跨阶段一次性动作不进流水线：`bookmarks`（源边界，S1 之后跑一次）、`reconcile`（对账）、`verify --audit-converted`。

## 1.5 层次契约：加工 / 验收 / 发布 / 服务 四层不等权（ADR D-24）

六个阶段是**流程顺序**，四层是**职责边界**。同一份数据在链上流动时，每一层只能碰它该碰的东西：

| 层 | 允许做 | 绝对不做 | 判定标准 |
|---|---|---|---|
| **加工**（S1–S4） | 写事实源 `kb.sqlite`、写工作区产物（md / csv / staging） | 不写 `面经库.db`、不换线上指针 | 可以反复重跑，结果幂等 |
| **验收**（各阶段出口 + G1–G8） | 只读产物、只出 verdict（PASS / WARN / FAIL） | 不修数据、不改状态、不自动放行 | 判据写进 `15`，结果落 `stage_runs` / 报告 |
| **发布**（S5–S6） | 建影子 → 校验 → 原子换指针 → 留回滚 | 不做加工、不做判据（只消费 verdict） | 门禁不过**不得** swap |
| **服务**（`search` / `--format rag`） | 只读检索库 | 任何写入、任何隐式重建 | 进程被杀不影响数据 |

**逐脚本归属（现状）**

| 脚本 | 实际层次 | 合规性 | 处置 |
|---|---|---|---|
| `intake` / `classify` / `extract` / `canonical` | 加工（写事实源） | ✅ | 台账/题表本就是它们的产物；`extract` 经 `kb/mdmap.py` 把 md 产物映射回源，题池单身份（`27` P0-1） |
| `gate` / `dispatch` | 验收（`gate_results` + 路由报告） | ✅ | 只判、不改源状态（`gate_result` 字段待接，见 `27` P0-3） |
| `search` | 服务 | ✅ | 只读 |
| `build_db` / `embed` | 加工→**发布准备** | ⚠️ 写的是影子路径，但会 `DROP` 向量 | 结尾必须打印"向量已清空，需 embed"；禁止直跑覆盖线上 |
| `batch_label` | 加工 + 验收 + 写事实源 | ⚠️ 三层叠加 | G6/G6b 在 merge 前跑，merge 单事务；不得直连检索库 |
| `refresh` | 发布（含建库 + 验收 + 切换） | ⚠️ **白名单例外** | 唯一允许 swap 的入口；G1–G5、G8 不过则 ABORT |
| `doc_convert`（父） | 加工 + 写台账 | ⚠️ 写盘 + 写库 | 子进程只写 `.docx`，父进程持锁写台账 |
| `doc_convert --one`（子） | 纯加工（单文件） | ✅ | 不碰库、不拿锁，可被超时杀掉（T16） |
| `purge_origin` | 删除动作（不属于四层） | ✅ | 四重校验 + 只删盘不写库；**不进流水线** |

规则落地方式：①新增脚本若跨层，必须在本节登记例外并写理由；②`refresh` 之外任何脚本写 `面经库.db` 视为缺陷
（`27` P1-3 已按此收紧写锁）；③验收层的判据只能来自 `15` / `meta/thresholds.yaml`，不许各脚本自带一套阈值。

## 2. 七项统一契约（每阶段必须能回答）

| 契约 | 载体 | 说明 |
|---|---|---|
| **输入清单** | `build/manifests/<stage>-<run>.csv` | 由上一阶段产物生成，**不是运行前扫盘**。列：`item_key, src_ref, expected_artifact` |
| **执行状态** | `stage_runs.state` | `running / completed / failed / aborted`，只描述"这次运行"，不描述文档 |
| **成功·失败·跳过数量** | `stage_runs.ok_count / fail_count / skip_count` | 缓存摘要，权威明细在既有表/日志（见 `detail_ref`） |
| **失败原因** | `stage_failures.reason` + `meta/reason_codes.yaml` | 归一化原因码，禁止再写自由文本（现状 `note` 里什么都装） |
| **可恢复断点** | `stage_runs.checkpoint` | 每阶段的续跑键不同：S1 `doc_hash 续扫`、S2 `page_no`、S3 `md_rel`、S4 `(doc_hash,seq)`、S5 `影子库`、S6 `swap 快照` |
| **产物版本与哈希** | `stage_runs.artifact_path / artifact_hash` | 文件 sha256（单文件）或 `sha256(sorted(rel, sha16))`（目录集合） |
| **下一步建议** | `stage_runs.next_action`（工具可写）+ `kb status` 推导 | 缺失时由 status 按 DAG + 过期判定给出，不写死在脚本里 |

## 3. 与"文档状态机"的关系（关键：两套状态，不许合并）

- **文档生命周期状态**：`source_documents.status`，仍只表达"这份内容在库里是什么身份"（6 个活值 + 预留态，见 `docs/27` Q-3）。**不要为了阶段再加 `s2_done/s3_pass` 之类的列**，否则状态会膨胀成 6×N 并再次出现"漏改一处就是数据错误"。
- **阶段运行状态**：`stage_runs`，表达"第几次跑、跑了哪些件、结果如何"。
- 两者用 `item_key` 关联（源件用 `doc_hash`，产物用 `md_rel`，题目用 `(doc_hash, seq)`），`kb status` 做联表推导。
- 由此 `processing/processed` 的取舍变简单：它原本想表达的"有没有产物"由 `document_products`（`docs/27` P1-1）承担，`processing/processed` 可以直接降级为预留态，不必再找写入方。

## 4. 新增两张表（迁移 014）

```sql
CREATE TABLE stage_runs (
  run_id         TEXT PRIMARY KEY,   -- S4-20261119T0720-3fa1
  stage          TEXT NOT NULL,      -- S1..S6
  parent_run     TEXT,               -- 本次输入来自哪次上游 run（自引用）
  tool           TEXT NOT NULL,      -- mianjing_kb.extract（阶段内多工具时一个工具一行）
  argv_json      TEXT,               -- 可复现参数
  input_manifest TEXT NOT NULL,      -- build/manifests/S4-...csv
  input_hash     TEXT NOT NULL,      -- 清单内容 sha256（判"输入未变"→免重跑）
  input_count    INTEGER NOT NULL,
  ok_count       INTEGER NOT NULL DEFAULT 0,
  fail_count     INTEGER NOT NULL DEFAULT 0,
  skip_count     INTEGER NOT NULL DEFAULT 0,
  state          TEXT NOT NULL,      -- running|completed|failed|aborted
  started_at     TEXT NOT NULL,
  finished_at    TEXT,
  artifact_path  TEXT,
  artifact_hash  TEXT,
  checkpoint     TEXT,               -- 续跑键 + 已到位置
  detail_ref     TEXT,               -- 明细在哪：表名或 build/*.json|jsonl
  next_action    TEXT,
  note           TEXT,
  CHECK (state IN ('running','completed','failed','aborted'))
);

CREATE TABLE stage_failures (
  run_id    TEXT NOT NULL,
  item_key  TEXT NOT NULL,
  reason    TEXT NOT NULL,           -- meta/reason_codes.yaml 里的码
  attempts  INTEGER NOT NULL DEFAULT 1,
  last_at   TEXT NOT NULL,
  detail    TEXT,
  PRIMARY KEY (run_id, item_key)
);
```

设计约束：`stage_runs` **只登记摘要与指针**，不复制件级明细——`ocr_pages`、`gate_results`、`label_failed.csv`、
`convert_log.json` 已经是事实，再抄一份就是第三套真相（`docs/27` §三 P1-5 的教训）。

## 5. 阶段图：允许一条有界回边

```
S1 ──► S2 ──► S3 ──► S4 ──► S5 ──► S6
         ▲      │
         └──────┘  needs_ocr（限 1 次自动 + 人工确认）
```

- `S3 → S2` 是唯一回边（`dispatch` 的 `needs_ocr`）；`stage_failures.attempts` 到上限就转人工，
  防止"OCR 重试 → 仍失败 → 再重试"的无限循环。
- `S4` 有两个出口：**结构出口**（题块 + 聚簇 + G8 双份）必须先过才允许进 S5；
  **标签出口**（LLM 打标 + G6/G6b）允许延后，S5 不得因"标签为空"而阻塞（现状 `difficulty/tags` 全 0 仍能建库，就是这条）。
- `S5 → S6` 的切换动作只走 `refresh` 既有机制（影子库 + G1–G5 + `os.replace` + 快照回滚），编排层只负责"按需调用 + 记录 run"。

## 6. `kb status`：只读，先上（不依赖新表也能出六成信息）

### 6.1 输出形态（每阶段一行，人读 + `--json`）

```
阶段   最近成功 run      本次输入     待处理   失败   产物            是否过期   建议
S1     11-19T07:20 3fa1  +12 件      0        0      ingest_list    否         —
S2     11-19T07:40 b19c  +9 件       3(OCR)   1      md 1,434      **是**     S3 有新件未跑
S3     11-18T23:10 77de  0           0        0      gate_report   否         review 队列 2 件待裁
S4     11-19T03:58 5c02  0           0        0      questions     否         标签出口未跑（G6/G6b SKIP）
S5     11-19T02:58 a0f1  —           0        0      面经库.db     否         —
S6     11-19T02:58 a0f1  —           —        —      线上库         否         可发布
```

### 6.2 判定规则（纯推导，不猜）

| 判定 | 规则 |
|---|---|
| **过期** | 上游 `artifact_hash` ≠ 下游 `parent_run` 记录的输入 `input_hash`；或上游 `finished_at` 晚于下游 |
| **待处理** | 输入清单中存在 `item_key` 在本阶段无对应 `stage_runs` 成功记录（或 `document_products` 缺行） |
| **失败** | `stage_failures` 按 `reason` 分组计数（`--reason` 下钻到件级） |
| **断点** | `state='running'` 或 `failed` 且 `checkpoint` 非空 → 提示"可从 X 续跑，已到第 N 件" |
| **建议** | DAG 上第一个"待处理>0 或过期"的阶段；同时附上该阶段实际要跑的命令 |

关键实现点：**"过期"靠哈希比对，不靠时间戳猜**——打标 merge 后忘记 `refresh` 这类事故，status 必须直接报
`S5 过期（S4 产物 5c02 未进入检索库）`，而不是等人想起来。

## 7. 编排层演进（三档，逐档可停）

| 档 | 形态 | 行为 | 前置 |
|---|---|---|---|
| **v0** | `kb status [--json] [--reason]` | 只读汇总 + 建议下一步 | 无 |
| **v1** | 各工具写 `stage_runs` / `stage_failures` | 每次运行落一行摘要（先接 S1/S4/S5 三个最高价值阶段） | 迁移 014 |
| **v2** | `kb run --stage S2 [--dry-run] [--resume]` | 选清单 → 调既有工具 → 校验产物 → 落 run；`--resume` 用 `checkpoint` | v1 + 清单格式 |
| **v3** | `kb run --until S6` | 按 DAG 串阶段，逐段调用；任一段失败即停并给原因与续跑命令 | v2 |

编排层的三条硬约束：

1. **只做"选择 + 调用 + 登记 + 校验"**，不把业务逻辑搬进 `orchestrator.py`；工具行为不变，CI 与单测不受影响。
2. **每段跑完必须校验产物**（存在性 + 哈希 + 该段的出口门禁），不通过就不写 `completed`。
3. **默认 dry-run 语义与本阶段一致**：`--dry-run` 也要写一条 `state='aborted'` 的 run 作为"预演留痕"，否则 status 看不出来跑过。

## 8. 与其他已知问题的咬合点

| 已有结论 | 在本设计里的落点 |
|---|---|
| P0-1 双身份（源文件 + md 镜像各抽一遍） | S4 的**输入清单**只允许"一文档一条 expected_artifact"；`document_products` 缺行即视为"未标准化"，从源头杜绝两个身份进同一清单 |
| P0-2 门禁自证 | 每阶段的出口校验写进 `stage_runs`（S1 判重计数、S3 三态、S4 G8、S5 G1–G5、S6 hit@k）；不再有"门禁在旁路跑、结论不进链" |
| P0-3 门禁不进主链 | S3 是独立阶段，`verdict` 落 `document_products.gate_verdict`；S4 的输入清单只取 `pass` |
| P1-3 锁覆盖不全 | 编排层在每段开始前按"目标库"取锁（`kb` / `online`），并在 run 里记 `lock_target`；不允许"编排层绕开锁" |
| P1-5 产库未迁移 | v1 上线前必须先做"copy → migrate(014) → verify"预演；`kb status` 在检测到 `schema_version` 缺失时直接告警"产库未迁移" |
| P1-6 文档漂移 | `kb status` 的六行输出即"当前口径"，文档基线表改为引用它，不再手抄数字 |

## 9. 验收（可执行）

1. **可查询**：`kb status` 在生产库只读跑通，六行齐全；人为改动 `kb.sqlite` 后 S5 必须报过期。
2. **可续跑**：`kb run --stage S4 --resume` 在中断点只处理剩余件；重跑同一输入，`input_hash` 相同 → 显示"无需重跑"。
3. **可追溯**：任一 `run_id` 能反查到输入清单、参数、产物哈希、失败件与原因码；
   `kb status --stage S5 --reason vec_missing` 能列出具体 `md_rel`。
4. **不回归**：`pytest` 全绿；`ruff/pyflakes` 双 0；`kb demo` 一条命令仍跑通（编排层不接管 demo）。
5. **不膨胀**：`stage_runs` 行数增长 ≈ 每次运行 × 阶段内工具数，不随文档数线性增长（明细留在既有表）。
