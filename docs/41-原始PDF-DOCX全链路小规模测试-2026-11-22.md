## 五、发现的问题（按严重度）

### F1（P1）英文实体在向量层塌缩成同一个点，关键词层又整句匹配 → “X 是什么”类提问首位必错

证据链：

1. `bge-small-zh-v1.5` 分词器把词表外拉丁词整词映射成单个 `[UNK]`：

```
'ThreadLocal' -> [CLS] [UNK] [SEP]        ids [101, 100, 102]
'Kafka'       -> [CLS] [UNK] [SEP]        ids [101, 100, 102]
'Redis'       -> [CLS] [UNK] [SEP]        ids [101, 100, 102]
'HashMap'     -> [CLS] [UNK] [SEP]        ids [101, 100, 102]
'ThreadLocal 是什么' / 'Kafka 是什么' -> [CLS] [UNK] 是 什 么 [SEP]（完全相同）
```

2. 实测向量余弦：`ThreadLocal` vs `Kafka` = **1.0000**；`ThreadLocal 是什么` vs `Kafka 是什么` = **1.0000**（L2 = 0.0）。
3. `keyword_search` 用整句做 FTS 短语查询（失败后回退 `LIKE '%整句%'`），`ThreadLocal 是什么` 命中 0 条 → 融合里只剩向量一路。
4. 实跑结果：`Q=ThreadLocal 是什么` → 第 1 名 `Kafka 是什么`（d=0.00），正确的 `什么是 ThreadLocal?` 排第 2（d=0.56）。去掉中文尾巴只查 `ThreadLocal` 时关键词层命中 1 条，融合后能排第 1（此时向量层把 `关于 JVM` 排第 1）。
5. 本域提问天然以英文术语为主（JVM/Redis/Kafka/Spring/HashMap/ThreadLocal），语料里这些词同样是拉丁词——**这不是边角 case，是主查询形态**。

建议（按收益排序）：

1. 查询预处理：抽取拉丁实体词（`[A-Za-z][A-Za-z0-9_+#.-]*`）单独作为 FTS 词项（`"ThreadLocal"` 或 OR 组合），而不是整句短语；同时保留整句 LIKE 兜底。
2. 实体命中加权：拉丁实体精确命中（题干/答案包含）给 RRF 额外分，压过纯语义分。
3. 入库侧给英文实体补中文对照（`ThreadLocal 线程本地变量`）再向量化，绕开 `[UNK]` 塌缩；或换多语/含英文子词的中文嵌入（bge-m3 类）。
4. 顺带启用 bge 的 query instruction（`query_embed`），当前入库与查询都用 `embed`，检索侧未用指令前缀。

### F2（P2）检索库 `source_path` 恒为空：`doc_contents` 用 `mirror_hash` 连接，命中 0

- `search.py:48`：`LEFT JOIN doc_contents dc ON dc.mirror_hash=q.doc_hash`。
- 实测本测试库：按 `mirror_hash` 连接命中 **0** 行；按 `doc_hash` 连接命中 **219** 行（全部）。
- 后果：`source_path`（md 相对路径）永远空，RAG 引用只剩文件名；同簇多来源时无法区分具体 md。`doc_contents.content` 也因此取不到（改写/溯源场景拿不到原文段）。
- `build_db` 明确同时写了 `doc_hash` 与 `mirror_hash`，G8 也按 `doc_hash` 记账——连接键应与 G8 一致：
  `LEFT JOIN doc_contents dc ON dc.doc_hash=q.doc_hash`（保留 mirror 兜底可再 JOIN 一次 `COALESCE`）。
- **已修（见 §10）**。

### F3（P2）`refresh` 不落 `verify_report`，发布后 `kb status` 必然 STALE

- `refresh.py` 全文无 `verify_report` / `db_identity` 写入；它只在切换前跑 G1–G5+G8 并把结论写进 publish manifest。
- 测试序列实证：`verify`（19:22:24 写报告）→ `refresh`（19:22:41 切换 + 回写 `indexed_at`）→ `status` 报 `STALE 过期原因：kb:库已变化；out:库已变化`。
- 生产现状同构：`verify_report` 的 `at=2026-11-19T19:28:32`，绑定 `out` 指纹 425,476,096 B，而线上库已是 425,480,192 B / 22:53 → 生产 `kb status` 现在也是 STALE（20010 题）。
- 后果：每次发布后运维都会看到“门禁报告需重跑”，真实告警被这种固定噪声稀释。
- 建议：`refresh` 切换成功、`_mark_indexed` 之后重写 `verify_report.json/.md`（写入切换后的真实指纹 + 内置门禁结论），或在 `status` 侧对最新 publish manifest 的 gates 做兜底读取。
- **已按第一种改法修复（见 §11）**。

### F4（P3）题干残留 Markdown 强调符与中文题号，影响展示与整句匹配

- 219 题中 **50 题题干含 `**`**（如 `**48** 、 **Redis** 提供了哪几种持久化方式?`），**44 题答案含 `**`**。
- 这是转换产物（pymupdf4llm 加粗）被切题器原样保留：展示脏、与 F1 的整句匹配叠加时更难命中。
- 建议在切题产物落地前剥除行内 `**`/`__`、行首 `\d+\s*[、.]\s*` 题号（不影响 `q_norm_hash` 的既有口径，若要改归一规则需按 `NORMALIZER_VERSION` 流程迁移标签）。

### F5（P3）md 命名两套并存，`gate --audit` 的 `drift` 口径与之互斥

- 生产 `20-题库MD`：`__<hash8>` 997 个、`_<hash8>` 28 个、纯 `stem.md` 409 个。
- `gate.py:264` 把“解析到的 md != 规范 `stem.md`”一律记 `drift`，因此任何 hash 命名件都算 drift；本轮 11/11 全 drift，就是因为 driver 用 `reconvert` 口径（`_<hash8>`）。
- 后果：drift 失去“异常漂移”的告警意义（生产若按 convert_log 审计 reconvert 过的件，也会被计 drift）。
- 建议：统一为 `__<hash8>`，并把 `drift` 判据放宽为“stem 与 hash8 都匹配即不算 drift”，只把真正指向别的文档记 drift。

## 八、结论

1. 链路本身**跑得通、守得住**：11 件原始文件 38 s 转出 11 份 md，门禁零异常，切出 219 题零空答案，G1–G5/G8 全 PASS，`refresh` 原子切换一次成功并可回滚。
2. 真实风险不在转换与切题，**在检索层（F1）与可追溯性（F2）**：英文术语塌缩让“X 是什么”这类最高频提问首位出错；`source_path` 恒空让引用只剩文件名。
3. 发布链路有个恒定的噪声源（F3）：`refresh` 不落门禁报告 → 每次发布后 `status` 必报 STALE，生产当前正处于该状态。
4. 建议下一轮按 F1 → F2 → F3 → F4/F5 的顺序修，F1 先做“拉丁实体抽词 + FTS 词项 + 实体命中加权”，这是最小改动、收益最大的一刀。

### 9.2 最终实现（`mianjing_kb/search.py`）

- `latin_terms()`：抽 `[A-Za-z][A-Za-z0-9_+#.-]{1,}`，长度 ≥3、忽略大小写去重。
- `entity_route_terms()`：**仅当单实体且中文 ≤6 字**才启用路由/聚焦（`ThreadLocal 是什么`、`Redis 持久化`、`JVM 内存区域划分`）；多实体长问句一律不走，避免泛实体噪声。
- `keyword_search(..., allow_entity_route=)`：整句 FTS 未命中 → 实体词项 FTS → 整句 LIKE → 词项 LIKE；hybrid 传 `False`，只有**无向量层/模型不可用**的降级路径才启用。
- `hybrid_search`：单实体短问时把向量候选**聚焦**到含该实体的行（无命中则回退全量）；`_row_has_term` 去空白匹配（`SpringBoot` ↔ `Spring Boot`）。
- `entity_tiebreak()`：融合分完全并列时命中实体者优先，只破并列、不改分。

- 全量 pytest **740 collected，exit 0**（原基线 728 passed / 1 failed，该 failed 已随本轮之前的修复消失）；`ruff check` 干净。

## 十、F2 修复记录（同日落地）

### 10.1 根因与改法

- 原 `_JOIN` 只按 `dc.mirror_hash=q.doc_hash` 连接 `doc_contents`；正常入库文档的 `questions.doc_hash` 是源 doc_hash，一个也连不上（测试库 0/219），`source_path` 恒空。
- 改为标量子查询：`doc_hash` 优先、`mirror_hash` 兜底（孤儿 md 题的 `doc_hash` 本身就是 `md-mirror:` 哈希），`source_path` 与 `source` 用同一套取法：
  `COALESCE(d.file_name, COALESCE(md_by_doc, md_by_mirror))`。
- 不用 `JOIN 两张 doc_contents` 的原因：生产 `doc_contents` 有 **48 个 doc_hash 对应多份 md**（同一原文的库内多份镜像，如 `专题笔记/…` 与 `题库/…`）。直接 JOIN 会让一条题变成 2–3 条结果。改用 `ORDER BY (md_rel NOT LIKE '题库/%'), length(md_rel), md_rel LIMIT 1` 只挑一条，既去重又优先给题库口径路径。

### 10.2 验证

- 新增 2 条用例：`test_source_path_resolves_by_doc_hash`（正常文档回链 md + 孤儿 mirror 兜底）、`test_duplicate_md_rows_do_not_multiply_hits`（同一 doc_hash 两行 md 时结果行数不翻倍且选 `题库/` 路径）。
- 原 `test_source_resolution` 未改：`documents.file_name` 仍优先（q1 仍给 `MySQL面试题.pdf`）。

## 十一、F3 修复记录（同日落地）

### 11.1 根因与改法

- `refresh` 只把门禁结论写进 publish manifest，从不写 `verify_report`；而 `status._gate_summary` 是拿报告里的 `db_identity` 与当前文件 `size_bytes/mtime_ns` 比对，切换 + `_mark_indexed` 一定会改指纹 → 发布后必 STALE。
- 新增 `_stamp_verify_report(build_dir, online)`：切换成功、`_mark_indexed` 之后**对线上库重跑 G1–G5/G8**，再调 `verify_ledger.write_report` / `write_backfill_plan` 落 `verify_report.json/.md` 与 `backfill_plan.csv`。报告写失败只记 warning，不回滚已完成的切换。
- 顺序是硬约束：报告必须晚于 `indexed_at` 回写，否则又给旧指纹盖章。G9 是软门且字段口径（`details`，无 `sql`）与 `verify_report` 不同，留在 refresh summary，不进报告。
- 生产 2 万题这套门禁实测 15 s 量级，重跑代价可接受（比“每次发布后固定红一次”便宜）。

### 11.2 验证

- 新增 `test_swap_writes_verify_report_bound_to_post_swap_files`：断言报告 `db_identity.kb/out` 与切换后真实 `size_bytes/mtime_ns` 逐一相等，且 `status._gate_summary` 判 `PASS / stale=False`。

- 全量 pytest 全绿、`ruff check` 干净。

### 11.3 残余

- 生产库当前那版 `verify_report`（`at=2026-11-19T19:28:32`，绑 425,476,096 B）仍是旧口径，需要跑一次 `kb verify` 或下一次 `refresh` 才会自动痊愈。
