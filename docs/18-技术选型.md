# 18-技术选型（mianjing-kb 面经题库知识库）

> 本文记录项目**已经落地**的技术栈与取舍理由，不讨论尚未采用的方案。所有结论均可追溯到仓库内的代码或文档；历史口径与当前代码不一致时，以代码为准并注明差异。
> 关联：`docs/00-决策记录.md`（ADR D-01~D-23）、`README.md`、`docs/17-项目审核与修复报告-2026-11-17.md`、`docs/项目审核报告/20026-11-19.md`。

## 1. 背景与范围

项目目标是把 `<CORPUS_ROOT>` 下的面经/真题/题库语料，加工成可检索、可抽题、可核验的知识库。语料与代码分离：语料留在原地不搬迁（README.md:3-4），本仓库只放可版本化的方案文档、元数据规则、管线脚本与测试（README.md:4）。

这一约束决定了整体选型基调：

- **本地优先、零 API 成本可跑**：OCR、向量、LLM 都能在本地跑通，云 OCR 因预算被整条删除（ADR D-02）。
- **单文件、可原子切换、可核验**：一切围绕 SQLite 文件库，不引入需要独立服务的组件。
- **规则可版本化、可人工覆盖**：分类/主题规则放 `meta/` 进 git，事实源落数据库而非散落文件。

## 2. 选型总表

| 层次 | 选型 | 关键落点 | 一句话理由 |
|---|---|---|---|
| 语言/运行时 | Python 3.11 | `mianjing_kb/` 全部脚本、`.pytest_cache` 的 `cpython-311` | 数据处理/脚本生态最直接，Anaconda 环境即开即用 |

| 向量检索 | sqlite-vec（vec0）+ bge-small-zh-v1.5（fastembed ONNX，512 维） | `mianjing_kb/embed_questions.py`、`mianjing_kb/search.py:5,80-103` | 与 SQLite 同进程，避免独立向量库 |

| 工程化 | pytest + 单源配置 + 影子库原子切换 + 门禁核账 | `tests/`（187 用例）、`mianjing_kb/kb/config.py`、`mianjing_kb/refresh.py`、`mianjing_kb/verify_ledger.py` | 测试兜底、配置可覆盖、上线可回滚可核验 |

## 3. 逐层决策

### 3.1 语言与运行环境：Python 3.11

- **选了什么**：全部工具链为 Python 脚本，运行于 `python`（README.md:66），基线环境 i5-13400F / 31.9 GB（README.md:114）。
- **为什么**：语料加工是典型的 I/O + 文本处理任务，Python 的标准库（`hashlib`、`sqlite3`、`csv`、`pathlib`）已经覆盖判重、落库、导出等主要需求，无需编译链。
- **替代方案**：曾考虑 shell/PowerShell 串起流程，但中文文本处理、NFKC 归一化、JSON 解析在 Python 里更可靠；PowerShell 只保留一个历史脚本 `scripts/补录-doc转docx.ps1`，且已标记 DEPRECATED（README.md:59）。

### 3.2 元数据存储：SQLite + WAL，事实源唯一

- **选了什么**：`kb.sqlite` 以 `source_documents` 为**唯一事实源**（ADR D-10）；`registry.json` 降级为"一次扫描的快照"（README.md:151）。所有写库脚本以末尾一次 commit 保证原子性。
- **为什么**：
  - 数据量级（1,501 行登记、32,087 题）远未到需要独立数据库的程度；
  - WAL 模式（`meta/schema/001_init.sql:4`）支持并发读与原子写；
  - 单文件便于备份、复制、影子重建。
- **替代方案**：关系型数据库服务（MySQL/PostgreSQL）需要独立部署与运维，与"零运维、本地优先"相悖；纯 JSON/CSV 无法承担"判重 + 状态机 + 事务 + 索引"的组合需求。
- **代价**：SQLite 单写者，批量导入期间独占写锁——通过"批增一条命令 + 单事务"规避（README.md:105-108）。

### 3.3 全文检索：FTS5 trigram，短查询 LIKE 兜底

- **选了什么**：检索库 `面经库.db` 中 `questions_fts`（题干+答案前 8000 字）与 `docs_fts`（文件名+正文）都用 `tokenize='trigram'`（`mianjing_kb/build_db.py:69-70`）。
- **为什么**：中文没有天然空格分词，trigram 把中文当 3 字符片段切分，直接支持任意子串查询；实测 2 字查询走 LIKE 全扫（13.5k 行 ms 级），3 字及以上走 FTS（`mianjing_kb/build_db.py:139-151`）。
- **替代方案**：ES/Solr 需要独立服务与中文分词插件；SQLite 原生 FTS5 已足够，且能与问题表同库 JOIN（`mianjing_kb/search.py:41-46`）。
- **已知限制**：trigram 要求查询串 ≥3 字符，否则回退 LIKE（`mianjing_kb/search.py:59`、`mianjing_kb/build_db.py:139-140`）；MATCH 语法对 `?`/`"` 敏感，用双写引号的短语查询规避（`mianjing_kb/search.py:60-66`）。

### 3.4 向量层：sqlite-vec + bge-small-zh-v1.5（512 维）

- **选了什么**：`vec_questions` 用 sqlite-vec 的 `vec0` 虚表，模型 bge-small-zh-v1.5 经 fastembed ONNX 运行，维度 **512**（`mianjing_kb/search.py:5`、`mianjing_kb/embed_questions.py`、`mianjing_kb/refresh.py:77-80`）。
- **为什么**：sqlite-vec 与 SQLite 同进程，KNN 查询 `WHERE embedding MATCH ? AND k=?`（`mianjing_kb/search.py:98-102`）不需要独立向量服务；bge-small-zh 对中文语义召回质量与体积平衡好。
- **替代方案**：独立向量库（Faiss/Milvus）运维成本高；项目规模（18,642 向量）用 sqlite-vec 完全够。
- **代价与债务**：全量重嵌约 9 分钟（README.md:173），暂无增量需求；审核报告指出 `copy_vec` 按 rowid 拷贝，重切后 qid 重排会导致向量静默错配（审核报告 B3），需 `--reembed` 或加内容对齐校验。

### 3.5 文档解析与 OCR：本地零成本

- **选了什么**：
  - PDF/docx/md → md 产物复用语料侧 `convert.py / convert_one.py`（README.md:146），本仓库不复制不改写；
  - `.doc`（OLE 复合文档）必须由 Word COM 转 docx，并用 **zip 魔数验收**（README.md:132，`mianjing_kb/doc_convert.py`）——首轮用 `SaveAs2/16` 存出的是 OLE 顶着 `.docx` 后缀的假文件，已全部删除重转；
  - OCR 用本地 PaddleOCR-json，`KB_OCR_ENGINE_DIR` 可覆盖，**当前引擎 v2.1.5**（`mianjing_kb/kb/config.py:67-72`），200 DPI，页级记录落 `ocr_pages` 表支持断点续跑。
- **为什么**：云 OCR 因预算被整条删除（ADR D-02）；本地引擎零 API 成本，历史实测初始化 0.99 s、0.72–0.80 s/页（README.md:136）。
- **口径差异（以代码为准）**：README.md:136 与审核报告记的是 OCR v1.4.1（历史快照），但 `mianjing_kb/kb/config.py:67-72` 已迁至 **v2.1.5**；本文以代码为准。
- **替代方案**：调用云 OCR API 被预算否决；自研 OCR 不现实。

### 3.6 LLM 层：OpenAI 兼容客户端 + staging 打标

- **选了什么**：`mianjing_kb/llm_client.py` 自研 OpenAI 兼容客户端，具备 provider 路由（local / online）、重试退避、JSON 宽松解析、脱敏；打标走 `batch_label.py`：staging 暂存 → G6 门禁 → merge（`mianjing_kb/batch_label.py`）。
- **为什么**：统一接口适配本地 ollama（qwen3-4b）与在线模型，避免绑定某厂商 SDK；staging 中间层让打标可预算封顶、断点续跑、抽查、单事务 merge。
- **替代方案**：直接调厂商 SDK 会锁定 provider；无 staging 直接写 questions 则无法断点续跑与回滚。
- **已知债务**：审核报告指出打标三件套中"人工金标"与"高级模型复核"只有影子没有实现（`docs/项目审核报告/20026-11-19.md` §四）；G6 drift 指标语义方向反了、qid 漂移会静默丢打标——这些是待补强项，不影响本项目已落地部分的事实认定。

### 3.7 工程化：单源配置 + 测试 + 影子切换 + 门禁

- **单源配置**：`mianjing_kb/kb/config.py` 集中路径、扩展名白名单、门禁阈值、`KB_*` 环境变量覆盖（`config.py:1-8,14-17`）。已知 P3 债务：gate 阈值在 `config.py:50-54` 与 `mianjing_kb/gate.py:52-54` 双份定义，有漂移风险。
- **测试**：pytest，187 个用例全绿（`docs/项目审核报告/20026-11-19.md` 实测核实；README.md:60 声明）。
- **影子切换**：`mianjing_kb/refresh.py` 把高风险的原地重建放到影子库 `面经库_shadow.db`，G1-G5 硬门禁全过才 `os.replace` 原子切换；WAL 侧车（`-wal`/`-shm`）必须清理，否则旧 WAL 会硬套到新主文件（`refresh.py:16-17,165-169`）。
- **门禁核账**：`mianjing_kb/verify_ledger.py` 提供 G1-G7 统一核账，任一硬门禁 FAIL 非 0 退出并产 `backfill_plan.csv`（README.md:56）；"门禁即清单"是项目自认最强的设计之一（审核报告 §一）。

### 3.8 元数据规则层：YAML + JSON 进 git

- **选了什么**：`meta/topic_rules.yaml`（文件名→topic，30 条）、`meta/folder_rules.yaml`（目录结构位→category/source_trust）、`meta/overrides.json`（人工覆盖，最高优先级）、`meta/exclusions.json`（出题池排除，保留检索不抽题），全部进 git（`mianjing_kb/kb/config.py:58-64`）。
- **为什么**：规则可版本化、可审计、可人工修正；目录结构承载语义（`docs/03 §8`、`docs/00-决策记录.md` D-05/D-20），而 topic 不等于目录名。
- **替代方案**：把规则硬编码进脚本会让每次调整都需要改代码；把规则放数据库则失去 git 的版本追踪与评审能力。

## 4. 关键架构决策回顾（与选型相关）

摘自 `docs/00-决策记录.md`，这些 ADR 直接约束了技术选型：

| ADR | 决策 | 对选型的约束 |
|---|---|---|
| D-01 | 先把方案打磨到可执行，暂不跑批处理 | 先文档后代码，工具链按阶段落地 |
| D-02 | 云 OCR 预算整条删除，改本地 PaddleOCR-json | 锁定本地 OCR 路线 |
| D-03 | 门禁替代"文本层检测" | 三态门禁成为质量基础设施 |
| D-04 | 判重先于 OCR | sha256 判重前置，省 OCR 成本 |
| D-05 / D-20 | 目录名是 collection 不是 topic；收件箱按内容性质建子目录 | 目录结构承载来源语义，topic 靠规则/近邻/覆盖 |
| D-07 | 先分类，再处理（流水线顺序不可逆） | 分类是所有下游的前置状态 |
| D-09 | 仓库建在 `<REPO_ROOT>` | 有意识偏离 `<REPO_BASE>` 统一约定 |
| D-10 | 原文档表是唯一事实源 | SQLite `source_documents` 为中心 |
| D-13 | 可入库清单落地为视图 + CSV，而不是新表 | `ingest_queue` 视图而非冗余表 |
| D-16 / D-17 | 合并轮改变判重口径；过时件进 99 区，物理删除有硬 gate | 判重与退役口径约束 intake/purge |
| D-23 | 隔离区副本不是可靠来源，新增 `revived` | intake 状态机扩展 |

## 5. 约束与已知代价

1. **qid 漂移**：`extract.store()` 按 doc_hash DELETE+INSERT，qid 是 AUTOINCREMENT，重切后重排；打标事实源落 `questions.topic`（按 qid merge）会静默丢失（审核报告 B1）。项目已用 `canonical.variant_id = doc_hash:seq` 稳定键规避部分问题（`mianjing_kb/canonical.py:39`），但打标层未跟上。
2. **打标 merge ≠ 检索生效**：merge 只写 kb.sqlite，检索库 topic 是 build_db 快照，需再跑 refresh 重建才生效（审核报告 B2）。
3. **向量错配**：`copy_vec` 按 rowid 拷贝，G4 只查行数/qid 集合相等，qid 重排后 G4 必过但向量指向错题（审核报告 B3）。
4. **OCR 口径差异**：README 记 v1.4.1，`config.py:67` 实为 v2.1.5（本文以代码为准）。
5. **性能基线**：hash 判重 ~860 MB/s；全量重扫 4.6 s；全量重嵌 ~9 分钟（README.md:116-137,173）。

> 以上 1–3 是审核报告明确记录的待补强项，属于"已识别的架构债务"，不是选型失误；选型层面的应对（稳定键、内容对齐校验、refresh 联动）见 `docs/项目审核报告/20026-11-19.md` §五 P0。
