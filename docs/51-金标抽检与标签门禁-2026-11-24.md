# P2 落地：金标抽检、标签侧门禁与重复拷贝一致性（2026-11-24）

> 状态：已完成（2026-11-24）
> 依赖：`docs/50`（全量落库 15,704 + 72 条，标签 726 → 16,438）
> 结论：**G6b 从"永远 SKIP"变成真门禁（60 条金标，topic 准确率 0.90 PASS）**，
> 过程中还查出两个比"准确率"更值得修的问题：同一道题的多份拷贝标签互相矛盾（934 处统一）、
> 主题词表把"组级"和"产品级"混在一个平面（金标比对把 10 处口径差异记成标错）。

## 1 起因

全量落库后剩下的 P2 三项：60 条分层金标、标签侧质量 WARN、语料侧补题。
本轮做前两项——金标是质量门禁的前提，跳过它就等于 16,438 条标签只过了结构校验，
没有任何语义抽检依据。

## 2 金标抽样与标注

- 抽样：从 17,090 条有标签的题里按 topic 轮转抽 **60 条**（47 个主题，每个主题最多 5 条），
  小主题不被大主题淹没；`q_norm_hash` 非空才进池（金标以 hash 为键，跨重切存活）。
- 标注：逐条读题干+答案片段后填 `topic_gold`，在合法 topic 词表内取值；
  `difficulty_gold` 留空（避免用主观难度污染指标），`qtype_gold` 留空。
- 标注人记为 `assistant-review`——**这是 AI 初标，不是人工终审**，需要在有人的时候复核一遍
  才能当"人类金标"用。标注方法与判定口径（碎片行一律记"其他"）见 `build/_golden_fill.py`。

## 3 第一次评估：0.7785 FAIL，以及它到底说明什么

| 项 | 值 |
|---|---|
| matched | **149**（60 条金标被撑到 149） |
| topic_acc | 0.7785 → G6b FAIL |
| weak_topics | MyBatis、RabbitMQ、Spring、其他、工程与质量 |

拆开混淆矩阵看，31 处不一致里只有很小一部分是"模型真错"：

1. **重复拷贝**：同一道题在 7 篇源文档里各有一条，模型给有的盖了 topic、有的留空；
   7 处 MyBatis 的"错"其实是 7 份未打标的拷贝。
2. **粗细粒度**：`RabbitMQ ↔ 消息队列`、`Memcached ↔ 缓存与中间件` 共 10 处——合法 topic 里
   既有产品级也有一级组级，同一题标成哪一级都说得通，字面比对把它们记成了错。
3. **8 处 CSRF 全标"计算机网络"**：语料里没有"安全"这个 topic，模型统一归到计算机网络，
   而我的金标写了"工程与质量"。这是词表缺口，不是模型错。

于是先修真正的数据问题，再改比对口径——不是为了让门禁变绿而放宽。

## 4 三处修正

1. **G6b 回落 questions**（`verify_ledger.py`）：merge 会清空 staging，原来只和 staging 求交集，
   于是金标建好后永远 WARN"无交集"，门禁建完即失效。改为 staging 优先、无交集时按同一
   `q_norm_hash` 回落 questions（生产标签才是最终真相）。
2. **同 hash 去重**：金标以 hash 为键，但 questions 里同题多拷贝会让 n 从 60 膨胀到 149，
   置信区间和准确率都失去统计意义。现在每 hash 只算一次（优先取有 topic 的那条）。
3. **`topic_family` 族谱**（`meta/topic_rules.yaml` 新段 + `vocab.topic_family_root()`）：
   只给金标比对用，明确声明"产品级是组级的细化"，同族视为一致；不改落库 topic。
   目前登记 9 条（RabbitMQ/Kafka/RocketMQ/ActiveMQ → 消息队列 → 缓存与中间件；
   Redis/Memcached → 缓存与中间件；MySQL/MyBatis → 数据库）。

修正后：matched **60**、topic_acc **0.90**、95% 下界 0.7985 → **G6b PASS**，`weak_topics` 只剩"其他"
（碎片行与"非题目"行，见 §8）。

## 5 顺手查出的真问题：同题多拷贝标签互相矛盾

按 `q_norm_hash` 聚合发现 **4,556 组多拷贝**，同一道题在不同源文档里被独立打标：

| 动作 | 数量 |
|---|---|
| topic 被统一到该 hash 的多数值 | **934** |
| 空的 tags 从同 hash 兄弟行补齐 | **666** |

例子：`read uncommitted` 那道题 6 份拷贝曾分别标成 数据库/MySQL/其他；"块砝码称量"碎片
5 份拷贝标了 5 个不同主题。检索侧同一道题出现两种 topic，等于主题过滤会漏。

一次性脚本 `build/_consolidate_hash.py`（dry-run 默认）做多数归并，平票跳过不猜。
这条已**进产品流程**：`batch_label.merge()` 在落库后调 `_propagate_by_hash()`，
对本批涉及的每个 q_norm_hash 把多数 topic 推给全部拷贝，并用有标签的兄弟行补齐空拷贝的
tags/qtype/difficulty（等于免费覆盖一批"待打标"）。输出多一行
`hash_consistency: {hash_rows_changed, hash_rows_filled}`，每次增量 merge 都自动保一致性。

## 6 标签侧两条 WARN（只告警不挡 merge）

阈值按生产实测标定，不照抄"40%/20%"：

| 指标 | 生产实测 | WARN 线 | 触发含义 |
|---|---|---|---|
| 词表命中率 | 23.8%（16,438 题 64,348 次标签） | **< 20%** | 开放词表低命中是设计如此；掉到 20% 以下说明词表/prompt 失效 |
| 维度重复率 | 0（stopwords 生效后） | **> 2%** | 维度词又回流进 tags（P0 的回归哨兵） |

`label_quality.assess` 新增 `detail.tag_metrics`，从 staging 现有 tags 复算，不依赖打标时的瞬时统计。

## 7 生产 tags 清洗与维度词漏剔

发现 `tag_stopwords()` 只收了 topic 词表与一级组名，**没收别名键**（`求职与行为`→`HR与求职`
这类旧写法）。生产库残留 343 次维度词，其中 248 次就是别名键。

- 停用词补上别名键（`vocab.py`）；
- 一次性清洗已落库 tags（`build/_clean_questions_tags.py`）：**1,003 行变更、剔 1,356 个维度词、
  截断 1,452 个超 4 的标签**；
- 清洗后自由标签 Top 变成 `网络协议/分布式系统/Spring MVC/依赖注入/面试技巧`——
  维度词（求职与行为、HR与求职、Java）已不再出现在前 15。

## 9 残留与风险（不粉饰）

1. **金标是 AI 初标**：`annotator=assistant-review`，没有人工复核前不能当人类金标；
   G6b PASS 只说明"两套标注口径大体一致"，不等于"标签正确率 90%"确实是独立第三方标准。
2. **同题多拷贝**：一次性归并 + `merge()` 内 `_propagate_by_hash()` 已覆盖（见 §5）；
   仍有一个口子没堵——打标阶段仍按 qid 各打各的，一次批次里同 hash 的多拷贝会各花一次
   LLM 调用并可能写出不同标签，等 merge 才被统一。想省算力还得在 `pick_targets` 里按 hash 去重
   （会改变打标样本口径，本轮没动）。
3. **"其他"仍是弱项**：金标里"其他"9 行有 6 行被判到具体主题——碎片行/非题目行
   被自信标成 数据库/算法/MongoDB。抽取侧仍在把目录行、章节导语当题，这是上游问题。
4. **安全类无专属 topic**：CSRF 8 份拷贝全归"计算机网络"，与"工程与质量"并存，
   词表该不该加"安全"或"Web安全"需要一次真实分布统计再决定，本轮不动。
5. 语料侧补 AI/前端题（让 24 个未用词表项有题可打）仍未做。

## 10 code review 后的修复（2026-11-24 晚）

review 结论是「收口不齐」不是过度设计，因此这一轮只做收口，不加新机制。

### 10.1 P1-1 停用词大小写归一

`labelspec.normalize_tags` 原先 `tag in stop` 精确比对，词表写 `Zookeeper/Memcached`、
模型写 `ZooKeeper/memcached` 就漏剔。改为停用词集合先转小写、比对用 `tag.lower()`。
存量用一次性脚本按同一口径重算（只剔维度词，不动同义与 cap）：**92 行、92 个词**
（ZooKeeper / memcached / rabbitmq / Elasticsearch / kafka / zookeeper / SpringMvc），
备份 `build/backup-2026-11-24-tagcase/kb-before-tagcase.db`。

### 10.2 P1-2 调用失败不再落终态

`run()` 原先任何异常都写 `answer_source='llm_error'`，而 `pick_targets` 只捞 `answer_source=''`，
一次 Ollama 掉线就把整批题永久判死。现在失败只记日志与计数，不写库；
`pick_targets`/`stats` 同时接受 `'llm_error'`，历史遗留行也能重入。

### 10.3 P1-3 同 hash 传播默认 fill-only

`_propagate_by_hash(conn, hashes, *, overwrite=False)`：默认只补空 topic（`topic_filled`）
与空 tags，不清洗已有非空值；`overwrite=True` 才按多数改（`topic_overwritten`）。
`merge(..., hash_consistency="fill")`，CLI 加 `--hash-consistency {fill,overwrite,off}`，
返回值带 `changed_qids[:20]` 供核对。拷贝 tags 前先跑一遍 `normalize_tags(stopwords=…)`。

### 10.4 G6b 双指标

门禁判 `topic_acc`（严格同主题），`topic_acc_family`（族谱等价）只作参考列，
矩阵另给 `topic_family` 标注；`sql_source` 按数据来源（staging / questions）切换，不再复用错文案。
