## 二、为什么这 41 篇一直没进库（根因）

`inventory.py` 的扩展名白名单是 `.pdf/.docx/.md/.txt`，**`.doc` 不在内**——所以 41 篇 `doc` 从来没有进过台账。这不是漏跑，是格式不支持：`.doc` 是 OLE 复合文档，`pymupdf`/`python-docx` 都读不了，必须经 Word 或 LibreOffice 转一次。

另一个根因是跳过目录：`inventory.py` 对 `面试题精华集`、`图解课件`、`简历模板` 一律 skip，把 `智力题.pdf` 和 `计算机组成.md` 一起误伤了。

本机现成条件：**Word COM 可用**（已实测 `New-Object -ComObject Word.Application` 成功），LibreOffice 未装。所以选 Word 批量另存，不引入新依赖。

## 三、具体做法：五步，全程可回滚

### 3.1 设计原则：不动源目录，补录走镜像暂存树

```
<CORPUS_ROOT>\
├─ 11-面经与真题\…             ← 源文件一个字节都不改
└─ 30-补录\                    ← 新建，只放转换产物，路径与源目录同构
   ├─ 11-面经与真题\11.3-专题总结包\高频面试题-笔记资料01-34\01、….docx
   ├─ 11-面经与真题\11.1-公司面经故事\大厂面经(11)\最新Java百度社招带答案面经.docx
   ├─ 12-综合题库\java面试综合整理版（大全）.docx
   └─ 09-算法与数据结构\面试题精华集\技术面试常见智力题.pdf   ← 直接拷贝
```

好处：源树只读不可变（v2 §6.1 的硬约束）；`30-补录` 随时可整目录删掉重来；`inventory.py` 只需加一条"`30-补录\<原路径>` 按 `<原路径>` 解析分类"的规则。

### 3.2 第 1 步：批量 `.doc` → `.docx`（Word COM）

用 `补录-doc转docx.ps1`（同目录，已写好）：

```powershell
pwsh -File .\补录-doc转docx.ps1 -WhatIf      # 先看清单，不落盘
pwsh -File .\补录-doc转docx.ps1              # 实际转换
```

脚本行为：

- 扫全树 `*.doc`，排除 `99-重复文件待删 / 20-题库MD / 21-面经数据库 / 30-补录 / 简历模板`；
- 逐个用 Word 只读打开 → `SaveAs2(目标, 16)` → 关闭，输出到 `30-补录` 同构路径；
- **幂等**：目标已存在且 >1 KB 就跳过；
- 单个失败不中断，记进 `21-面经数据库\build\补录日志.json`（rel / ok / 目标 / 错误）；
- 不改源文件；`-WhatIf` 只打印不执行。

实测估算：41 篇、多在 0.1–0.4 MB，每篇 1–2 秒，**约 1 分钟**。

### 3.3 第 2 步：`inventory.py` 认 `30-补录`（改 3 行）

```python
# inventory.py 里，walk 之前加一层路径归一：
if rel.startswith("30-补录" + os.sep):
    rel = rel[len("30-补录" + os.sep):]      # 分类仍按原目录解析
    origin = "补录"
```

同时把扩展名白名单加上 `.docx`（本来就有），并给 `面试题精华集` 的跳过规则加白名单：允许 `技术面试常见智力题.pdf`、`计算机组成.md` 通过。

### 3.4 第 3 步：台账覆盖表（解决"目录分类 ≠ 内容分类"）

39 篇高频面试题虽然在 `11.3-专题总结包` 下，内容是**题库**不是"面经故事"。加 `build\overrides.json`，让 L1 优先读它：

不需要 39 条手写：`补录-doc转docx.ps1 -EmitOverrides` 会按文件名关键词生成初稿（规则见下），再人工过一遍即可：

| synchronized / CAS / AQS / 线程池 / volatile / 内存模型 / 并发 / 阻塞队列 | `03-并发编程` |

### 3.6 第 5 步：判重前置（别把重复件请回来）

这 41 篇里有高重复风险的至少两篇：`java面试综合整理版（大全）.doc`（13.6 MB，12-综合题库 下已有多份"核心面试知识整理"，其中 `99-重复文件待删` 里就躺着 2 份 11 MB 的同名族）和 `最新Java百度社招带答案面经.doc`（11.1 里可能已有同源件）。

## 八、如果文档在别的目录、根本没有分类

### 8.1 先说现在的真实行为（会骗人）

`inventory.py` 的 `detect_topic()` 是三级：**文件名正则（30 条）→ 目录名映射 `TOPIC_BY_FOLDER` → 兜底"综合"**；而 `classify()` 对「非 `11-` / 非 `12-`」目录的件一律返回 `category="题库"`。

所以把一份文件丢进任意新目录（`13-新下载\`、`未分类\`、甚至语料根），它不会被标成"未分类"，而是**静默变成"题库 / 综合 / 面试题"**。

后果：`topic=综合` 从"真综合题库"退化成垃圾桶——当前 83 条 `topic=综合` 里已经混着这类件，统计和筛选都在失真。**这是必须修的第一件事，否则"未分类"根本不存在。**

### 8.2 目标：让"未分类"成为一个正式取值（三处最小改动）

都不动产物、不动文件位置，只改判定逻辑：

```python
# ① detect_topic 兜底不再返回"综合"
def detect_topic(title, folder):
    for pat, topic, sub in TOPIC_BY_TITLE:
        if re.search(pat, title):
            return topic, sub
    t = TOPIC_BY_FOLDER.get(folder)
    if t is None:
        return "未分类", ""
    return t, ""

# ② classify 对未知顶层目录给 category="未分类"
    if folder in TOPIC_BY_FOLDER:                    # 01~10 既有分类
        t, s = detect_topic(title, folder)
        return "题库", t, s, "面试题"
    t, s = detect_topic(title, folder)
    return "未分类", t, s, "待判"

# ③ 台账每条加 topic_source 字段
#    l1_folder | l1_title | override | none
```

第 ③ 条不是锦上添花：没有 `topic_source`，事后无法回答"这个 topic 是目录给的还是模型猜的"，也就没法做分类质量评估（v2 §5.1 的"公司 id 归一正确率 ≥95%"这类验收无从谈起）。

同时新增唯一入口目录：

```
<CORPUS_ROOT>\31-收件箱\
```

规则一句话：**任何来源不明、目录无意义的文档先扔这里**；`inventory` 把 `31-收件箱` 下所有件判 `category=未分类`，不参与"题库/综合"统计。

### 8.3 分类先于处理，但改分类仍不必重跑解析

统一口径：**先分类，再处理**——分类结果决定"值不值得解析、用哪套拆题策略、算几份来源"，所以必须在解析之前拿到（流水线见 §10.4）。

但它不妨碍"改分类不返工"，因为两者作用在不同层：

- **解析层**（md 产物）只由 `ext` 和解析器决定：pdf→pymupdf4llm、docx→python-docx、md→直接读。**与分类无关**；
- **分类层**（`source_documents` 的 `category/topic/collection`）只决定拆不拆题、怎么拆、权重多少。

所以分类判错的代价被锁在"元数据 + 拆题策略"，改分类只需重跑 S2 拆题，**不动 md、不重跑 OCR**。这是敢把分类前置的最坏损失边界。

`未分类` 是**合法终态而非错误**：照样进 convert、照样可检索（FTS 不看 topic），只标 `status=classified` + `topic_source=none`，筛选面板单列。这条必须保住——否则新增件会卡在人工分类，增量就永远跑不起来。

### 8.4 分类归因三档（成本从 0 到低）

| 档 | 方法 | 判据 | 覆盖率预期 |
|---|---|---|---|
| ① 规则 | 文件名 + 首 40 行跑 `TOPIC_BY_TITLE` 现有 30 条正则 | 命中即定 | 现有语料实测约 70%（标题带 MySQL/JVM/Spring 这类） |
| ② **近邻判类** | 新件 md 与已入库 397 篇算 embedding 相似度，取 top-20，按 topic 加权投票 | ≥70% 一致即定；40–70% 进待确认；<40% 保持未分类 | 吃掉 ① 剩余的大半 |
| ③ LLM 判类 | 强模型一次调用，输出受控词表内的 topic | JSON Schema 约束 | 只处理 ①② 都不确定的残渣 |

第 ② 档是这轮新加的建议，比 LLM 更划算：**已有 397 篇的 topic 是目录人工确认过的，用它们做"类比"比让模型从零判断更稳**；CPU 上跑 bge-small-zh，单篇毫秒级，全量 0 成本。

### 8.5 语料树之外的文件（Downloads、桌面、U 盘）

不要 `mklink` 软链（跨卷、权限、备份三处坑），用**复制进收件箱**：

```powershell
# 只拷贝，不动源文件；同目录内重名自动加时间戳再拷
Copy-Item -LiteralPath '<DOWNLOAD_DIR>\xxx.pdf' `
          -Destination '<CORPUS_ROOT>\31-收件箱\xxx.pdf'
```

之后与补录同一条链：`inventory.py` → `convert.py --category 未分类` → `gate.py`。

> 不建议给 `inventory` 加"多根目录"参数（`ROOTS=[面经整理ing, 其他目录\]`）：不同项目的文档混进同一台账，比多一步复制更麻烦。收件箱是唯一入口，边界才清楚。

### 8.6 拒收规则（别让合同、发票、学习路线图混进来）

未分类件最容易夹带非题库内容。`gate.py` 里加一道"题库特征分"，三条同时不满足即判 `category=非内容`（只留台账不进题库，报告单列）：

- 题目编号密度 ≥ 1 个/千字（`^\d+[、.）]`、`问：`、`Q:`）；
- 问号密度 ≥ 3 个/千字；
- 单篇有效字符 ≥ 800。

### 8.7 验收

| 项 | 标准 |
|---|---|
| `topic=综合` 回落 | 从 83 条回落到"真综合题库"（约 26 条在 `12-综合题库`，其余迁出） |
| 未分类可检索 | 未分类件在 FTS 检索里**查得到**，筛选面板单列"未分类" |
| 可追溯 | 每条台账有 `topic_source`，抽查 20 条能说清 topic 来源 |
| 后置分类不返工 | 补分类后 `20-题库MD` 文件时间戳不变（证明没重跑解析） |

## 九、有目录、但目录名不在 01–12 体系里怎么办

### 9.1 先看实测：目录名的价值不在 topic 上

- 444 条里 **313 条（70%）目录深度 ≥3**，而这些深层目录名当前**一个字节都没进台账**——`classify()` 里写的是 `folder = rel.split("\\")[0]`，只取第一层。
- 但如果把深层目录名直接当 topic 喂进去，收益极小：`topic=综合` 的 291 条里，能被深层目录名救回的**只有 2 条**（`计算机基础\算法刷题` 下的 `Leetcode-Go.pdf`、`Fucking-Algorithm.pdf`）。
- 反证很直白：深层目录名大多是**包装名**——`原创PDF面试手册`、`Markdown版`、`面向字节系列`、`这是Java面试题资料合集`——它们说明"这批资料从哪来"，不说明"讲的是哪个学科"。

**结论：别把目录名硬塞进 `topic`。**那会制造假分类，而且挡不住的一个事实是：`topic` 已经由 12 个顶层目录 + 文件名正则覆盖了 97%。

### 9.2 目录名真正的三个用途（按价值排序）

| 用途 | 取哪一级目录 | 实测例子（条目数） | 落到哪个字段 |
|---|---|---|---|
| **① 来源集 collection** | 最深一级、剔除包装词 | `面向字节系列`(35)、`这是Java面试题资料合集`(22)、`01-大厂面经汇总(22份)`(21)、`大厂真题`(18)、`Markdown版\大厂面经汇总`(17) | `collection` |
| **② 来源可信度 / 类别** | 结构位（11.1 / 11.2 / 11.3 / 01–10 / 12） | 11.1 公司面经故事=个人叙事；11.2 大厂真题=真题；11.3 专题总结包=课程/公众号合集 | `source_trust` + `category` |
| ③ 子主题 sub_topic | 二级目录名，仅当命中知识词典 | `计算机基础\操作系统`、`计算机基础\算法刷题` | `topic_candidate`（弱候选，不直接采信） |

### 9.3 为什么 collection 才是重点：见证数会被虚高几十倍

v2 §7 的排序式是 `见证数 × 来源可信度 × 时效系数`。没有 `collection` 时，`面向字节系列` 的 35 篇会被算成 **35 个独立来源**——同一门课把一道题讲 35 遍，见证数就虚高 35 倍，排序彻底失真。

规则与 §5.2 的 style 变体归族同源，只是粒度更粗：

> **同一 `collection` 下的多个 doc，在"见证数"里只计 1 个来源。**

这一条不需要模型，只需要把目录名记下来。

### 9.4 台账新增 4 个字段

```python
doc_meta:
  dir_path          # 完整相对目录（如 11-面经与真题\11.3-专题总结包\面向字节系列）
  collection        # 来源集名（剔除包装词后的最深一级）
  source_trust      # high | medium | low（由结构位与来源类型决定）
  topic_candidate   # 目录名命中知识词典时的建议值，不直接当 topic
```

`dir_path` 必须整条存——v1 那句"目录名/文件名就是元数据源，不能拍平"是对的，但**当前实现只留了第一层**，等于把 70% 的信息在入库那一刻就扔了。

### 9.5 目录规则从硬编码升级成词典

把 `TOPIC_BY_FOLDER`（现在是代码里的 dict）换成 `meta\folder_rules.yaml`，支持 glob 与"只填它认识的字段"：

```yaml
rules:
  - match: "11-面经与真题\\11.2-大厂真题*"
    category: 真题
    source_trust: high
    collection_from: last-seg

  - match: "11-面经与真题\\11.1-公司面经故事*"
    category: 面经
    source_trust: low          # 个人叙事，主观且不可复现
    collection_from: last-seg

  - match: "*\\Markdown版\\*"
    ignore_seg: Markdown版     # 包装词，不参与 collection 命名

  - match: "*\\原创PDF面试手册\\*"
    ignore_seg: 原创PDF面试手册

  - match: "01-Java基础"
    topic: Java基础           # 顶层主题目录，强映射
```

匹配顺序：**具体 → 泛**；一条规则只覆盖它写了字段，其余交给下一档规则或下一层推断。等价于给 `TOPIC_BY_FOLDER` 加了层级、通配和"来源"语义。

### 9.6 改后的判定链

```
topic:        文件名正则（30 条） → 深层目录命中知识词典 → 顶层主题目录 → 未分类
collection:   最深一级目录（剔除包装词） → 为空则用顶层目录名
source_trust: 结构位（11.1=low / 11.2=high / 11.3=low / 01–10=medium / 12=medium）
category:     结构位优先（11.1=面经 / 11.2=真题 / 11.3=专题笔记），其余按 9.4 规则
```

### 9.7 任意自建目录（例如 `13-某站下载\`、`<SOURCE_DIR>\`）

不判 topic，只记三件：

- `collection = 目录名`（保住"这批同源"的信息）；
- `category = 未分类`；
- `source_trust = low`（来源未知，默认低）。

之后靠 §8.4 第 ② 档**近邻判类**补 topic。这样既不丢信息，也不假装知道它是什么学科——**"不知道"要显式写出来，不能兜底成"综合"**。

### 9.8 验收

| 项 | 标准 |
|---|---|
| collection 覆盖率 | 100%（顶层直属的记为 `<顶层直属>`），不允许空值 |
| collection 正确性 | 抽 10 个，每个 encompass 的 doc 数与人眼判断一致 |
| 见证数回落 | 用 collection 重算，抽 5 道高频题：见证数应显著下降（预计从 30+ 降到个位数） |
| dir_path 完整率 | 444 条 100% 有完整目录路径，不再只有第一层 |

## 十、只两个时点：开工前一次补齐 / 上线后持续新增

### 10.1 明确不做中间阶段的增量

中间态（S1 解析到 S5 上线之间）最多几周，为它单独维护一套分支逻辑，收益小于状态碎片的维护成本。所以只保留两个时点：

| 时点 | 场景 | 处理方式 | 代价 |
|---|---|---|---|
| **① 现在** | `build_db` 尚未跑过、`questions.json` 不存在，项目处于 S0/S1 | 全量 intake → 分类 → 处理，**一次跑完** | 无增量逻辑，零返工 |
| **② 上线后** | 库已在跑，持续有新资料进来 | 只认"新 hash"的增量链 | 单件 2–4 分钟 |

中间几天零散进来的资料：先丢 `31-收件箱` 攒批，不单独设计分支。批量 ≥50 件时直接全量重跑，比增量更省心。

### 10.2 新增"原文档表"：唯一事实源

`registry.json` 从"事实源"降级为"一次扫描的快照"，真正的账本是这张表——它记录**历史上见过的每一个文件**，删除文件也不删行。

```sql
CREATE TABLE source_documents (
  doc_hash      TEXT PRIMARY KEY,        -- sha256(文件字节) 前 16 位
  sha256        TEXT NOT NULL,           -- 完整 64 位，审计用
  file_name     TEXT NOT NULL,           -- 源文件名（原名，含扩展名）
  ext           TEXT NOT NULL,
  size_bytes    INTEGER NOT NULL,
  src_path      TEXT NOT NULL,           -- 首次发现时的绝对路径
  dir_path      TEXT,                    -- 当前相对语料树路径（移动则更新）
  collection    TEXT,                    -- 来源集，见 §9.2
  status        TEXT NOT NULL,           -- 状态机见 10.4
  category      TEXT,
  topic         TEXT,
  sub_topic     TEXT,
  topic_source  TEXT,                    -- l1_folder|l1_title|override|neighbor|llm|none
  classifier    TEXT,                    -- rule|neighbor|llm|manual
  classified_at TEXT,
  gate_result   TEXT,                    -- pass|low_cjk|garbled|non_content
  family_id     TEXT,                    -- 内容指纹判出的同源族，见 10.3
  batch_id      TEXT NOT NULL,
  first_seen_at TEXT NOT NULL,
  last_seen_at  TEXT NOT NULL,
  note          TEXT
);
CREATE INDEX idx_sd_status ON source_documents(status);
CREATE INDEX idx_sd_coll   ON source_documents(collection);
CREATE INDEX idx_sd_topic  ON source_documents(topic);
CREATE INDEX idx_sd_name   ON source_documents(file_name);
```

要点：

- `doc_hash` 直接当主键，判重是一次索引查找，不是全表比对；
- `file_name` 必须保留**源文件名**——用户在资源管理器里认的是名字，不是 hash，出了问题要能对回去；
- 分类结果就存在这张表里，**文件记录与分类记录不拆两张表**，避免"文件有了、分类丢了"的半状态；
- 删除只改 `status`（`absent` / `superseded`），行永远在 —— 所以"上个月删掉的文件又被下载回来"能被立刻认出来。

### 10.3 判重：hash 是主路径，但内容指纹才是主力

**实测数字**（这轮真跑过）：

| 项 | 结果 |
|---|---|
| 全量 444 件 sha256 | **2.93 秒**（2,523 MB，860 MB/s，单件 6.6 ms） |
| 444 条内部字节级重复 | **0 组** |
| `99-重复文件待删` 的 138 件 vs 库内 444 条 | 字节级完全相同**只有 1 件**（`设计模式面试专题.md`） |

结论很硬：**hash 判重成本趋近于零（3 秒扫完整个库），所以不需要任何"快速判重"的优化设计**；但 hash 只能抓"同一文件被收了两遍"，抓不到"改名/重新导出"——138 个被人工判为重复的文件里，hash 只认出 1 个（0.7%）。

所以判重分两级，各管一件事：

| 级别 | 手段 | 抓什么 | 成本 | 何时跑 |
|---|---|---|---|---|
| **一级（主键）** | `sha256(文件字节)[:16]` | 同一文件重复拷贝、重复下载 | 6.6 ms/件 | 每次 intake，必跑 |
| **二级（同源）** | pdf 像素指纹（dpi=72 `md5(pix.samples)`）、md/文档字符指纹（归一后 simhash 或 5-gram Jaccard ≥0.9） | 改名、重新导出、格式转换 | 0.2–1 s/件 | 仅 hash 未命中且"疑似"时跑：同名、size 差 <20%、或标题高度相似 |

二级命中不合并文件，只写 `family_id`（同一族、不同 hash），供 §9.3 的"来源计数去重"与 §10.5 的见证数使用。

hash 命中时的三种落地：

| 情况 | 判据 | 处理 |
|---|---|---|
| 同一路径重复扫描 | `dir_path` + `file_name` 都相同 | `duplicate`，只刷 `last_seen_at` |
| 换位置/改名 | `doc_hash` 同、路径不同 | `moved`/`renamed`，只更新 `dir_path`/`file_name`，**不重处理** |
| 曾被删除又回来 | 表里该 hash `status=absent` | 复用原有解析与分类结果，状态改回 `processed` |

### 10.4 统一"先分类再处理"：五状态流水线

> **口径提示（2026-11-19 更新）**：本节原先只是设计意图，`processing/processed` 两态无工具写入；
> **Q-3 拍板后已落地**：`extract` 开始时写 `processing`，成功后写 `processed` 并记 `document_products`
> （`kb/products.py`、015 迁移），失败留 `processing` 作为断点；增量接入用 `extract --incremental`。
> 状态机现状仍以 `docs/19-功能流程图.md` 为准，阶段划分见 `docs/28`。

```
intake.py          算 hash → 查表 → 未命中则插入 status=pending_classify
      ↓
classify.py        规则（文件名/目录/collection）→ 近邻判类 → LLM 残渣
                   → 写 category/topic/topic_source/classifier/classified_at，status=classified
      ↓  （只有 classified 才允许往下走）
convert.py + gate  解析 + 门禁；gate 判非内容 → status=rejected
      ↓
parse_banks/extract  按 category 选拆题策略
      ↓
build_db           写 documents/questions/canonical + FTS5 + 向量
```

状态机（`status` 的全部取值，不允许出现表外的值）：

| status | 含义 | 后续 |
|---|---|---|
| `pending_classify` | 新件，等分类 | 只能进 classify |
| `classified` | 分类完成（含"未分类"） | 内容池入口，可进 convert / extract |
| `processing` | 处理中（extract 开始即写） | 崩溃后断点续跑依据；成功转 `processed` |
| `processed` | 已出产物并完成抽题（0 题的件也算） | 终态；`extract --incremental` 默认跳过 |
| `rejected` | 非内容（如简历模板、学习路线图） | 终态，只留台账 |
| `failed` | 转换/门禁失败（预留言） | 当前实现把失败留在 `processing`，由下次增量重试 |
| `duplicate` / `moved` / `absent` / `superseded` | 旁支终态 | 不参与处理 |

**为什么顺序不能颠倒**（三条理由都带数字）：

1. **省算力**：88 个未登记文件里有 45 个本就不该解析（简历模板 8、课件图 26、xmind 9、xlsx/zip 2）——先分类能直接 `rejected`，不浪费一次转换；
2. **定策略**：`category` 决定拆题路径——`题库`→`parse_banks` 拆题、`面经`→`extract` 抽题并归公司/年份、`专题笔记`→只建索引不拆题；
3. **定权重**：`collection` + `source_trust` 决定见证数与排序（§9.3），必须在入库前算好，否则排序公式拿到的"来源数"是假的。

**防矛盾条款**：分类与解析器**解耦**——解析器只由 `ext` 决定，分类不参与选解析器。所以最坏情况是"元数据错、拆题策略错"，md 产物仍然是对的，改分类只需重跑 S2。这条保证"先分类"不会演变成"分类错就全废"。
