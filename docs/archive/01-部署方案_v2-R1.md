## 0. 一句话结论

架构判断（本地优先 / 单文件 SQLite / 同题聚合返回多答案）全部保留；但有三处必须改，否则第一阶段就会走偏：

1. **解析阶段已经完成 96.6%**（423/438），不需要再引入 Docling 作为主解析器，它降级为"失败件二线工具"；
2. **v1 的"无文本层才 OCR"判据在真实语料上不成立**——15 篇失败件全部**有**文本层，只是字体编码损坏，必须换成"文本质量门禁"；而且已转换成功的文件里还有 **11 篇是"假成功"**（占已转内容 10.6%、合计 2,537 页）；

修正后 P0 从 v1 的 2–3 天压到 **0.5–1 天**，全量阶段从 13–19 天压到 **8–12 天**。

## 3. 修正一：解析层——保住已经跑通的 96.6%

### 3.1 选型结论：pymupdf4llm 留主路，Docling 降为二线

| 方案 | 状态 | 决定 |
|---|---|---|
| pymupdf4llm + 子进程隔离 + pypdf 兜底 | 已产出 397 md、2,408 万字符、17,584 图 | **保留为主解析器** |
| Docling | 未安装；依赖 torch 级组件（~5 GB） | **降为二线**：只对"主路失败且非编码损坏"的少量文件单独调用，不进主流水线 |

理由是收益/成本不划算：主路覆盖 96.6%，Docling 带来的版面还原增量集中在那 15 篇里，而其中 10 篇本身就是编码损坏（OCR 才是正解），只剩 5 篇以内可能受益。为一个位数的文件引入 5 GB 依赖和一条新失败路径，不符合"先跑通再优化"。

**保留 v1 的正确判断**：Docling 的版面还原确实更好——所以它不是被删掉，而是被放到 `mianjing_kb\\docling_one.py`（新增，按单文件调用），供将来想做表格结构化时用。

### 3.2 质量门禁（替代"有无文本层"）——本版最重要的一条

新增 `mianjing_kb\\gate.py`，对**每一份已转换产物**（含 `ok=true` 的）计算三指标，不通过即判 `ocr_needed`：

| 指标 | 定义 | 门槛 | 实测依据 |
|---|---|---|---|
| CJK 比例 | CJK 字符 / 总字符 | **≥ 0.15** | 正常件 p10=0.276、p50=0.478；11 篇假成功全部 ≤0.143 |
| 乱码字符率 | (U+FFFD + 私用区 + 拉丁扩展混排) / 总字符 | **< 1%** | 损坏件呈现 `ړ ଓ ୗ ᭗ ᶎ` 这类非中文码位 |
| 有效字符率 | 可打印 + 中文标点 / 总字符 | **≥ 0.90** | 排除大量控制字符与残码 |

设计约束：

- 门禁结果写 `convert_log[].gate = pass|fail(reason)`，**不覆盖原 `ok` 字段**——保留"转换成功但内容不可信"这一事实，便于回溯；
- 门禁先在一份已知答案的样本上校准：用 §2.1 的 11 篇（应全部 fail）+ 5 篇健康件（应全部 pass）跑一遍，0 误伤才允许上线；
- 门禁同时承担对账职责：逐条核对 registry → convert_log → 产物文件三者一致，把 §2 里 **ok=423 vs 产物 397 差 26** 的缺口查清并落到报告里。

### 3.3 门禁失败后的处置顺序——**判重先于 OCR**

这是 R1 补的关键规则，缺了它 P0 当天就会做 791 页重复劳动。门禁判 fail 之后**不允许直接推 OCR**，必须按下面顺序处置：

```
gate fail
 ├─ ① 查同族健康版（§5.2 D1–D3）
 │    ├─ 有 → 判 superseded，写 doc_family，免 OCR   ← JavaGuide v1.0/1.1/v2.0（791 页）
 │    └─ 无 → ②
 ├─ ② 判内容类型
 │    ├─ 代码/图为主 → 只取文字段（Leetcode-Go 1,382 页，单列策略）
 │    └─ 文字为主 → ③
 └─ ③ 进 ocr_needed，与转换失败件同一条队列（364 页）
```

落库要求：`convert_log[].disposition ∈ {ocr | superseded | partial_ocr | skip}`。没有这个字段，事后无法解释"为什么这篇没证据"。`superseded` 必须记录指向的替代 `doc_id`，否则"跳过"就变成静默丢数据。

## 4. 修正二：OCR 层——本地已有，云预算归零

| 项 | 实测 |
|---|---|
| 引擎 | `<OCR_ENGINE_DIR>\PaddleOCR-json.exe`（v1.4.1） |
| 协议 | stdin 每行一个 `{"image_path": ...}`，stdout 回一行 JSON，`code:100` 为成功 |
| 初始化 | 0.76 s，必须等到 stdout 出现 `OCR init completed.` 才发第一条 |
| 速度 | 0.72 / 0.80 秒/页（200 dpi，常驻进程） |
| 质量 | score 0.80–1.00，多数 0.92+，CJK 占比 0.839 / 0.853，无缺字 |
| 备选 | `Umi-OCR_Rapid_v2.1.4`、`v2.15\Umi-OCR_Paddle_v2.1.5` |

工程约束（三条硬要求，全部来自实测踩坑）：

1. **cwd 必须是引擎目录**——模型路径是相对的 `models/ch_PP-OCRv3_*`，换目录即 init 失败；
2. **页面图落 ASCII 临时路径**（如 `%TEMP%\ocr_probe\pN.png`），中文路径直接喂引擎会失败；
3. **丢文本层**：OCR 产出的 md **只用 OCR 文本**，原文本层一律丢弃——否则 `5.2̵ ړ...` 这类乱码会一起进库，污染拆题与检索。

断点与兜底：每篇 OCR 完立刻追加 `build\ocr_log.json`（字段：rel / pages / ok_pages / fail_pages / mean_score / elapsed），单页失败重试 ≤2 次，仍失败记 `ocr_manual` 不阻塞整批。

代码页类文件的处理：`LeetCode题解（java语言实现）`、`算法刷题题解答案LeetCode中文版` 两篇共 443 页以代码为主，OCR 会把代码变噪音。策略是**文字说明转文本、代码块保留原位图**（页面图本来就会存进 `20-题库MD` 的图目录），不强行转全部文字。

## 5. 修正三：元数据与去重——贴合真实目录

### 5.1 元数据四级链改写（含 sub_topic 的坏消息）

先纠正一个数据事实：`registry.json` 里 `category=题库` 共 **210 条**，其中 **`sub_topic` 为空的 209 条**（只有 1 条填了"类加载"）。也就是说 **L1 目前只能稳定供出 `topic + category` 两级**，`sub_topic` 几乎是空的。"`topic=综合` 有 83 条"是另一个口径，不要混用；其中落在 `12-综合题库` 的合集属正常，真正需要抽查的是 **`01`–`10` 目录里 57 条无 sub_topic 的题库**。

| 级别 | 来源 | 抽取内容 | 置信度 |
|---|---|---|---|
| L1 目录 | `01-Java基础`…`12-综合题库` 及二级目录 | `topic` / `category`（`sub_topic` 目前覆盖率仅 0.5%，不能指望） | 高（`folder→topic` 零错配） |
| L2 文件名 | 文件名主干 | 公司 / 岗位 / 轮次 / 年份（主要命中 `11.x` 目录）+ **补 sub_topic** | 高 |
| L3 正文头部 | 前 40 行 | 公司/岗位/面试时间/轮次（面经常自述） | 中 |
| L4 LLM 补抽 | 前 60 行送模型 | 只补前三层缺失字段（含 sub_topic 大头） | 中 |
| 兜底 | — | 写 `unknown` 进"元数据待确认"队列，不阻塞入库 | — |

**保留 v1 的两个正确设计**：
- `year_archived`（来自路径，整理时间）与 `year_interview`（来自正文/文件名的面试时间）双字段，**时效判定只用后者的**；缺失按"归档年 −1"估计并标 `year_inferred=true`；
- 公司/岗位归一词典（`companies.yaml` / `positions.yaml`）——当前语料里公司信息少，词典先建骨架，随入库长。

### 5.2 去重：从两级扩到三级（v1 只有 sha256 + SimHash）

| 级 | 方法 | 抓到了什么（实测） |
|---|---|---|
| D1 完全相同 | sha256 | 同文件复制 |
| D2 **像素指纹** | 每份 PDF 抽 4 页渲染 dpi=72，`md5(pix.samples)` 拼接 | **抓住了"改名同件"**：`Java面试知识点整理手册.pdf` = `350道`（127 页版），4 页指纹完全一致 |
| D3 近似版本 | 字符级 SimHash / 汉明距离 ≤3 | 夜间模式 / 亮白风格 / v1.0→v2.0 版本族 |

实测样本（写进 `doc_family` 表做回归用例）：

| 家族 | 成员 | 判定 |
|---|---|---|
| JavaGuide | v1.0(238p) / V1.1(252p) / v2.0(301p) / 5.0 / 5.0暗黑 / v3.0(md) | 5.0 与 v3.0 是可用版本；前三版判 `superseded` 且内容不可信（CJK 0.05x） |
| 图解操作系统 | 图片版(306p/69MB) / 亮白(文字层) / 暗黑(文字层) | 亮白+暗黑为**同一内容的 style 变体**，不重复计答案；图片版判 `superseded` |
| 350道 | **127 页（`12-综合题库` 根目录，与"Java面试知识点整理手册"像素同源）** / **128 页（`JAVA常见面试题库\` 子目录，内容不同）** | 两版不同；OCR 主清单暂取 127 页版，保留哪版待 §10 #1 |

**展示层规则**：`style` 变体（夜间/暗黑/亮白）归入同一 `doc_id` 的 `variants`，不参与"见证数"计数——否则一份资料会被算成 3 个独立来源。

## 7. 修正五：检索与"一题多答案"

**保留 v1 的核心洞察**（这是方案里最有价值的一条）：最后一跳必须**按 `canonical_question` 聚合**，返回一条题目 + `answer_variants[]`，而不是直接吐 top-k 块——否则同题重复会占满名额、把另一种正确答法挤出去。

落地顺序（不要一次上齐）：

| 步 | 检索层 | 依赖 | 何时 |
|---|---|---|---|
| ① | FTS5 `tokenize='trigram'`（免分词，中文子串直接命中） | 无（SQLite 内建） | P1，立刻可用 |
| ② | `sqlite-vec` 向量召回 | embedding 服务 | P3 |
| ③ | bge-reranker 精排 top-20 | 模型 | P3 |
| ④ | RRF(k=60) 融合 ①② | — | P3 |

**分词取舍**：v1 用 jieba 预分词，现网 `build_db.py` 已用 `trigram`。先选 **trigram**——零依赖、中文短查询（"HashMap 扩容"、"索引失效"）子串命中好，不需要维护词典。但它是**待验证方案，不是定论**，P1 必须实测两项：

- **索引体积**：trigram 索引约等于原文 3 倍，2,408 万字符语料预计 6–8 GB，须实测确认 D 盘水位；
- **短查询表现**：2 字以下查询（"GC"、"IO"）trigram 噪音大，达不到验收线就换 jieba 预分词或双索引并存。

向量层上线后，长句查询的词语召回由向量补足，这是不急着上 jieba 的主要理由。

时效排序系数沿用 v1：`排序 = 见证数 × 来源可信度 × 时效系数`，其中时效只看 `year_interview`。

## 8. 修正六：推理栈——8 GB 显存要重算，按四档推进

v1 的算式是"chat 6.0 GB + bge-m3 1.6 GB ≈ 7.6 GB，正好吃满 8 GB"，同时要求 `-np 4` 与 `-c 8192`。**这个组合在 8 GB 上大概率 OOM**：KV cache 按 q8 量化、8K 上下文、4 并发槽位，实际额外占用 1–2 GB，叠加后必然超。改为：

| 档 | 组成 | 显存/资源 | 用途 | 现状 |
|---|---|---|---|---|
| 档 0 | CPU embedding（bge-small-zh ONNX，`onnxruntime` 已装）+ 云端 API 做抽取 | 0 显存 | 抽取抽检、P0/P1 冒烟 | **今天可用** |
| 档 1 | PaddleOCR-json（CPU） | 0 显存 | 全部 OCR | **已实测** |
| 档 2 | llama.cpp Vulkan + Qwen3-8B Q4_K_M，`-np 2`、`-c 4096`、KV q8 | ~5.5–6.5 GB | 本地批量抽取 | **未安装、未验证，0.5 天验证** |
| 档 3 | rerank / VLM（Qwen2.5-VL-7B） | 用时起、跑完退 | 精排与图 caption | P3 按需 |

关键改动：

- **`-np 4` → `-np 2`**，`-c 8192` → `-c 4096`（题目级 chunk 用不到 8K）；
- **bge-m3 不常驻**：8 GB 上让 embedding 走 CPU（bge-small-zh，1 万题量级完全够速），bge-m3 只在需要 1024 维质量时临时起；
- 驱动/Vulkan 这条风险不变（v1 的判断正确），但**必须先验证再排工期**：本机没有 `llama-server`，Vulkan 路径一天都没跑过。
