## 0. 一句话结论

R1 的九处判断里，有 **七处仍然成立**（pymupdf4llm 主路、质量门禁替代文本层、本地 OCR 零预算、L1 只供 topic+category、
6 步流水线、一题多答案聚合、8 GB 显存降档）。必须改的是 **三处**：

1. **判重必须加第四级：题级**。合并轮已把 110 个源文档级重复清零，剩下的重复全在"同题多版本"和"跨格式 pdf↔md"，
   `cluster`（0.92 吸附 / 0.85 灰区）从 P2 的可选项变成 P1 的必做项。
2. **合并版（23 份）必须从 PDF 书签恢复源边界**。合并版 md 里 0 个一级标题、源文件名无痕迹（JVM 合集 148,964 字 / 534 个 `######`），
   110 个源的"见证数 × 来源可信度"只存在于 PDF TOC 的 L1 书签。**这是物理删除 99 区的前置 gate**。
3. **阶段重排**：工具链已建成（intake/classify/gate/ocr_pages/ingest_queue/pipeline + kb 包），
   P0 不再是"从零建流水线"，而是"补 4 个缺口"——书签映射、`ok=423 vs md=391` 的 32 条对账、门禁全量校准、OCR 实跑。

## 5. 元数据与源边界（R2 最重要的一节）

### 5.1 四级链不变，新增"合并版继承"

| 级别 | 来源 | 抽取内容 | 置信度 |
|---|---|---|---|
| L1 | 目录 | `topic` / `category`（`topic_rules.yaml` 已落，475 条零未分类） | 高 |
| L2 | 文件名 | 公司 / 岗位 / 轮次 / 年份；补 `sub_topic` | 高 |
| L3 | 正文前 40 行 | 面试时间、轮次 | 中 |
| L4 | LLM 补抽 | 只补前三层缺失（含 `sub_topic`） | 中 |
| **L1'（新）** | **PDF TOC 的 L1 书签** | 合并版的 `source_count` + `sources_json`（源文件名 + 页区间） | **高**（书签就是源文件名） |

### 5.2 书签→源映射（删除 99 区的硬 gate）

`intake.py` 对每个 `.pdf` 读 `doc.get_toc()`，取 L1 书签作为源边界：

```sql
ALTER TABLE source_documents ADD COLUMN source_count INTEGER;   -- L1 书签条数，非合并版为 1
ALTER TABLE source_documents ADD COLUMN sources_json TEXT;      -- [{"name":"51道.pdf","page_start":1,"page_end":23}, ...]
```

已全量核过 23 份合并版（2026-11-17 实测）：

- **23/23 都有 L1 书签，L1 合计 110 条 = 110 个源，逐一对齐**（分布：Java基础 6、并发 8、JVM 11、MySQL 9、Redis 10、Dubbo 7、Spring 5、RabbitMQ 5、MyBatis 5、设计模式 5，其余 2–4）；
- L1 数量与书签总数不同（如 Java基础 508 条书签 / 6 个 L1、SpringCloud 72 条 / 2 个 L1）——**多出来的层级正是子标题**，可用于段内切题。

**落库判据（实现时踩到的坑）**：源边界只认"**L1 标题形如文件名**"（`.pdf/.docx/...` 结尾），
不能把"L1 条数"一律当源数——普通 PDF 的 L1 是章节标题，按条数算会把 291 份 PDF 误判成
119 份合并版 / 3,338 个源（干跑实测）。无源级书签的按单源处理并写 `from: fallback_no_source_toc`。

已核的两个样本（作为回归用例）：

| 合并版 | L1 书签（源） | 页区间 | 校验 |
|---|---|---|---|
| JVM 合集 | 11 条（`Java虚拟机（JVM）面试题 51道` / `JVM大厂面试题（含答案）` / … / `JVM面试突击第一季`） | p1 / 24 / 57 / 81 / 96 / 106 / 135 / 145 / 155 / 175 / 195 | 214 页 = 11 源之和 ✓ |
| Mongo 合集 | 4 条（`MongoDB篇` / `MongoDB面试题` / `第二版：MongoDB 24 道` / `MongDB篇(带答案)`） | p1 / 7 / 11 / 18 | 23 = 6+4+7+6 ✓（第 4 源 `第二版：MongoDB 24 道.pdf` 现在 99/07） |

**为什么是硬 gate**：110 个源文件一旦从 99 区物理删除，`合并版 → 源文件名 → 页区间` 的对应关系再无处可查；
`见证数 × 来源可信度` 是 R1 §7 的核心排序因子，丢了它，23 份合并版退化为"1 个来源"。

### 5.3 题级切分：按书签段，不按标题

`cluster.py` 拆题时以 `sources_json` 的页区间为一级边界，段内再按 `######` 小标题切块。
每题记录 `source_span`（属于哪个源、哪几页），这是"一题多答案"能并排展示的前提。

## 6. 判重：从三级扩到四级（R2 的结构性改动）

| 级 | 方法 | 已实证抓到了什么 | 何时跑 |
|---|---|---|---|
| **D1** 完全相同 | sha256（`kb.hashing`） | 同文件复制；隔离区副本 | 已在 `intake.py` |
| **D2** 像素指纹 | 抽 4 页 dpi=72，`md5(pix.samples)` | 改名同件：`Java面试知识点整理手册` = `350道`(127p)，4 页指纹全同 | P1 补 `fingerprint.py` |
| **D3** 字符级 SimHash | 汉明距离 ≤3；**必须覆盖 pdf↔md** | 夜间/亮白/暗黑风格变体；**跨格式 2 对**：`memcached面试专题`（md@12 vs pdf@99）、`ActiveMQ消息中间件` 两对 | P1 补（部分已由人工完成，需机器化） |
| **D4** 题级聚类 | 归一化题干 embedding，**0.92 吸附 / 0.85 灰区** | 合并轮把文档级重复清零后，剩下的重复全部是"同题多版本" | **P1 必做**，表已建、算法未写 |

处置矩阵（写进 `dispatch.py`，与 R1 §3.3 一致并扩级）：

```
新文件 → D1 命中 ? superseded/hash_dup
        → D2 命中 ? 判改名同件（保留信息量大的一份）
        → D3 命中 ? doc_family 归族，style 变体不计数
        → 过门禁 → D4（按题）→ 高置信合并 / 灰区人工
```

**D3 的跨格式要求是合并轮用实例换来的教训**：本轮 6 件过时件里 2 件是"pdf 已隔离、md 还在清单"，D1 完全看不见。

## 8. 检索与排序：见证数改"题级"

R1 的聚合设计原样保留（按 `canonical_question` 返回一题多答案，不直接吐 top-k 块）。排序公式修正为：

```
score = Σ(每题见证: w_span × w_trust × w_time)
w_span  = 该题出现在几个不同源（书签段），不是几份 md
w_trust = 源可信度（合并版按段继承源书名，不整体继承）
w_time  = 只取 year_interview，缺失按归档年 −1 并标 inferred
```

展示层规则沿用 D-13：style 变体（暗黑/亮白/夜间）归 `variants`，**不计见证数**；同一源被合并进合并版，**只算 1 个见证**。

FTS5 `trigram` 仍是待验证方案（R1 §7 的两项实测：索引体积 ≤8 GB、2 字短查询 Recall）——合并版让字符量口径从"391 md"变成"391 md + 1,927 页合并版"，索引体积必须在 P1 重测。
