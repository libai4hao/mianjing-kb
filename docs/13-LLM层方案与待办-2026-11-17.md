## 2. 分层设计（三层解耦）

```
┌─ KB 核心层（不变）──  extract / classify / build_db / embed  →  面经库.db
│                                                        └─ rag_contexts() 出 context
├─ LLM 接入层（新增）──  llm_client.py：base_url + model + timeout + /no_think + JSON helper
└─ 运行时层 ──  Ollama serve（桌面 GPU 主 / 笔记本本地兜底）     ← OpenAI 兼容 /v1
```

原则：

1. **KB 核心不感知模型**：只产 `contexts` 与收 `str/JSON`，换模型只改环境变量
2. **接入层唯一入口**：所有调用走 `mianjing_kb/llm_client.py`，禁止散落 urllib
3. **运行时按需下沉**：桌面 GPU 是主算力，笔记本只承担「读库 + 轻问答」

## 3. 模型矩阵（按任务 × 设备）

| 场景 | 桌面 | 笔记本 | 依据 |
|---|---|---|---|
| 交互式 RAG 问答（T1） | **Qwen3-4B Q4_K_M**（9.2s/题，76 tok/s） | 若桌面不可达：Qwen3-1.7B Q4（预估 25-35 tok/s，待 L0 实测） | docs/12 §3 |
| 结构化抽取（T2 批量） | 4B（3.2s/题）或 8B（11s/题，质量略高 qtype 0.65 vs 0.55） | 不做（算力不足，交桌面批跑） | 同上 |
| 夜间全库打标 13,296 题 | 4B：约 11h；8B：约 40h | ✗ | 3.2s/题 ×13296 |
| Embedding | bge-small-zh（ONNX CPU，已有） | 不需要（库在桌面） | P3-② |
| 重排（可选） | bge-reranker-base ONNX（CPU 可跑） | 同桌面 | 待 K10 评估 |

不采用：GLM-4-9B（9B Q4 ≈5.6GB，桌面必落 PCIe 陷阱）；任何 >4.5GB 权重块的模型（桌面红线见 §6）。

## 4. 部署拓扑

```
台式机（LLM Server）                      笔记本（Client）
 ollama serve                               llm_client.py
 127.0.0.1:11434  ←本地工具                 └─ base_url = http://<Tailscale IP>:11434/v1
 0.0.0.0:11434    ←仅 Tailscale 内网可达       （桌面不可达 → 本地 qwen3-1.7b）
 模型: qwen3-4b(主) / qwen3-8b(批) / qwen3-1.7b(备用副本?)
```

- 传输：用户已有 Tailscale 组网，直接复用；**不用公网端口**
- 桌面 `OLLAMA_HOST=0.0.0.0:11434` + 防火墙入站仅允许 Tailscale 网段（100.64.0.0/10）
- Ollama 无鉴权 → 安全边界只靠「Tailscale + 防火墙」两层（见 §9）
- 模型文件：桌面 `<LLM_ROOT>\ollama_models`（用户级环境变量已设）；笔记本同款目录约定

## 5. 接口契约（llm_client.py 固化）

| 项 | 约定 | 理由 |
|---|---|---|
| Endpoint | `http://127.0.0.1:11434/v1/chat/completions`（可被 `LLM_BASE` 覆盖） | OpenAI 兼容，换 vLLM/云 API 零改动 |
| Thinking | Qwen3 一律追加 `/no_think` | 思考链吃 token + 污染 JSON（docs/12 §4） |
| `num_ctx` | 交互 4096；批量 8192（仅 4B/8B 批处理） | 控制 KV 显存；桌面 4B@8192 已验证 76 tok/s |
| temperature | QA 0.2；抽取 0.1；解析失败重试用 0 | 抽取稳定性 |
| timeout | T2 15s；T1 60s（4B）；批量 300s | 实测 9.2s/3.2s 留 6 倍余量 |
| `keep_alive` | 服务端 `OLLAMA_KEEP_ALIVE=2h` | 避免冷加载超时竞态（docs/12 §4） |
| JSON 任务 | prompt 写「从 A/B/C 中选恰好一个」，禁止写枚举字面量 | 小模型会原样抄占位符（docs/12 §4） |
| 重试 | 连接失败重试 2 次（指数退避 2s/8s）；JSON 解析失败重答 1 次 | 批处理断点容错 |
| 输出校验 | T2 必须过 `{"qtype": ∈枚举, "difficulty": 1-5, "tags": [...]}` schema | 入库前拦截 |

实现状态（2026-11-19）：`num_ctx` 已实现——环境变量 `LLM_NUM_CTX`（正整数，缺省不透传），`chat()` 把它写进 `options.num_ctx`；`keep_alive` 保持服务端部署项（`OLLAMA_KEEP_ALIVE`），客户端不实现。

## 6. 显存红线（本机最重要的一条运维规则）

> **模型(KV+权重) ≤ 显存 × 45%**

- 桌面 8GB → ≤3.6GB：4B（3.61GB@8192ctx）刚好压线 ✓；8B（4.7-5.6GB）✗
- 笔记本 4GB → ≤1.8GB：1.7B（~1.1GB）✓；4B ✗
- 换模型/换 quant 前先查 `/api/ps` 的 `size`，超红线直接否决，不要再做「压 ctx 抢救」的无用功（4096/2048 实测无改善）

## 7. 运维（桌面为服务机）

| 项 | 做法 |
|---|---|
| 启动 | `mianjing_kb/llm_serve.ps1`：设 4 个环境变量（MODELS/KEEP_ALIVE/HOST/DEBUG）→ 健康检查 `/api/tags` → 预热一次 |
| 自启 | 计划任务（登录触发，`-WindowStyle Hidden`），失败重试 3 次 |
| 日志 | `<LLM_ROOT>\logs\serve_YYYYMMDD.log`，保留 7 天 |
| 健康 | `llm_client.health()`：`/api/tags` + 目标模型存在 + 一次 1 token 试调 |
| 磁盘 | C 盘留 ≥20GB（曾因 2.4GB blob 写满全盘瘫痪，`OLLAMA_MODELS` 已迁 D） |
| 升级 | 模型/服务升级前先跑 `llm_smoke --tasks t2 --n 5` 做 5 题回归 |

## 8. 降级阶梯

1. 桌面 GPU（4B）→ 2. 桌面 CPU（4B≈10 tok/s 预估）→ 3. 笔记本本地 1.7B → 4. **纯检索模式**（`search.py` 不给 LLM 直接返回 top-k，`--format rag` 已支持）
批处理任务只认 1/2，不允许跑到 3。

## 9. 安全

- Ollama 无鉴权 + 无 TLS：仅 Tailscale 内网 + 防火墙网段白名单，**禁止**端口映射到公网
- 笔记本侧不落 `OLLAMA_MODELS` 大文件到 C 盘（用 E 盘 86GB 或 D 盘约定）
- 库文件（面经库.db 261MB）只桌面持有；笔记本只读远端 API，不复制库
