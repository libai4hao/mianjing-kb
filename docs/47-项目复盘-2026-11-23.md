## 1 结论先说

1. **整体不是过度设计，但有三处确实过度**：金标/G6b 空转、99 区与 pilot5000 线、文档+词表治理跑在数据前面。判据不是"模块多"，而是"投入了但没被使用"。
2. **有一次真实跑偏**：把"能检索、能背"这个核心目标，让位给了标签/门禁/文档这类元数据治理。7 天里治理层产出 60 篇文档、10 个门禁、100 个二级标签，而题库的标签覆盖是 **36/19,913 = 0.18%**。
3. **错漏集中在两类**：①"改了但不生效"的静默失效（配置/预算/提交）；②门禁口径与实现不一致（说"硬门"，实际不拦）。外加一个结构性老账：切块把章节标题当题、26.4% 答案为空。

## 3 过度设计判定（逐项，不是一刀切）

判定标准只有一条：**这个东西有没有在生产决策里被真正用过**。

| 项 | 代码/文档成本 | 实际被用 | 判定 |
|---|---|---|---|
| G6b 金标抽检 + `golden_labels` + `label_facts` | `--golden-sample/--golden-load/--eval/--annotator` 四组参数 | **0 行金标**，从未产出过一次评估 | **冻结**：无金标时直接 SKIP，别再当"硬门"写进文档 |
| 99 区（池 2,850 / 题 108） | 独立目录 + 池管理 | 108 题，`complete=True` 后无后续动作 | **冻结**：不再扩池，不再补规则 |
| `pilot5000` 5,000 题影子试跑 | 484 行 + 整套 `pilot` 子命令 | 从未真正执行 | **降级**：归档成脚本，不进主线 |
| `baseline_stats` / `doc_audit` / `label_samples` | 3 个模块 | **0 引用、0 测试、不在 CLI** | **删除** |
| 三级复核链（`pending`/`review`/`review-resolve` + `manual CSV` 模板 + `offline` 规则打标 + `suggest/keep/drop`） | `batch_label` 1,218 行里约一半 | 36 条标签走了 4 种入口 | **收敛**：留 LLM 打标 + 一个人工终审动作，其余入口合并或下线 |
| 词表 12 组 / 100 二级 | 一个 yaml + 一张表 | 支撑了 36 条标签 | **不算过度**（词表很便宜），但**不要再加**直到标签量上来 |
| 文档体系（60 篇 + `项目审核报告/`） | 8,924 行，维护成本最高的一项 | 27 篇已过期；`docs/32`「唯一口径」已和代码不符 | **收敛**：只留口径/流程/基线/决策，报告类移出 `docs/` 顶层 |
| 门禁 G1–G9 | `gate.py` 663 + `verify_ledger.py` 986 | 强制 6 个，其余靠人看 | **保留但降承诺**：写清"强制/参考"，别一律标"硬" |
| `wlock` / `privacy_scan` / `qcheck` / `answer_state` / `qsalvage` | 都是 300 行上下 | 都用上了，且都拦住过真问题 | **保留**（这是本项目的正向资产） |
| 多 provider（local/online）+ `probe` + `llm_smoke` | 454 行 | local 回环跑通，online 未真正用 | **保留**（回环不外发是硬约束，留两条路合理） |

一句话：**"治理工具"过剩，"数据产出"不足。** 三个门禁拦过真问题（G4 向量错配、G6 其他率、G8 双身份），
但另外一半门禁从未拦过任何东西，因为对应的数据是空的。

## 4 跑偏在哪里

### 4.1 重心偏移：从"检索/可背"漂到"元数据治理"

README 写的第一句是「接入 → 分类 → 切题 → 建库 → 混合检索」，核心价值是**查到、背得出**。
近三天的投入结构却是：答案来源标记 → 固定抽检集 → 标签落库 → 补词表 → 复盘。
真正卡住"查到、背得出"的两件事——**26.4% 答案为空**、**章节标题被当成题**——都还挂在待办里。

可量化的偏移：标签体系从 10 组扩到 12 组、83 项扩到 100 项，同期标签产出从 0 变成 36。
**词表增速快于数据增速**，这是典型的"工具先行"。

### 4.2 度量体系大于被度量对象

三个独立质量体系（门禁 10 项 / 抽检 253 题 / 标签复核 7 态）同时对着一批只有 36 条标签的数据。
抽检给出"严格准确率 25.5%、可用率 61.5%"，这是**整个项目最有价值的数字**，但它躺在 `docs/43`、`docs/45` 里，
没有变成任何一条自动告警。

### 4.3 一次真实的负优化

用 `chunk_v2` 对 659 个含空答案文档盲重跑，得到 **36,515 题 / 6,750 空**，比生产（19,913 / 5,268）更差。
教训不是"重跑错了"，而是**改切块前没有固定回归语料**——所以只能靠"跑一遍看总数"来判断，成本极高且不可比。

### 4.4 口径文档开始失真（这是跑偏的早期信号）

| 文档 | 写的 | 实际 |
|---|---|---|
| `docs/32` 门禁表 | G6b「硬」 | 不在 `REQUIRED_GATES`，`refresh` 从不校验 |
| `docs/32` 线上基线 | 题 20,010 / 向量 20,010 | 19,913 / 19,913 |
| `docs/29` 基线 | 18,642 已标"作废" | 但多个文档仍在引用该量级 |

`docs/32` 自称"唯一口径索引"，它一滞后，其他 59 篇的错误引用就都有了"依据"。

## 6 返工账（这些钱花过两次）

| 事件 | 代价 | 本可避免的原因 |
|---|---|---|
| 18 次 `fix(chunker)` | 每次改都要人肉重跑、人肉比总数 | 没有固定回归语料 |
| `chunk_v2` 盲重跑 | 一次全量切题 + 评估的时间，结论是"更差" | 先诊断后重跑的原则没落地（这次之后才写进 `docs/44`） |
| 标签 merge 后直接 `refresh` 被 G4 拦 | 一次 350 s 的 `--reembed` | 标签写入会改向量 metadata，这条约束没有前置到流程里 |
| `--seed` 静默回滚 / prompt 静默截断 | 两轮"以为改好了"的空跑 | 缺"写完重读"的生效断言 |

## 7 两周收敛路线（按此顺序，不要并行扩新面）

1. **P0-3 切块回归集**（1 天）：20 篇样本 + `kb chunk --regress` 一条命令给出题数/空答案/标题题三个数。
2. **P0-1 决策补答**（2 天）：50 条人工对照 → 决定"全量补答"还是"标 `no_answer_source` 不补"。**不要两条都做。**
3. **P1-1 打标 500 条**（1 天机时）：只看两个数——`other_topic_rate` 和人工抽检 20 条的通过率。
4. **P0-2 门禁口径对齐**（半天）：代码 + `docs/32` + `status` 三处同批改。
5. **P1-4 / P1-5 清账**（半天）：删 3 个死模块、删旧探针库、入口收表。
6. **P2-1 文档分家**（半天）：`docs/` 只留现行，报告类挪走。

**明确不做（本轮拒绝）**：99 区继续投入、金标体系扩张、跨平台适配、继续加词表、再拆新的质量指标。
一句话原则：**在 36 条标签变成 1,000 条之前，治理层只允许修 bug，不允许加功能。**
