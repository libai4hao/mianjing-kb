## 一、成立的部分（先说对的，避免过度返工）

1. **"原文档表 = 唯一事实源"是对的**（D-10）。`doc_hash` 主键 + 删件只改状态 + `registry.json` 降级为快照，
   判重是索引查找而非全表比对（444 件 2.93 s）。这是整个方案最硬的一块，不该动。
2. **"先分类再处理" + "解析器只由 ext 决定"的防矛盾条款**（D-07）设计得克制：分类错最多重跑拆题，不重跑 OCR。
3. **门禁替代"文本层检测"**（D-03）在本语料上是正确判据；`gate.py` 能复现 JavaGuide 等"假成功"件。
4. **影子库 + G1–G5 + 原子切换 + 回滚快照**（`refresh.py`）是高风险重建的正确姿势；`-wal/-shm` 侧车清理、
   `quick_check`、行数校验、运行锁、`--swap-only` 都在。比"直接 rebuild 线上库"高一个档次。
5. **打标 staging 中间层 + 预算封顶 + 断点续跑 + 单事务 merge**，以及 G6b 金标门禁的机制方向正确。
6. **工程卫生**：迁移注册表 + `BEGIN IMMEDIATE` + 收尾 `_validate_schema()`、跨进程写锁（含死锁接管与陈旧锁归档）、
   事件表幂等、`ruff/pyflakes` 双 0、公开前 PII/机器指纹/作者身份处理——这些是很多"能跑就行"的项目没有的。

以上不需要重做；下面的问题都是在它们之上"少了一层校验"或"口径没对齐"。

## 二、P0：三条结构性问题（会直接污染结论）

### P0-1 题池双身份：同一原文被抽了两遍，见证数系统性放大

**机制**（代码事实）：

- `extract.doc_pool()`（`extract.py:76-103`）的题池 = `status='classified'` 的源文件 **+** `20-题库MD` 下所有 md 镜像；
- 源文件的 `doc_hash` 是内容 sha256；镜像 md 的 `doc_hash` 是 `sha256("md-mirror:"+rel)`；
  **两个身份不同，因此没有任何去重**；
- `build_db` 只把镜像的 `mirror_hash` 写进 `doc_contents`，`questions.doc_hash` 仍是镜像 hash；
  `question_freq` 视图按 `COUNT(DISTINCT doc_hash)` 计见证数（`004_questions.sql`）→ 同一原文被计两次。

**生产库实测（面经库.db，2026-11-19）**：

| 指标 | 数值 | 说明 |
|---|---|---|
| 总题行 | 32,087 | |
| 挂镜像身份的题行 | **20,570（64.1%）** | `doc_hash` 不在 `documents` 表 |
| 同一原文"两边都出题"的文档 | **921 篇** | `doc_contents` 可回链源件，且源侧/镜像侧均有题 |
| 其中源侧 / 镜像侧题行 | 10,786 / 20,235 | 两侧切题结果还不一致（PDF 切得粗，md 切得细） |
| 含镜像身份、见证数被放大的多文档题 | **6,068 / 7,317（83%）** | |
| 典型题 | 《什么是 Spring Boot》docs=32 | 台账 16 + 镜像 16，总 41 行 |

**后果**：

- `docs/06-R3`、`docs/21` 的"多文档簇 3,059、覆盖 73.8%""Top 题 24 文档"这类基线**全部不可用**（至少虚高一倍量级）；
- D-05/D-16 花大代价解决的"见证数虚高"（`collection` 级口径）在实现层又漏了回来，且比原来更隐蔽；
- 检索侧同一题返回两条（答案还可能不同），RAG 上下文自相矛盾；`canonical` 的 `witness`、`question_variants`
  的 `collection` 也一并失真。

**建议**（一条即可根治）：**题池只认一个身份，且身份由"产物映射"而不是文件名猜**。
优先方案：题池以 md 为唯一文本源（md 就是过了门禁的产物），源文件只在"无 md"时兜底；
同时让镜像题的 `doc_hash` 回填为源 `doc_hash`（`build_db` 已有 `by_stem`，但那是猜测，见 P1-1）。
最低成本的先手：`extract.doc_pool` 里"同 stem 已有 md 镜像 → 跳过源文件"，然后 `extract` + `refresh` 重跑，
用附录 A 的 SQL 复核 `镜像题行 = 0`、Top 题见证数应减半。

**落地状态（2026-11-19，代码已完成，生产数据未重跑）**

按"产物映射"而非"文件名猜"实现，新增 `mianjing_kb/kb/mdmap.py`：

| 决策 | 实现 |
|---|---|
| 题池身份 | 题池键 = 源 `doc_hash`；mapped 产物用源 hash，**md 不再持有自己的身份** |
| 映射方式 | `<stem>__<hash8>.md` 精确命中优先；无前缀再用唯一 stem；同 stem 多候选按"非 md 源优先 + doc_hash 序"裁决，并记 `conflicts` |
| 无产物源 | 回退抽源文件（`mode=source`），不再借同名镜像兜底 |
| 一个源多产物 | 只取主产物（hash8 > 体积更大 > rel），其余记 `duplicates` 不进池 |
| 旧件共存 | `x.md` 与 `x__hash.md` 同目录时旧件留档、不进池 |
| 孤儿 md | 无对应源 → 保留 `md-mirror:` 身份（`mode=orphan`），这是唯一允许的镜像身份 |
| 守卫门禁 | `verify_ledger.g8_single_identity()`：有源回链（`doc_contents.doc_hash` 非空）却仍有 `mirror_hash` 题行 → FAIL；`refresh.REQUIRED_GATES` 已含 G8 |

`extract` 新增 `--plan`（只打印映射，不写库）与 `build/md_identity_report.json`（mapping/conflicts/duplicates/orphans）；
`build_db` 用 mdmap 替代 `by_stem`。测试：`tests/test_single_identity.py` 8 例、`test_verify_ledger.py` 3 条 G8 用例；
全量 397 passed、ruff/pyflakes 干净。

**仍待做**：生产 `extract` 未重跑、`refresh` 未切换，`面经库.db` 的 20,570 行镜像身份仍在；
重跑后按 `docs/29` §4 重算基线（预计题量落到约 2 万，见证数不再翻倍）。G8 会让未修数据在 refresh 阶段直接阻断，
属预期行为。

### P0-2 门禁在"自证"：G1 已被放宽成同名族兜底，G4 只比数量

**证据**：

- `verify_ledger.g1_coverage()`（`verify_ledger.py:122-164`）对每篇 classified 文档：
  `has_doc = 源 hash 有 doc_contents 行 or 同名 md 存在；has_q = 源 hash 有题 or 任一同名镜像有题`。
  注释写明"同名多源取首个是已知局限"。→ **同名不同源会被互相担保**；
- 生产 `build/verify_report.md`（2026-11-19T02:58）G1 PASS 的明细直接写着
  `"md 镜像按同名族判定（任一同 stem md 有题即覆盖）"`——即"全绿"的部分原因是把判据换成了更弱的键；
- `g4_index()`（`verify_ledger.py:234-262`）只校验 `COUNT` 与 `rowid/qid` **集合相等**，
  不校验向量与题目是否同源。B3（`copy_vec` 按 rowid 复制）如果真的错配，G4 依然 PASS。

**后果**：G1 由"台账=产物"退化为"附近有个同名文件就有题"，恰好掩盖 P0-1；
门禁从"发现问题的机制"变成"确认没问题的仪式"。这比没有门禁更危险（评审 `docs/23` 已对 G6b 提过同一原则，
但同样的病在 G1/G4 上没被处理）。

**建议**：
1. G1 改成按**身份**校验（源 hash ↔ 其自身产物/题，不允许 stem 兜底），同名族只作为诊断信息；
2. G4 增内容抽样：随机 200 条 `qid`，用该题 `q_text` 的向量与 `vec_questions` 存的向量算余弦（同题 ≥0.99），
   ≥2% 不达标即 FAIL；这条能真正抓 B3；
3. 新增 **G8 双份检测**：同一 `q_norm_hash` 同时出现在"有台账身份"与"镜像身份"的 `doc_hash` 上 → FAIL
   （就是 P0-1 的守卫，成本一条 SQL）。

### P0-3 门禁没进主链：gate 结论只落文件，抽题不看 verdict

**证据**：

- `source_documents.gate_result` 字段存在（`001_init.sql:24`），但**全仓无写入方**；生产库非空仅 4 行（历史遗留）；
- `gate --md-dir` 只写 `gate_results(md_path, doc_hash=NULL, verdict)`，且生产 `gate_results` **0 行**；
  `--audit` 模式干脆只写 `gate_report.json`；
- `extract.doc_pool` 不查 `gate_results`，也不看 `verdict`：只要 `status='classified'` 就抽题。

**后果**：`docs/19` §4 画的 `gate → pass → chunker` 是**图上的箭头**，代码里没有这道闸。
一份"假成功"（CJK 低/乱码高）的 md，只要状态是 classified，照样进题池——这正是 D-03 想避免的事故形态。
同时制两套阈值（`gate.TH_BAD=0.02/TH_MIN=100` 与 `config.GATE_GARBLED_MAX/GATE_MIN_VISIBLE`），
两套 verdict 词表（`pass/review/fail` 与 `pass/low_cjk/garbled/non_content`），使用者无法判断以哪套为准。

**建议**：门禁结果**写回事实源**（`source_documents.gate_result` 或新 `document_products.gate_verdict`），
`extract` 只抽 `verdict=pass`（review 入人工队列，fail 进 dispatch）；两套阈值合成一份 `meta/thresholds.yaml`，
`gate.py` 与 `config` 读同一处（`docs/23` §7 已提"集中阈值"，本次把它和"门禁进主链"绑在一起做）。

### P1-2 缺稳定 ID 契约：四个子系统各用一把键，重切一次全错位

| 对象 | 键 | 稳定性 |
|---|---|---|
| `source_documents` | `doc_hash`（内容 sha256[:16]） | 稳定 |
| `questions` | `qid`（AUTOINCREMENT）+ `UNIQUE(doc_hash, seq)` | **重切即漂移** |
| `label_facts` | `q_norm_hash` | 题干改一字即失联 |
| `vec_questions` | `rowid = qid` | **重切即错配**（已知 B3，靠 `--reembed` 规避） |
| `canonical_questions` | `sha(q_norm(代表题干))` | 代表变体变了就换 ID |
| `question_variants` | `sha(doc_hash:seq)` | 随 seq 漂移 |

现状靠三处补丁维持（`store()` 按 `q_norm_hash` 重挂 label、`build_db` 重建时 DROP 向量、`refresh --reembed`）。
只要有一次忘记 `--reembed`，检索不出错、门禁不报警（G4 只比数量），属于**静默降级**。

**建议**：定一条**稳定键 = `(doc_hash, q_norm_hash)`**（内容内唯一、重切不变），作为向量表外部主键与标签外键；
`qid` 降级为纯行号，任何跨库关联都不许用它。`refresh` 默认 `--reembed`，`copy_vec` 改成"显式 flag + 校验题集哈希一致"，
不一致直接 ABORT。

### P1-3 写锁覆盖不全：`build_db` / `embed` / `extract` 在锁外

`kb/wlock.py` 已接入 `intake / batch_label / doc_convert / review_cli / refresh`（T15），但
`grep wlock` 显示 **`build_db.py`、`embed_questions.py`、`extract.py`、`canonical.py`、`gate.py` 未接入**。
其中 `build_db/embed` 直接写线上 `面经库.db`，`refresh` 正持锁做 reembed + `os.replace` 时若有人手跑 `kb build-db`，
就会出现"影子已建好、线上被第三方重写、随后被 swap 覆盖"或"swap 后向量与题不对应"。
`busy_timeout` 只能缓解 SQLite 层面争用，管不了文件级 `os.replace`。

**建议**：锁分两把——`kb`（写 `kb.sqlite`）与 `online`（写 `面经库.db`）；`build_db/embed/canonical` 接 `online`，
`refresh` 同时持两把；并在锁文件里写"本次操作目标库"，冲突提示能直接说清是谁在动哪个库。

### P1-4 见证数口径与方案不一致

`docs/03` §9.3 明写：`witness = count(distinct collection)`（同 collection 计 1），目的就是防"同一来源打包重发虚高"。
实现是 `COUNT(DISTINCT doc_hash)`（`004_questions.sql` 的视图 + `cluster` 的 `n_docs`），
既没有 collection 折叠，又叠加了 P0-1 的镜像放大。**方案里的算法与代码里的指标不是同一个东西**，
所以"Top 题 24 文档"既不能证明题目热门，也不能用来排序。

**建议**：先把指标名改诚实（`n_distinct_docs` → `n_docs_raw`），再实现 `witness = count(distinct collection)`
（`source_documents.collection` 已在台账里，一条 JOIN 即可）；报告与前端一律用新的 witness。

### P1-5 生产库与代码不同代：迁移从未在产库跑过

生产 `kb.sqlite` 的表清单里**没有 `schema_version`、没有 `document_events`**，
即 T2/T12/T14 的迁移体系与事件表只在代码和测试库中存在；`labels_staging / label_facts / golden_labels` 全为 0。
下一次 `intake`（第一个写库工具）会在写锁内一次性补跑 001–013 全部迁移，
其中包括 `ALTER TABLE`、事件表回填（1,515 行 × 逐条 `append`）、`013` 预设灌入——
这条路径**没有任何产库预演记录**，一旦中途失败，事实源就处于"半迁移"状态（虽然 T14 已把单条迁移事务化）。

**建议**：上线前做一次"迁移预演"：`copy kb.sqlite → kb_dry.sqlite`，跑 `migrate()` + `verify G1–G5` + `extract --dry-run`
比对行数；把这一步写进 SOP 的"首次写库前"清单，并在 `docs/06-R3` 的基线表里标明"代码级已落地 / 产库未迁移"。

## 四、P2：可选优化（不阻塞，但影响体感与可维护性）

1. **检索不去重**：`search.hybrid_search` 按 `qid` 融合，同一 `q_norm_hash` 的重复行会一起返回；
   叠加 P0-1 后，k=10 可能全是同一道题。建议结果层按 `q_norm_hash` 合并（保留答案最长/来源最可信的一条 + 其余作为 witness）。
2. **vec 过滤后置**：`vector_search` 的 `AND q.topic=?` 作用在 KNN 之后，带过滤时 k 不足（T1 已登记，等向量表加 metadata）。
3. **空答案 19%**：32,087 题中 6,175 条 `a_text` 为空、7,808 条 <20 字。对 RAG 而言"有问题没答案"就是噪声。
   建议 `extract` 增加答案覆盖率口径（或在簇内继承同题最优答案），并让 G6 报覆盖率。
4. **同文档内重复题**：`(doc_hash, q_norm_hash)` 重复 1,209 组（chunker 重复产出）。建议 `extract` 落库前按
   `(doc_hash, q_norm_hash)` 去重（保留最长答案），或在 `chunker` 侧抑制。
5. **三套聚类/三组数字**：`canonical`（13,716 簇）、`cluster.py`（6,881 簇）、`report` LSH（3,059 簇）并存，
   指标互不可比。建议明确"canonical = 唯一题登记簿"，`cluster` 只保留 99 区判重用途并在文档标注，避免被当同一口径引用。
6. **`canonical_id` 不稳定**：取"最长变体题干"的 hash，重跑可能换代表 → ID 漂移。建议取"簇内最小 `q_norm_hash`"作为 ID。
7. **`build_db` 直跑会静默 DROP 向量**：跑完若不 `embed`，`search` 降级 kw、G4 报 WARN 但放行。建议 `build_db` 结尾打印"向量已清空，需 embed"并在 `kb refresh` 之外禁用直跑。
8. **残留 `sys.path.insert(REPO/"mianjing_kb")`**：仍有 10 个模块（`build_db/search/dispatch/reconvert/embed_questions/...`）
   把包目录塞进 `sys.path`，与 T3"不再塞模块目录"的说法不一致，也保留 bare-name 遮蔽风险。
9. **G4 WARN 放行**（T18 待定）：硬门允许 WARN 意味着"已知降级"也能 swap；建议 WARN 时在 summary 顶部打印"本次切换带降级项"，别只在 detail 里。
10. **Windows 单点依赖 + 转换无进程级超时**（2026-11-19 已处理，T16 完成）：`.doc` 转换依赖 Word COM、
    OCR 依赖 PaddleOCR-json，只在 Windows 实测；Word COM 调用原本没有可靠超时，一份异常文档会卡死整批。
    **不做跨平台重构**（LibreOffice headless 成本高、收益低，属已知边界），只做**进程隔离**：
    `kb/proc.py` + `doc_convert` 逐件子进程 + `--timeout`（默认 180 s，超时杀进程树、记 `timeout`、继续下一件）。
    验证见 `tests/test_doc_convert_isolation.py`（假 worker 挂起 → 两件各记 timeout 且总耗时受限）。
    同类风险仍在 `ocr_pages`（PaddleOCR 子进程已有逐页调用，但无硬超时）与 `question_freq` 的 `.doc` 抽文本，
    处置方式相同：**先隔离进程，再谈跨平台**。

## 五、流程断点地图（"哪一步必须靠人记"）

| 阶段 | 工具 | 是否被编排 | 产物/状态留痕 | 失败可见性 |
|---|---|---|---|---|
| 登记判重 | `intake` / `pipeline --check` | 部分（`pipeline` 只到第 3 步） | `source_documents` + `batches.state` | 好（分块提交 + failed 状态） |
| 分类 | `classify` | 由 `pipeline` 串起 | 字段落台账 | 好 |
| 转换 / OCR | `doc_convert` / `ocr_pages` / `ocr_merge` | **无编排**（SOP 手工） | `ocr_pages` 页级 + `convert_log.json` | 中（`convert_log` 是文件，不是台账） |
| 门禁 | `gate` | **无编排、不进主链** | `gate_report.json` + `gate_results`（产库 0 行） | 弱（结论不进事实源） |
| 抽题 | `extract` | 手工 | `questions`（双身份，无产物关联） | 中（错误只打 warning） |
| 聚簇 / canonical | `canonical` / `cluster` | 手工 | 全量重建 | 中 |
| 建库 / 向量 | `build_db` / `embed` | 手工 | 快照库 | 弱（DROP 向量无提示） |
| 打标 → merge → 生效 | `batch_label` + `refresh` | **无编排**（5 步手工，`docs/23` §5 已指出） | staging + `label_failed.csv` | 中 |
| 99 区删件 | `cluster → bookmarks → purge` | **无编排**（靠四重校验兜底） | `99_deletion_log.csv` | 好（安全，但不顺手） |
| 核账 | `verify_ledger` | 由 `refresh` 内置 G1–G5 | `verify_report.md` | 中（判据偏软，见 P0-2） |
| 状态查询 | **无 `kb status`** | — | — | 无（靠 SOP 记忆） |

结论：**链是完整的，编排是缺的**。在单人、单机、低频批处理场景下可以靠 SOP 撑着；
一旦变成"每周跑几次增量"，缺 `kb status` 与产物状态会持续制造"忘了跑 refresh / 忘了 reembed"的事故。
