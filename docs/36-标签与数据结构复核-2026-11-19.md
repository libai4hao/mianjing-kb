# 标签与数据结构复核（2026-11-19）

> 状态：现行设计，未落库 · 最后更新：2026-11-19 · 适用版本：v2-R3
> 结论：建议的“有限闭集 + 少量开放字段”方向正确，但不能直接替换现有 `topic/qtype/difficulty`。
> 采用**增量字段 + 稳定 code + 旧字段双写**，先保证 5,000 题试跑可回滚，再切换 prompt 与门禁。

## 1. 复核结论

| 建议 | 结论 | 处理 |
|---|---|---|
| 一级领域 10–20 个 | 采纳 | 现有 10 个数量够，但 `Java` 是语言不是领域；重组为 12 个一级领域 |
| 二级主题 50–150 个、稳定 ID | 采纳，修正 | 现有 83 个在区间内，但没有稳定 ID；新增 `code`，显示名只做展示 |
| 题型 7 类 | 采纳，增量 | 新增 `qtype_code`；旧 `qtype` 保留显示名，避免 chunker/search 立刻断裂 |
| 难度 3 档 + 判定依据 | 采纳，增量 | 保留 1–5 整数做排序；新增 `difficulty_band` 与 `difficulty_basis` |
| 元数据 | 采纳，可选 | 岗位保留；语言/框架/公司/时间/来源为可选，缺失不强制模型编造 |
| 质量标签 | 采纳，拆分 | “完整/残缺/无有效内容”做单值 `quality_state`；“重复/歧义/广告/过时”做多选 flags；`需人工复核` 归 `review_state` |
| 开放字段 | 采纳 | 保留 `canonical_q`；新增 `keywords`、`concept_candidates`；`concept_ids` 等映射后再落 |
| 稳定身份 | 采纳 | 用 `code`（如 `BACKEND.JAVA`），不用自增 `id`，也不把显示名当主键 |

**关键修正**：不要在一夜之间把 `八股/算法/HR/场景/项目` 改成 7 个新枚举。`chunker`、`extract`、`build_db`、`search`、`vec_questions` 都以 `qtype` 文本落库；直接换值会让历史题、向量 metadata、筛选条件同时失真。正确做法是双写：旧字段继续服务现有链路，新 code 服务新标签与检索。

## 2. 一级/二级结构

### 2.1 当前结构的问题

`meta/tag_vocab.yaml` 现有 10 组、83 个二级标签，数量本身在建议区间内，但层级语义不对：

- `Java` 被当成一级领域，实际是语言，应归 `BACKEND`；
- `数据库` 与 `缓存与中间件` 是合理一级；
- 缺少 `测试`、`客户端` 两个用户明确提到的一级领域；
- `label_taxonomy` 只有自增 `id`，没有稳定 `code`；prompt 和落库都使用显示名，改名即断链。

### 2.2 建议的 12 个一级领域

| code | 显示名 | 说明 |
|---|---|---|
| `BACKEND` | 后端 | Java/Spring/MyBatis/设计模式/并发等语言与框架内容 |
| `FRONTEND` | 前端 | React/Vue/TS/浏览器/工程化 |
| `DATABASE` | 数据库 | 索引/事务/InnoDB/MVCC/分库分表 |
| `CACHE_MQ` | 缓存与中间件 | Redis/缓存/Kafka/消息队列 |
| `NETWORK` | 网络 | TCP/UDP/HTTP/HTTPS/DNS |
| `OS` | 操作系统 | 进程线程/内存/死锁/IO/文件系统 |
| `ALGO` | 算法与数据结构 | 数组/链表/树/DP/图/复杂度 |
| `AI` | AI 与大模型 | Transformer/RAG/微调/量化/Agent |
| `TESTING` | 测试 | 单测/集成/性能/自动化/缺陷定位 |
| `CLIENT` | 客户端 | Android/iOS/跨端/移动性能/UI |
| `ENGINEERING` | 工程与质量 | 幂等/限流/熔断/监控/灰度/一致性 |
| `PROJECT_BEHAVIOR` | 项目与行为 | 项目追问/难点取舍/团队/职业规划 |

二级 `code` 采用 `一级CODE.二级SLUG`，例如：

- `BACKEND.JAVA`、`BACKEND.SPRING`、`BACKEND.CONCURRENCY`
- `DATABASE.INDEX`、`DATABASE.MVCC`
- `NETWORK.TCP`、`NETWORK.HTTP`
- `TESTING.UNIT`、`TESTING.PERFORMANCE`
- `CLIENT.ANDROID`、`CLIENT.IOS`

目标二级数量 90–100（现有 83 + 测试/客户端补充）；仍落在 50–150 的建议区间。

## 3. 题型与难度

### 3.1 题型：7 个稳定 code

| code | 显示名 | 旧值映射 | 判定要点 |
|---|---|---|---|
| `knowledge` | 知识题 | 八股（定义型） | 是什么、区别、列举 |
| `principle` | 原理题 | 八股（机制型） | 为什么、如何工作、机制/流程 |
| `scenario` | 场景题 | 场景 | 线上问题、方案选择、排障 |
| `project` | 项目追问 | 项目 | 你负责什么、难点、取舍 |
| `algorithm` | 算法题 | 算法 | 手撕、复杂度、数据结构 |
| `system_design` | 系统设计题 | 新增 | 容量、架构、扩展、容灾 |
| `behavior` | 行为题 | HR | 经历、动机、协作、冲突 |

旧 `八股` 不强制映射到 `knowledge` 或 `principle`；新标签由模型按判定要点选择，历史题保留旧显示值，新增 `qtype_code` 为空（或按规则批量回填，另行迁移）。

### 3.2 难度：3 档 + 依据

| band | 显示名 | 1–5 映射 | `difficulty_basis` 允许值 |
|---|---|---|---|
| `basic` | 初级 | 1–2 | `definition`（定义/记忆） |
| `intermediate` | 中级 | 3 | `mechanism` / `tradeoff` |
| `advanced` | 高级 | 4–5 | `design` / `edge_case` / `experience` |

保留 `difficulty` 1–5 用于排序和兼容；`difficulty_band` 必须与整数一致，`difficulty_basis` 必填。G6 校验规则：band 与 int 不匹配、basis 缺失或不在枚举内 → `FAIL`，不是 warning。

## 4. 元数据与质量

### 4.1 元数据

| 字段 | 类型 | 必填 | 来源/说明 |
|---|---|---|---|
| `position` | JSON 数组 | 否 | 现有岗位多选，保留 |
| `language` | TEXT | 否 | Java/Python/Go/JS 等，能从题干/框架判断才填 |
| `framework` | TEXT | 否 | Spring/React/Kafka 等 |
| `company` | TEXT | 否 | 只从来源路径/元数据取，禁止模型猜 |
| `interview_time` | TEXT | 否 | 面试/发布时间；与 `published_at` 区分 |
| `source_type` | TEXT | 否 | 面经/题库/真题/专题/其他 |
| `outdated` | INTEGER | 否 | 0/1；由内容判断或人工标记 |

`company`、`interview_time` 在很多文档里不存在，缺失应写 NULL，不能为了让字段“好看”而编造。

### 4.2 质量：单值状态 + 多选 flags

| 字段 | 取值 | 说明 |
|---|---|---|
| `quality_state` | `complete` / `incomplete` / `empty` | 完整、残缺、无有效内容，单选 |
| `quality_flags` | `duplicate` / `ambiguous` / `ad` / `outdated` | 多选，负向问题 |
| `review_state` | `NULL` / `pending` / `agree` / `disagree` | 现有复核状态；“需人工复核”映射到这里，不重复做 quality flag |

不要把“完整”和“残缺”同时塞进多选：一个是正向状态，一个是负向状态，混在一起无法做门禁。展示层可以派生“需人工复核”，但事实列只保留 `review_state`。

旧 `quality` 值迁移：

| 旧值 | 新结构 |
|---|---|
| 完整 | `quality_state=complete`，flags 空 |
| 残缺 | `quality_state=incomplete` |
| 无答案/无有效内容 | `quality_state=empty` |
| 重复 | `quality_state` 保留原状态，flags 加 `duplicate` |
| 过时 | flags 加 `outdated` |
| 广告 | flags 加 `ad` |
| 歧义 | flags 加 `ambiguous` |
| 需人工复核 | `review_state=pending`，不写 quality flags |

## 5. 开放字段

| 字段 | 类型 | 上限 | 说明 |
|---|---|---|---|
| `canonical_q` | TEXT | 60 字 | 现有标准化问句，保留 |
| `keywords` | JSON 数组 | 3–8 个，每个 ≤24 字 | 检索关键词；旧 `tags` 可兼容映射 |
| `concept_candidates` | JSON 数组 | 0–5 个 | `{name, confidence}`，开放知识点候选 |
| `concept_ids` | JSON 数组 | 映射后 | 先不开放给模型；由词表映射任务写入 |

`concept_candidates` 是开放文本，允许新知识点；`concept_ids` 必须来自 `concept_taxonomy(code, name, aliases)`，不能由模型自由生成。

## 6. 数据结构落库方案

采用**增量迁移**，不改现有主键与旧字段语义。建议迁移编号 018（016/017 已被占用；以实际 `MIGRATIONS` 顺序为准）。

### 6.1 `label_taxonomy` 增加稳定 code

```sql
ALTER TABLE label_taxonomy ADD COLUMN code TEXT;
ALTER TABLE label_taxonomy ADD COLUMN parent_code TEXT;
-- 先按固定映射回填 code，再建唯一索引；不要用自增 id 当稳定身份
CREATE UNIQUE INDEX IF NOT EXISTS ux_label_taxonomy_code ON label_taxonomy(code);
```

回填规则：`level1` → 上表 12 个一级 code；`level2` → `一级CODE.规范化SLUG`；`Java` 组整体迁到 `BACKEND`，`Java` 本身成为 `BACKEND.JAVA`。

### 6.2 `labels_staging` 与 `label_facts` 双写

两张表都增加同一组字段，保证 staging merge 后事实源不丢信息：

```sql
ALTER TABLE labels_staging ADD COLUMN level1_code TEXT;
ALTER TABLE labels_staging ADD COLUMN level1_name TEXT;
ALTER TABLE labels_staging ADD COLUMN level2_code TEXT;
ALTER TABLE labels_staging ADD COLUMN level2_name TEXT;
ALTER TABLE labels_staging ADD COLUMN qtype_code TEXT;
ALTER TABLE labels_staging ADD COLUMN difficulty_band TEXT;
ALTER TABLE labels_staging ADD COLUMN difficulty_basis TEXT;
ALTER TABLE labels_staging ADD COLUMN language TEXT;
ALTER TABLE labels_staging ADD COLUMN framework TEXT;
ALTER TABLE labels_staging ADD COLUMN company TEXT;
ALTER TABLE labels_staging ADD COLUMN interview_time TEXT;
ALTER TABLE labels_staging ADD COLUMN source_type TEXT;
ALTER TABLE labels_staging ADD COLUMN published_at TEXT;
ALTER TABLE labels_staging ADD COLUMN quality_state TEXT;
ALTER TABLE labels_staging ADD COLUMN quality_flags TEXT;   -- JSON 数组
ALTER TABLE labels_staging ADD COLUMN keywords TEXT;        -- JSON 数组
ALTER TABLE labels_staging ADD COLUMN concept_candidates TEXT; -- JSON 数组
ALTER TABLE labels_staging ADD COLUMN concept_ids TEXT;     -- JSON 数组，映射后写
```

`label_facts` 同样增加这些列；主键仍是 `q_norm_hash`，不改为 `qid`。`labels_staging` 现有 `topic/qtype/difficulty/tags/position/quality/canonical_q` 全部保留并双写：

- `topic` = `level2_name`（兼容旧检索/报表）
- `qtype` = 新显示名或旧值（过渡期由调用方决定）
- `difficulty` = 1–5 整数
- `tags` = `keywords` 的兼容副本

### 6.3 `golden_labels` 增加金标维度

```sql
ALTER TABLE golden_labels ADD COLUMN level1_code TEXT;
ALTER TABLE golden_labels ADD COLUMN level2_code TEXT;
ALTER TABLE golden_labels ADD COLUMN qtype_code TEXT;
ALTER TABLE golden_labels ADD COLUMN difficulty_band TEXT;
ALTER TABLE golden_labels ADD COLUMN difficulty_basis TEXT;
```

G6b 仍按 `q_norm_hash` 对照；新增 code 只用于分主题/分题型统计。

### 6.4 `questions` 的检索列

`questions` 已由 012 加了 `position/quality/canonical_q`。本轮不直接把 `qtype` 换值，建议后续在 `build_db` 投影时增加：

- `level1_code`、`level2_code`
- `qtype_code`
- `difficulty_band`
- `keywords_json`、`concept_ids_json`

`vec_questions` 的 metadata 先保留 `topic/qtype/difficulty/q_key`，等检索过滤确认需要 code 后再加；不要在没有回滚方案时改 vec0 schema。

## 7. 校验规则

新增 `labelspec` 校验（建议在迁移后启用）：

1. `level1_code` 必须存在于 `label_taxonomy.enabled=1` 且 `parent_code IS NULL`；
2. `level2_code` 的 `parent_code` 必须等于 `level1_code`；
3. `qtype_code` 必须属于 7 个 code；
4. `difficulty` 必须在 1–5，`difficulty_band` 与整数映射一致，`difficulty_basis` 必填；
5. `quality_state` 必须是 `complete|incomplete|empty` 之一；
6. `quality_flags` 只能取 4 个负向值，去重后落 JSON；
7. `keywords` 3–8 个、每个 ≤24 字；`concept_candidates` 0–5 个；
8. `concept_ids` 只能来自 `concept_taxonomy`，空值允许；
9. `company`/`interview_time` 缺失不报错，禁止模型编造；
10. 旧字段与新 code 同时存在时，`topic` 必须等于 `level2_name`，`qtype` 必须是新显示名或历史旧值。

G6 建议分成两层：

- **硬校验**：code 父子关系、qtype code、difficulty band/basis、quality_state；
- **软校验**：keywords 数量、concept candidates 数量、metadata 完整率，只进 detail，不阻断 merge。

## 8. 迁移与上线顺序

1. **先加列、回填 code**：不改 prompt，不换 `qtype` 值；现有打标继续工作。
2. **双写**：`batch_label` 输出新 code + 旧字段；`merge` 同时写 `label_facts` 新列。
3. **更新 prompt 与 G6**：prompt 展示 `code=显示名`；G6 硬校验新字段。
4. **改检索投影**：`build_db`/`vec_questions` 按需增加 code；先只读对比，不切线上。
5. **5,000 题试跑**：先 100–200 题打标抽检，确认闭集分布、非法率、人工复核率。
6. **冻结 v2**：确认稳定后再把 `topic` 降级为显示字段，禁止新代码再以显示名做键。

## 9. 与现有决策的关系

- 不改变 `label_facts` 主键 `q_norm_hash`（D-32 的标签主键决策仍有效）；
- 不改变 `q_key` 作为题目稳定身份；
- 不把 `qid` 用于跨重建标签；
- 新增字段属于 D-34 Golden Query / D-35 RAG 去重的前置数据基础：Golden Query 用 `q_key` 标注，标签 code 用于分主题指标；
- 本设计不与 D-27 生产迁移混做：先落列与双写，生产迁移仍按 D-27 的独立窗口执行。

## 10. 验收清单

- `label_taxonomy.code` 唯一，父子关系 0 冲突；
- 12 个一级、90–100 个二级，`enabled=0` 的历史标签仍可查；
- 100 条试标：`qtype_code`/`difficulty_band` 非法 0，`difficulty_basis` 缺失 0；
- `labels_staging` merge 后 `label_facts` 新列与 staging 一致；
- `topic` 与 `level2_name` 一致，旧检索无回归；
- `concept_candidates` 可写入，`concept_ids` 为空直到映射任务运行；
- 5,000 题试跑中标签字段不导致 `UnicodeEncodeError`/JSON 解析失败。
