# 12-本地 LLM 冒烟报告（2026-11-17）

> 目的：为 RAG 检索库选一个**本机可跑**的生成模型，量化 T1（RAG 问答）/ T2（结构化抽取）质量与延迟。
> 前置：docs/11 §4 推荐 Ollama + Qwen3-8B（Q4_K_M）；本报告用实测数据修正该推荐。

## 0. 结论先行

| 项 | 结论 |
|---|---|
| 生产推荐 | **Qwen3-4B Q4_K_M**（2.5GB）。T1 延迟 9.2s、T2 3.2s、json_ok 100%、grounded 0.85，全部指标不输 8B |
| 8B 定位 | 仅离线批处理（打标、批量抽取）。交互场景 54s/题不可接受 |
| 不作为 | GLM-4-9B（9B 级 Q4 ≈5.6GB，必然落进本机同一显存陷阱，见 §2） |
| 关键量化 | 4B **76 tok/s** vs 8B **7.6 tok/s**（同机同后端，10 倍差） |

## 1. 环境搭建（网络受限下的可行路径）

| 组件 | 来源 | 结果 |
|---|---|---|
| Ollama 0.40.16 | ollama.com 官网 + 本地 7890 代理 | 1.7GB 安装包，~2.9MB/s |
| Qwen3-8B-Q4_K_M (4.8GB) | **ModelScope 直连**（不走代理） | 8-9.7MB/s，约 10 分钟 |
| Qwen3-4B-Q4_K_M (2.4GB) | ModelScope 直连 | 同上 |
| 模型目录 | `OLLAMA_MODELS=<LLM_ROOT>\ollama_models`（用户级环境变量） | C 盘不再放模型（此前 C 盘被 2.4GB 残留 blob 写满，工具链全部瘫痪） |
| fastembed bge-small-zh | hf-mirror + `HF_HUB_OFFLINE=1` | 否则 fastembed 无代理联网会**静默挂起** |

网络路径结论（供下次换机复用）：

- **能用的**：ModelScope（阿里云，全速）、hf-mirror（~560KB/s）、本地 7890 代理（官网下载）
- **不能用的**：GitHub 直连（37KB/s，aria2 16 线程聚合无效）、winget 后端、gh 系列镜像（ghproxy/llky/ghfast 全挂）
- 备选未走通：conda-forge `llama.cpp`（搜索超时放弃）、AMD repo.rocm.com 预编译包（只支持 RDNA3，6650XT 是 gfx1032）

## 2. 速度之谜：8B 为什么只有 7.6 tok/s（本报告核心）

### 2.1 排除项（都不是原因）

| 假设 | 实测 | 结论 |
|---|---|---|
| 模型没进显存 | `/api/ps` size_vram=5.59GB=size；debug 日志 `offloaded 37/37 layers`、`Vulkan0 model buffer 4455MB` | **全在显存**，排除 |
| Python 客户端问题 | 同 prompt 用 PowerShell Invoke-RestMethod 走通 | 排除 |
| FTS5 检索卡死 | 分步复现 import/检索 <1s | 排除（但顺手修了 FTS5 语法 bug） |
| ROCm 更快 | `OLLAMA_LLM_LIBRARY=rocm` + `HSA_OVERRIDE_GFX_VERSION=10.3.0` → `size_vram=0`，日志全 CPU_REPACK | **ROCm 不认 gfx1032，回落 CPU**（7.7 tok/s） |
| Vulkan 后端整体烂 | **4B 同后端 76 tok/s**、prefill 287 tok/s | 排除，Vulkan 本身健康 |

### 2.2 收敛结论

| 模型 | 权重+KV | 实测 decode | 理论带宽上限（224GB/s ÷ 权重） | 达成率 |
|---|---|---|---|---|
| Qwen3-4B | 3.61GB 全 VRAM | **76.1 tok/s** | ~66 tok/s | ~115%（KV 复用，合理） |
| Qwen3-8B | 4.74~5.59GB 全 VRAM | **7.6 tok/s** | ~47 tok/s | **16%** |

- ctx 压缩试验：8192→4096→2048（总量 5.59→5.02→4.74GB）**速度纹丝不动**，说明与 KV 大小无关
- CPU 对照：8B 纯 CPU(REPACK, 8 线程) 7.7 tok/s —— **与"GPU 全载"的 7.6 几乎相等**，即 GPU 路径等速于 CPU 路径
- 推断：**8B 的权重块（~4.4GB 单次分配）在 Windows WDDM 上超过驱动阈值后被降级/拆到共享内存，每 token 经 PCIe 回读**（131ms/token ≈ 4.4GB ÷ 33GB/s PCIe 3.0/4.0 实测有效带宽）；4B（2.6GB）未触发该阈值，纯 VRAM 内跑满带宽
- 该问题与 Ollama 版本无关，是 **8GB 卡 + WDDM + 大单块分配** 的组合行为；阈值经验值 3.6~4.5GB

> 换句话说：**不是显卡慢，是 8GB 显存装不下 8B 的连续权重块**。要在本机跑 8B 级模型，需 12GB+ 显存，或 Linux/ROCm 环境。

## 3. 冒烟数据（20 题分层抽样，seed=42，`/no_think`）

| 指标 | qwen3-4b | qwen3-8b |
|---|---|---|
| T1 RAG 延迟均值 | **9.18s** | 54.33s |
| T1 grounded 率 | 0.85 | 0.85 |
| T1 作答长度 | 601 字 | ~600 字 |
| T1 错误 | 0 | 0 |
| T2 抽取延迟 | **3.16s** | 11.25s |
| T2 json_ok 率 | **1.00** | **1.00** |
| T2 qtype 准确率 | 0.55 | 0.65 |

**判定**：qtype_acc 的 0.10 差距 = 20 题里 2 题的标注分歧（"算法 vs 八股"这类库内标注本身有噪声），不构成选型理由；延迟差 5.9 倍是硬指标。→ **4B 生产、8B 离线**。

## 4. 途中修掉的真 Bug

1. **search.py FTS5 语法炸**：题干原文含 `?`/引号直接进 `MATCH` → `syntax error near "?"`。改为引号短语查询（内部双引号双写转义），空结果回退 LIKE。覆盖 81 测试通过。
2. **llm_smoke.py 三处**：
   - Qwen3 思考链污染：T2 输出 `<think>` 导致 JSON 解析率 50% → 统一 `/no_think`（1.0）
   - 提示词枚举歧义：`"qtype": "八股|算法|HR|场景|项目"` 被 4B **原样抄回**（json_ok 0.3）→ 改为"从中选恰好一个"（1.0）。**小模型会把占位符当答案，提示词必须显式约束**
   - `_stat` 把均值算成非零率（chars_avg 恒为 1.0）
3. **服务稳定性**：`OLLAMA_KEEP_ALIVE=2h`。此前两次"冒烟卡死"根因 = 5 分钟空闲卸载 + 首调冷加载 >120s 超时 + 旧请求队列脏状态；排查手法记入 docs/04。

## 5. 复现命令

```powershell
# 1) 模型（已下好，<LLM_ROOT>\models）
ollama create qwen3-4b -f <LLM_ROOT>\models\Modelfile.qwen3-4b
# 2) 服务（关键环境变量）
$env:OLLAMA_MODELS="<LLM_ROOT>\ollama_models"; $env:OLLAMA_KEEP_ALIVE="2h"
ollama serve
# 3) 冒烟
python mianjing_kb/llm_smoke.py --model qwen3-4b --n 20
python mianjing_kb/llm_smoke.py --model qwen3-8b --n 20 --tasks t2   # 只补测抽取
```

产物：`build/llm_smoke_qwen3-4b.json`、`build/llm_smoke_qwen3-8b.json`（T1）、`build/llm_smoke_qwen3-8b_t2.json`（T2 补测）。
