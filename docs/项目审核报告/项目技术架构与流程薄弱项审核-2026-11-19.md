## 二、增量判定规则核验：**有 hash、无 mtime，且有一个真缺口**

**判定机制**（`mianjing_kb/intake.py:184-189`、`mianjing_kb/kb/hashing.py:17-30`）：
- **唯一增量判定键 = sha256 内容哈希**（前 16 位作 doc_hash）。**不使用 mtime**，size 只登记不参与判定。全量重扫 1,501 件 4.6s（860MB/s），靠速度补偿了不用 mtime 的成本。
- 动作矩阵完整：`added`（新 hash）/`duplicate`（同 hash 同路径，只刷 last_seen_at 不改路径）/`moved`·`renamed`（同 hash、原件已不在原处才改路径，**不降级已入库状态**）/`resurrected`（曾 absent 又回来，复用原分类）/`to_quarantine`/`revived`（99 区内容回正式区重走分类）。
- mtime 唯一用武之地是 `mianjing_kb/cluster.py:85` 的切题文本缓存键（path+size+mtime）——**纯性能缓存失效机制，不是入库增量判定**，语义正确。
- md 镜像树（20-题库MD）已改用**路径 hash**（`sha256("md-mirror:"+rel)`，`mianjing_kb/extract.py:75-83`），OCR 合并/懒加载改写 md 不再产生孤儿行——这条是 2026-11-17 修复的，正确。
- 下游全是**有意全量**：extract 全池重切（幂等 DELETE+INSERT）、build_db 影子全量重建、embed 全量重嵌（K2 增量明确未做）。增量只存在于登记层，这个架构取舍在当前量级成立。

**核验发现的缺口（P2，上一轮报告漏列，本轮确认）**：**同路径原地修改内容**会产生幽灵行——
1. 文件改内容后 hash 变了 → intake 判 `added` 插新行（`intake.py:115` 只按 hash 查，不检查“该路径是否已被别的 hash 占用”）；
2. 旧行仍 `classified`，src_path 指向同一路径且文件存在 → **G5 拦不住**（只查 src_path exists）；
3. extract 的 doc_pool 两条 hash 都映射到同一个物理路径（`extract.py:63-73`），读到的是**新内容** → 同一份内容抽出的题落两份（两个 doc_hash），频次统计/CSS 目 witnessing 计数虚高，G1 两行都 PASS。

修复方向（供方案参考，未改代码）：intake 扫描时对同物理路径检查旧占用行，命中则旧行标记 `superseded`（note 记 `replaced_by:<new_hash>`），G5 顺带自然覆盖。成本低，一个 JOIN 的事。

## 三、后续新文档（pdf/docx/md）入库流程

按 docs/04 SOP 与现有工具链，三种格式共用登记层，从“转换”开始分叉：

```
① 丢弃入 31-收件箱（唯一新增入口，目录即语义）
        │
②  python mianjing_kb/pipeline.py --check   ← 预览：只报新增/重复数，不写库
    python mianjing_kb/pipeline.py          ← 真跑：intake(hash判重) → classify(规则判类) → ingest_queue 清单
        │   md/txt 直接收工进入⑤；pdf/docx/doc 继续往下
③  转换产 md（本仓库外，复用语料侧 21-面经数据库\tools\convert_one.py）
      .doc  → 先 python mianjing_kb/doc_convert.py（Word COM + zip 魔数验收），原 .doc 记 superseded
      pdf/docx → convert_one.py 产 md 落 20-题库MD/<category>/<topic>/<stem>.md
        │
④  质量门禁与兜底（失败件的六个出口）
      python mianjing_kb/gate.py --audit                    ← 三态 pass/review/fail（NFKC 归一）
      python mianjing_kb/dispatch.py                        ← fail/review 件六路由分流
      真乱码/无文本层 → mianjing_kb/ocr_pages.py --pdf x.pdf --pages 1-N → mianjing_kb/ocr_merge.py 合并回 md
      缺口补录 → mianjing_kb/backfill_convert.py（圈缺口→转换→OCR 清单）
      灰区人工 → mianjing_kb/review_cli.py --resolve ... --status classified|superseded|rejected
        │
⑤  抽题落库
      python mianjing_kb/extract.py                          ← chunker v2 切题 → questions 表（幂等）
      （切不出题的讲解型 md 会进 skip_log 记 chunker_no_split，G1/G2 凭记录放行）
        │
⑥  重建与切换（一条命令完成 3-5 件事）
      python mianjing_kb/refresh.py --reembed               ← 影子重建检索库 → 向量重嵌 → G1-G5 门禁
                                                       ← 全 PASS 才 os.replace 原子切换，FAIL 删影子保线上
        │
⑦  收尾
      python mianjing_kb/canonical.py                       ← 题簇登记簿重算（witness/多数票 topic）
      python mianjing_kb/verify_ledger.py                   ← 终检，硬门禁 FAIL 非 0 退出并产 backfill_plan.csv
      （新题要打标：batch_label.py --check → 打标 → --sample 50 → --merge，注意上轮报告 B2：
        merge 后检索层生效仍需再跑一次 refresh）
```

**流程中值得注意的三点**：
1. **步骤③是全流程唯一在仓库外的环节**（转换复用语料侧脚本），pipeline.py 不串联它——新批次入库的 SOP 是“pipeline 一条命令 + 手动转换 + 手动 gate/extract/refresh”，衔接靠人。若要优化，优先级最高的补链是把 gate→dispatch 也挂进 pipeline（转换链涉及仓库边界，次之）。
2. **新文件的 topic 断链已闭环**：规则判不出的走 `classify --neighbor`（标题 Jaccard）/ `--vec`（bge 语义近邻投票，cos≥0.85 自动落库，其余出 `topic_neighbor_review.csv` 人工清单），再不行落 overrides.json 人工拍板——三条归因档齐备。
3. **md 直接入库最短路径只有 5 步**（收件箱→pipeline→extract→refresh→verify），pdf 走全链 7 步，.doc 多一道预转换。步骤⑥务必带 `--reembed`——上轮报告已指出：不带它走向量拷贝路径，在 questions 重排后存在静默错配风险（G4 拦不住）。

**总体结论**：增量判定“hash 有、mtime 无”是合理选型（hash 是内容真值，mtime 在 Windows 拷贝场景不可靠），但需补“同路径内容变更→旧行退役”规则；入库流程主链完整、六路由兜底齐全，唯一薄弱点是步骤③在仓库外靠 SOP 人工衔接，以及打标后需要二次 refresh 才生效（上轮 B2）。
