## 二、全流程设计完整性：主链闭环，三个断点

**闭环确认**（登记→分类→门禁→转换→抽题→建库→检索→核账）：每一步都有工具承接，状态机 12 态中 9 个被实际使用，灰区件有 dispatch 六路由 + review_cli 人工出口，G5 的“退役留痕”口径自洽。以下断点按严重度排：

| # | 断点 | 定位 | 影响 |
|---|---|---|---|
| B1 | **extract 重切会静默抹掉题级打标**。`extract.store()` 是按 doc_hash DELETE+INSERT（`tools/extract.py:131-140`），qid 是 AUTOINCREMENT，重跑后 qid 重排；而打标事实源落在 `questions.topic`（按 qid merge）和 `labels_staging`（主键 qid，`meta/schema/005_labels_staging.sql:5`）。**任何一次全量重 extract，已 merge 的打标全部丢失且无告警**。项目自己已意识到 qid 不稳定（`canonical.variant_id` 用 `doc_hash:seq`，`tools/canonical.py:39`），但打标层没跟上 | P0 |
| B2 | **打标 merge ≠ 检索层生效**。merge 只写 kb.sqlite；检索库 面经库.db 的 topic 是 build_db 快照，需再跑 refresh 重建才生效。README 的打标用法（check→打标→sample→merge）与 docs/15 §3.6 的调度脚本都**没提 refresh 联动**——打完标检索行为不变 | P1 |
| B3 | **refresh 默认向量拷贝路径有静默错配风险**。`copy_vec` 按 rowid 原样拷（`tools/refresh.py:79-85`），G4 只查行数与 qid 集合相等（`tools/verify_ledger.py:254-256`）。questions 重切后 qid 集合仍是 1..N，**G4 必过但向量指向了错误的题**。历史记录显示重切后确实走了 reembed 才幸免，但机制上默认路径不设防 | P1 |

次要缺口：`pipeline.py` 名为“批增一条命令”实际只到 ingest_queue（转换/OCR/抽题/建库全在链外，文档口径一致但易误读）；夜间调度 batch_label.ps1 未落地（文档如实，不算虚报）；`processing/processed/failed` 三个 schema 状态无工具写入（死状态，无害）；gate 阈值在 `tools/kb/config.py:51-54` 与 `tools/gate.py:52-54` 双份定义，有漂移风险（P3）。

## 三、核心逻辑正确性：抽查发现的真 bug

1. **G6 topic 漂移指标语义错误**（`tools/verify_ledger.py:355-360`）：drift 的基线是 questions 现有 topic 分布，而打标的**目标就是 topic 为空的题**——首批打标时 known 集合接近空，drift 必然 ≈1.0 → 必 WARN。README 实测记录“G6 WARN 放行”正是此因。“补充缺失主题”是预期产出，却被当成异常信号。这个软门禁目前**形同虚设且方向反了**。
2. **merge 可能抹掉已有 topic**（`tools/batch_label.py:180-182`）：`UPDATE questions SET topic=(SELECT topic FROM labels_staging ...)` 无 topic 非空守卫。G6 允许 <5% 的空 topic 行 PASS，这些行 merge 时会把 questions.topic 覆盖成空串。
3. **打标产出的 qtype/difficulty/tags 三列从不落库**（merge 只 UPDATE topic）：花成本产出的字段被整批丢弃，questions.qtype 永远是 chunker 启发式结果。要么落库，要么从 prompt/staging 里砍掉省 token。
4. **计价口径粗**（`tools/batch_label.py:143`）：`tokens_total × sum(price)` 把输入价+输出价相加统一计——输入输出单价通常差 4 倍。tokens 字段存的是 in+out 合计，无法拆分。对 ¥10 预算无伤大雅，但 budget 封顶的数学是错的。
5. **pick_targets 与 health 的待打标口径字面不一致**（`tools/batch_label.py:54-55` vs `:100`：前者不带 `'未分类'`）——当前题级列无此值所以行为等价，属口径双份。
6. G1 的“同名族判定”用 stem 命中即算覆盖（`tools/verify_ledger.py:146-149`），是拿召回换精确的有意取舍，已知局限有注明，可接受。
7. docs/13 §5 契约承诺的 `num_ctx`/`keep_alive` 在 llm_client 中**均未实现**（grep 全库只命中文档）；`chat_json` docstring 说“解析失败返回 None”实际返回带 `obj=None` 的 dict——行为对、文档错（P3 文档漂移）。

以上均有测试盲区：`test_batch_label.py` 覆盖了 staging/resume/budget/merge/脱敏（9 条，质量不错），但 **G6 drift 计算、merge 空值覆盖、tokens 拆分计价均无测试**。

## 四、LLM 打标三件套专项回答（核心问题）

| 能力 | 状态 | 证据 |
|---|---|---|
| 基础打标（LLM→staging→门禁→merge） | ✅ **完整** | 并发/断点续跑/预算封顶/失败不阻塞/脱敏/G6 schema 门禁/单事务 merge，实测 local 端到端跑通 |
| 人工金标 | ⚠️ **只有抽检动作，没有金标机制** | `--sample N` 只是把 staging 随机打印到控制台（`batch_label.py:158-167`）——人工判断的结果**无处录入、无准确率计算、无留痕**。schema 里没有 golden/labels 表；docs/15 G6 承诺的“抽检 50 题人工准确率 ≥0.8”和 docs/13 L6 的“30 题抽查模板 ≥70%”都没有实现载体，"0.8"目前靠人脑、不可复核 |

结论：**打标质量保障目前是“格式门禁 + 人工随机看一眼”，设想的“金标 + 基础打标 + 高级复核”三层里只落地了中间层。**

## 五、优化方案（建议按此顺序实施）

### P0 —— 先堵架构级风险（半天）
1. **打标表与 qid 解耦**：`labels_staging` 与 merge 落库改用稳定键 `(doc_hash, seq)` 或加 `q_norm_hash` 列（extract 已算好，`tools/extract.py:124`）。这样重切后打标可按 norm hash 重挂，不再丢失。
2. **refresh 拷贝向量前加内容对齐校验**：对比现行库与影子库 questions 的 `q_norm_hash` 聚合（如逐 qid 抽样比对或全量 hash），不一致即拒绝拷贝、提示必须 `--reembed`。一行聚合 SQL 就能拦住 B3 的静默错配。
3. **merge 加守卫 + 输出生效提示**：UPDATE 加 `WHERE ... IS NOT NULL` 子查询守卫；merge 成功的 JSON 输出里明确写“检索层生效需跑 `refresh.py --reembed`”。

### P1 —— 补齐金标层（1 天，这是“人工金标”的答案）
4. **新迁移 007_golden_labels**：`(gid, q_norm_hash, q_text, topic_gold, qtype_gold, difficulty_gold, annotator, created_at)`——键用 q_norm_hash 而非 qid，跨重切存活。
5. **金标录入 CLI**（扩展 review_cli 或独立 golden_cli）：从 staging 分层抽样（按文档级 topic × qtype 分层，比纯随机更能暴露弱点），逐条展示题干 + LLM 打标结果，人工录入正确值落金标表。
6. **`--eval` 验收命令**：计算 staging vs 金标的 topic/qtype 准确率 + 混淆矩阵，落 `build/label_eval.json`。**G6 的 ≥0.8 从此从人脑判断变成可计算、可复跑的门禁**——这就是 docs/15 承诺但没兑现的那一环。

### P2 —— 补齐高级模型复核层（1 天，这是“高级复核”的答案）
7. **双模型对照 + 分歧路由**：labels_staging 加 `review_topic/review_model/verdict` 三列。基础模型打完后，用在线大模型（LLM_PROVIDER=online 已就绪）**只复核三类题**省钱：金标层判出的低准确率 topic 分区、G6 drift 命中的新 topic、基础模型低置信题。分歧题落 review 桶给人工终审，一致题直接过。docs/13 §3 实测 local 4B qtype 准确率仅 0.55——在线 flash 类预期 ≥0.85，这个复核层是数据质量的真实杠杆。

### P3 —— 打标口径治理（半天）
8. **topic 封闭词表**：从文档级 topic 分布 + meta 白名单生成受控词表，prompt 锁枚举，词表外落“其他”+review 桶。消除"Java/Java基础/JAVA基础"碎片化——否则检索按 topic 过滤会在题级与文档级两套口径间分裂（G3 只查空串，拦不住词表外主题）。
9. **G6 drift 指标重定义**：基线从“questions 现有分布”改为“受控词表”；首批打标（known 为空时）显式 SKIP 而非 WARN。schema 合格率建议改称 G6a（格式门禁），金标准确率做成 G6b（内容门禁）。
10. **qtype/difficulty/tags 落库或砍掉**：merge 把三列写进 questions（或独立列），否则从 prompt 输出要求中删除、按省下的 token 重估成本。

### P4 —— 小修清单（顺手）
- gate 阈值收敛到 config 单源；`chat_json` docstring 与 `--resume` 参数声明对齐实现；budget 计价拆 in/out；build_db 的 `mirror_topic` 目录推断在 `parts[-2]` 为 category 名时回退（`tools/build_db.py:99`）；merge 前校验 staging 的 q_text 与当前 questions 一致（防 staging 跨 extract 生成周期残留）。
