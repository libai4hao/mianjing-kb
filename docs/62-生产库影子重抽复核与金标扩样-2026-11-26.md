### 3.3 怎么读这组数

- **题干稳定性大幅改善**：消失的题干只有 42 个（0.4%）。`docs/61` 的 P1–P8 让“同一题在重切后换个说法”
  的情况基本不再发生——这是精度闸的副作用，也是它最有价值的产出之一。
- **标签/补答保住了**：`store()` 按 `q_norm_hash` 继承答案与治理字段（`docs/60` ISSUE-04）后，
  孤儿标签只剩 32 条，补答溯源丢 25 条。存量 5,195 条补答里 5,155 条仍在。
- **784 篇被硬拦是主要卡点**：拦下原因全是“重抽后这些题对不上”，而不是标签丢失；
  被拦的文档整篇保留旧题，所以影子库里新旧两套切法并存，比分不能当成“新切题器全量效果”。
  本节初稿曾把主因归为 `answer_state`/`answered_at`，2026-11-27 只读复核已纠正：
  `answer_state` 原本就未参与硬拦截，生产库也没有“只有 `answered_at`、无补答溯源”的行；
  真正需要保护的是无法按 hash 对齐的补答溯源与治理字段，详见 §3.5。
- **题量 +29% 集中在少数大文档**：`prod 1 → shadow 482`、`prod 4 → shadow 305` 这类极端增长，
  2026-11-27 已定位为旧切题器超长块、`docs/59` 多题混杂隔离与重复身份共同造成；9 篇贡献净增长的
  52.0%，且输入 Markdown 指纹未变、旧题干 hash 零丢失。证据与剩余盲评要求见 §3.6。
- 另有 15 篇“只在影子有题”的孤儿 md 文档（127 题），属于身份映射差异，不是新增内容。

### 3.4 决定与前置条件

**不切换**。要让它可切换，三条前置：

1. **分级状态损失策略**：把状态保护拆成“硬保护（`label_facts`、补答溯源、人工治理字段）”与
   “可重算（`answer_state`、无补答溯源 `answered_at`、覆盖率类）”。只有前者触发整篇拦截，后者记录后重算。
   2026-11-27 已完成代码口径修正，但影子复跑证明这不会解除当前 784 篇硬拦截，详见 §3.5。
2. **存量口径溯源与预期题数**：2026-11-27 已定位旧切题器超长块、多题混杂隔离与重复身份，
   但“切换后这些文档应有 N 题”的精确预期仍须盲评确认，详见 §3.6；不能直接拿影子题数当验收值。
3. **盲评闸门**：生产独有 42 条 + 影子独有抽 100 条盲评，精度与召回都过线；同时跑一次
   `refresh --reembed` 的影子检索库，量向量重建时间与召回变化（本轮未做）。

### 3.5 分级状态保护修正与影子复跑（2026-11-27）

生产库继续以 `mode=ro` 作为备份源（131,112,960 B，SHA256 `68d5165d5bbc71003bb3744ba35bd077ee10b204546e746f931e2277cc91936d`），
复跑只写 `build/state-loss-shadow-2026-11-27/kb-shadow.db`，命令与 §3.1 相同，不带 `--allow-state-loss`。

先纠正前提：`answer_state` 原本就不在硬保护判定中；生产 19,015 行全部带 `answer_state`，
但“只有 `answered_at`、没有 `answer_source`/`answer_model`”的行为 0。因此本次代码改动不是放宽
`answer_state`，而是把单独时间戳从补答溯源证据改为可重算状态，并新增旧 qid/字段审计。

| 指标 | 结果 | 解释 |
|---|---:|---|
| 解析候选题 | 50,048 | 包含随后被整篇回滚的候选，不是影子库最终题数 |
| 影子库最终题行 | 24,480 | 与 2026-11-26 影子结果一致；生产仍 19,015 |
| 硬拦截文档 | 784 | 全部仍是 `unmatched_governed_questions`，**没有减少** |
| 可重算状态重置 | 15 | 仅在成功替换的文档中累计；回滚文档不计入 |
| 补答溯源丢失 | 25 | 来自 `--allow-empty-overwrite` 显式清空 0 题文档时无法对齐的旧补答 |
| `label_facts` 孤儿 | 32 | 与上一轮一致，purge 因错误率超限未执行 |

对 784 篇按未匹配旧 qid 做只读归因（类别可重叠）：403 篇涉及真实补答溯源，783 篇涉及基础标签，
770 篇涉及 `position`/`quality`/`canonical_q`，只有 9 篇含未被 `label_facts` 背书的基础标签。
基础标签大多可由 `label_facts` 重挂，但扩展治理标签没有独立事实表或人工/模型来源标记，
不能仅凭“可重算”假设丢弃。因此保留现有硬保护，不为了降低拦截数字而放宽不可重建数据。

结论：**口径修正完成，T41 的“分级状态损失策略”只完成可重算状态部分，未达到可全量切换的程度。**
若要进一步放行，需先给扩展治理标签补可追溯来源/事实存储，或设计保留旧治理行的隔离与人工对齐机制；
这已超出本轮范围。存量题量差异溯源与盲评仍是独立前置条件，生产库、检索库均未切换。

## 4 T20：金标扩样到 500

### 4.1 为什么加 `--golden-export`

`--golden-sample` 从 `labels_staging` 抽，而 staging 在 `--merge` 之后就被清空——生产库已经
19,015 题、topic 覆盖率 99.4%，staging 是 0，用它抽只能得到 0 条。新增的 `--golden-export N`：

- 从 `questions` 按 `(topic, qtype)` 分层轮转抽，保证小主题不被大主题淹没；
- 跳过已进 `golden_labels` 的题干（按 `q_norm_hash`），不重复标注；
- 记录 `source_dir`（`md_rel` 首层目录）便于核对来源分布；
- 排除 `topic` 为空的行——生产库还有 112 题没打上主题，进了金标也无法参与准确率对比
  （首版没排，500 条里混进 13 条空主题，已改条件重抽）；
- 与 `--golden-sample` 共用“已有未回灌清单不覆盖”的守卫，输出仍走 `--golden-load` 的同一格式。

### 4.2 本次产出

`python -m mianjing_kb.batch_label --golden-export 500` → `build/golden_todo.json`：

| 项 | 值 |
|---|---|
| 抽样条数 | 500 |
| 分层数（topic×qtype） | 138 |
| 来源分布 | 题库 316 / 面经 86 / 真题 69 / 专题笔记 5 / 个人面经 1 / 无 md_rel 23 |

现有金标 60 条（`annotator=assistant-review`）的 G6b 现状：`state=PASS`、`topic_acc=0.85`
（95% 下界 0.739）、`topic_acc_family=0.9`、弱主题 `其他`。

### 4.3 剩下的步骤（需要人）

1. 打开 `build/golden_todo.json`，逐条填 `topic_gold`（必填）、`qtype_gold` / `difficulty_gold`（可空）；
2. `python -m mianjing_kb.batch_label --golden-load build/golden_todo.json --annotator <名字>`
   （非法项整批拒绝，回灌后原文件改名为 `golden_todo.loaded-<ts>.json` 留档）；
3. `--eval` 看混淆矩阵与弱主题，按错误分布改词表/prompt，用同一 500 集重跑对比；
4. 稳定后扩到 1,000 固定为回归基线；topic 准确率 ≥0.8 才允许 `--merge`（G6b 已是硬门）。

## 5 复跑口径

```text
# 基线重建 / 门禁

python -m mianjing_kb.batch_label --golden-export 500 [--golden-out <path>]

python -m mianjing_kb.batch_label --eval
```
