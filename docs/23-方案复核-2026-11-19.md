## 2. 同一题多次失败 / 低置信度的处理

现有降级链（`tools/llm_client.py:199-251`）：

- 429/5xx/超时/网络异常 → 指数退避 3 次（含抖动）；4xx 鉴权/参数错误立即失败，不空转；
- JSON 模式解析失败也会重试，第二次起在 system 末尾强化"只输出严格 JSON"；
- 重试耗尽抛 `RuntimeError`，`batch_label._worker` 捕获后写 `label_failed.jsonl`，不阻塞整批（`batch_label.py:152-168`）；
- `--resume` 靠"staging 已有 qid 跳过"实现：失败题没进 staging，下次跑同一批**会自动重试**——这是事实上的待办清单，但只有 jsonl，没有按错误类型聚合的 CSV，也没有进入 `--review`。

低置信度走的是另一条路：`questions.conf IN ('low','none')`、topic 出词表、金标弱区 → `review_targets` 选出来 → 同模型 `review_one` 判 agree/disagree → disagree 的行走 `--review-list` 人工终审，未 resolve 前 `merge` 不落库（`batch_label.py:332-360,504-525`）。

**没有的**：模型升级链。当前没有"本地小模型失败 3 次 → 自动切 online/更大模型"的逻辑，也没有跨模型的重试预算、失败历史表（每题的 attempt 记录）。复核用的还是同一个 `cfg["model"]`，等于自己审自己。

建议（按成本）：
1. `label_failed.csv`：把 jsonl 聚合出 `qid, 错误类型, 尝试次数, 模型`，作为人工待办清单的入口（半天）；
2. `LLM_ESCALATE_MODEL` + 失败后单次升级调用（只对 `JSON 解析失败`/`空响应` 这类"模型能力"错误，不升级鉴权错误）；
3. `label_attempts` 表记 (qid, model, attempt, error)，让"重试几次、换没换模型"可审计。

## 3. 数据清洗与去重质量

**做得好的**：字节级精确去重彻底。`doc_hash` 取 sha256 前 16 位（64 bit），10 万量级文件碰撞概率可忽略；`intake` 区分 `added/duplicate/moved/renamed/quarantined`，原件不在原处才改路径；`purge_origin` 现在按完整 sha256 复核保留副本，删除前还会重算原文摘要。删除明细落 `dedupe_deleted.csv` / `origin_deleted.csv`。

**真正的缺口**：`tools/kb/hashing.py` 里的 `char_fingerprint` / `similarity` / `pixel_fingerprint` 是给"改名 / 重新导出 / 格式转换"的同源判定写的，但全仓 grep 只有定义、**没有任何调用**。也就是说文档级只认字节完全一致：同一份 PDF 重新导出、同一篇面经存成 docx 与 md、图片版转文字版，都不会在入池阶段被判成重复，只能等题级聚类去兜。实际数据里这类副本不少（docs/08、docs/10 的重复计数主要靠 hash 抓，抓不到的就进库了）。

**数据质量的下游证据**：`docs/07` 的频次表里混进了整段试卷/长块（如"开始考智力题…"），说明切题器对"整卷连排、无题号"的排版仍会切出超长块；这些块进入聚类会拉低簇质量。

建议：把 `char_fingerprint` 接进 `intake` 的"同名/同尺寸候选"二次判定（只在 hash 不同但文件名或大小接近时调用，成本可控）；`pixel_fingerprint` 只在 PDF 与 PDF 之间启用。

## 4. 聚类效果

**机制**：SimHash 8×8bit 分带候选 → 汉明 ≤24 → Jaccard ≥auto(0.92) 强并、≥manual(0.85) 记待人工；归一后同文直接强并。99 区按"件"聚合取最优档（strong > manual > none），无库内见证的 99 内部互抱不算可删。阈值是 CLI 参数（`--auto/--manual`），可调是优点。

**量**：`docs/07` 3,289 个题目块 → 2,483 簇，394 簇出现在 ≥2 份文档；canonical 阶段 8,931 簇 / 18,642 变体，切题器 v2 后 32,087 题 → 13,716 个 canonical 簇（`docs/21`）。

**质量**：没有 precision/recall，只有 `--sample 50` 的人工抽样文件（`cluster_sample50.md`）+ 本次新增的"同题不同答"对抗测试。也就是说：
- 能回答"聚了多少簇"，不能回答"聚得对不对"；
- 答案块覆盖率低时，"同题异答"判定失效（已在结果里输出 `answer_coverage`，<30% 告警，但真实语料覆盖率还没测过）；
- 长块/整卷噪声会制造假簇，属于切题问题传导到聚类。

建议：抽 50 对人工标注"同题/不同题"做固定评测集（放 `eval/cluster_pairs.yaml`），每次改阈值或切题器跑一遍，输出 precision/recall。这是把"聚类效果"从感觉变成数字的最低成本做法。

## 5. 流程是否顺畅

顺畅的部分：`kb demo` 一条命令跑通 接入→分类→切题→建库→门禁→检索；`pipeline --check` 先预览再写；`refresh` 影子库 + G1-G5 + 原子切换 + 3 份回滚快照；`kb` 统一入口 33 个子命令。

不顺畅的部分：
- **打标闭环靠人记**：`--check → 打标 → --sample → --merge → refresh --reembed` 是五个手工步骤，漏最后一步就是"库里有 topic、检索还是旧快照"；
- **99 区删件是一条手工流水线**：`cluster → bookmarks（删前必跑）→ purge --apply --yes`，中间任何一步忘了，purge 的四重校验会挡住（安全），但流程本身没有编排；
- **失败件没有出口**：`label_failed.jsonl` 只躺在 build 目录，没有命令把它变成"待人工"清单。

建议加一个 `kb status`（读库输出：待分类/待打标/复核未决/99 区各档/门禁状态），把"下一步该跑什么"变成可查询状态，而不是靠 SOP 记忆。

## 6. 人工金标

**链路是完整的**：`--golden-sample` 按 topic 分层轮转抽 50 → `build/golden_todo.json` 人工填 → `--golden-load` 整批校验（q_norm_hash/topic_gold 必填、qtype ∈ 词表、difficulty ∈ 1-5，任一非法整批拒绝）→ 落 `golden_labels` 并把清单改名 `*.loaded-<ts>` 留档 → G6b 门禁算 topic 准确率，`<0.8` FAIL 直接阻断 merge；`--eval` 出混淆矩阵与弱主题，弱主题再喂给 `--review` 做复核目标（`batch_label.py:203-306`，`verify_ledger.py:g6b_golden`）。

**三个需要注意的点**：
1. `matched < 20` 时 G6b 返回 SKIP 而不是 WARN——金标太少时门禁静默失效，看上去"全绿"其实没测；
2. 金标按 `q_norm_hash` 关联 staging/questions，题干清洗规则一变（切题器 v2 就是一次），旧金标会失联，`matched` 掉下去又回到 SKIP；
3. 只卡 topic（qtype/difficulty 只记录不设阈，这是明示的口径），所以"金标通过"不等于三类标签都对。

建议：G6b 在 `golden>0 && matched<20` 时输出 WARN 并在 summary 里显式写"样本不足，未判"；金标回灌时打印 `matched` 预估，避免"填了但没对上"。

## 7. 参数配置化程度

**已配置化**：

| 类别 | 参数 | 位置 |
|---|---|---|
| 路径 | `KB_CORPUS_ROOT / KB_BUILD_DIR / KB_DB / KB_META_DIR / KB_OCR_ENGINE_DIR` | `kb/config.py` |
| LLM | `LLM_PROVIDER / BASE / KEY / MODEL / CONCURRENCY / TIMEOUT / JSON_MODE / NUM_CTX / PRICE` | `llm_client.resolve_config` |
| 聚类 | `--auto / --manual / --sample / --limit` | `cluster.py` |
| 打标/复核 | `--limit / --budget` | `batch_label.py` |
| 检索评测 | `--k / --mode / --min-recall` | `eval_retrieval.py` |

**仍硬编码**（改要动代码）：

- `gate.py`：`TH_BAD=0.02`、`TH_MIN=100`（`config.GATE_GARBLED_MAX/GATE_MIN_VISIBLE` 是另一套四态口径，注释已说明"有意不合并"，但对使用者是两套数）；
- `classify.py`：近邻 `min_jac=0.45`、向量自动落库 `best_cos≥0.85 且 conf≥0.6`；
- `extract.py`：`MIN_CHARS=80`、`MIN_NORM=6`；
- `chunker.py`：`MAX_TOKENS=1200`；
- `search.py`：`RRF_K=60`；
- `embed_questions.py`：`BATCH=256`；
- `refresh.py`：`ROLLBACK_KEEP=3`；
- `batch_label.label_one/review_one`：`max_tokens=128/160`。

结论：**路径与模型接入层配置化做得好，质量阈值仍散在模块常量里**。不建议全上环境变量（阈值属于算法参数，进 git 更利于复现），建议集中到 `meta/thresholds.yaml` 一处，代码只读这一份，CLI 可覆盖——既保留可复现，又不用改代码调参。

## 8. 建议优先级

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | G6b `matched<20` 输出 WARN 而非静默 SKIP | 门禁假绿比没门禁更危险 |
| P0 | 失败件聚合 `label_failed.csv`（qid/错误类型/尝试次数/模型） | 现在失败件没有人工入口 |
| P1 | `label_attempts` 表 + 可选 `LLM_ESCALATE_MODEL` | 让"多次失败"可审计、可升级 |
| P1 | `char_fingerprint` 接进 intake 二次判定 | 文档级近重复目前完全没抓 |
| P1 | `eval/cluster_pairs.yaml` + precision/recall | 聚类效果目前无量化 |
| P2 | `kb status` 聚合待办状态 | 把 SOP 记忆变成可查询状态 |
| P2 | 阈值集中到 `meta/thresholds.yaml` | 参数化收口 |
