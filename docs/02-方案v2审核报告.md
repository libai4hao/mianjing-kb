## 二、硬伤（🔴 阻塞级，必须修）

### 2.1 假成功件与 OCR 排程之间有断层——**v2 最大的盲点**

v2 的结构是：§3.2 质量门禁把 11 篇假成功推入 `ocr_needed` 队列，但 §2.2 和 §9 的 OCR 工作量清单里**只有 15 篇失败件推出的 10 篇 / 1,494 页，完全没算这 11 篇**。两条路在文档里没有汇合。

实测这 11 篇假成功的页数（v2 未统计）：

| 页数 | 文件 |
|---|---|
| 1,382 | Leetcode-Go.pdf |
| 301 | v2.0-JavaGuide 面试突击版 |
| 252 | V1.1-JavaGuide 面试突击版 |
| 238 | v1.0-JavaGuide 面试突击版 |
| 212 | 开源电子书：Nginx 开发手册文档 |
| 53 | 【合并版】大厂算法面试合集 |
| 44 | 剑指Offer 精选题（含答案） |
| 20 | 数据结构面试题 |
| 19 | 大厂面试01 |
| 15 | 操作系统面试题（带答案） |
| 1 | Java 后端学习路线概览 |
| **2,537** | **合计** |

**修法（不是简单把 2,537 页加进 OCR 清单）**：门禁失败件必须先过 §5.2 的 D1–D3 判重，再决定 OCR：

| 处理 | 适用 | 页数 | 依据 |
|---|---|---|---|
| 判 `superseded`，**免 OCR** | JavaGuide v1.0 / V1.1 / v2.0 | 791 | 同族已有健康版本（5.0 CJK 0.385、v3.0-md CJK 0.442 已入库），OCR 它们 = 重复劳动 |
| OCR | Nginx 手册、算法合集、剑指Offer、数据结构、操作系统面试题、大厂面试01、路线概览 | 364 | 无替代源 |
| 单独策略 | Leetcode-Go | 1,382 | 代码为主，按 v2 §4 已有规则（文字转文本、代码保留位图），实际 OCR 量远小于全页数 |

补上这条规则后，**最坏情况**（11 篇全 OCR）也只有 2,537 + 1,494 ≈ 4,031 页 ≈ 0.75s/页 ≈ 50 分钟——工期结论不变，但执行顺序必须是"判重先于 OCR"，否则 P0 当天就会做 791 页的重复劳动。

### 2.2 基线表引用的是运行中快照，已过期

| 指标 | v2 §2 写的 | 2026-11-17 审核实测 |
|---|---|---|
| 已产出 md | 300 篇 | **397 篇** |
| 图片 | 12,577 张 | **17,584 张 png（总文件 17,981）** |

原因：300 是 convert.py 运行中途的快照；进程退出后又补写了 120 个 md 源文件的拷贝产物。这不改变任何结论（D 盘 88.6 GB 仍够），但**基线表必须改成终态数字**，否则 P0 验收对不上账。

另有一个待解释差异：ok=423，产物 md 只有 397，差 26。成因未查明（疑为文件名冲突覆盖或部分 ok 条目无独立产物）。**建议把"423 vs 397 对账"列为 P0 门禁的第一个任务**，正好用 gate.py 顺手完成。

### 2.3 §5.1 把两个口径混成了一个数

v2 原文："**83 条题库停在'综合 / 无 sub_topic'**"。实测两个事实：

- `topic=综合` 的题库条目：83 条（这个数是 topic 口径）；
- `sub_topic` 为空的题库条目：**209 / 210 条**（几乎全空）。

"83" 和 "无 sub_topic" 是两回事。真实状况比 v2 描述的更严重：**inventory 的 sub_topic 字段基本没填**，L1 层实际只能稳定供出 `topic + category` 两级。v2 的"folder→topic 零错配"仍然成立，但据此要修订两处：
1. §5.1 的数字与表述（"需要抽查 01–10 目录里 57 条无 sub_topic 的题库"，57 是实测值）；
2. §5.1 的 L1 行、L2/L4 的预期要上调——sub_topic 大头要靠 L2 文件名和 L4 LLM 补，不是靠目录。

### 2.4 §2.2 "350道" 一行有两处不严谨

- v2 表里"整理的多家公司常见面试题库350道 / 127 页"没有写清是**根目录版**；`12-综合题库\JAVA常见面试题库\` 下还有 128 页的另一版。实测复核确认两版页数分别 127 / 128，与判重指纹结论一致；

## 三、应修项（🟡）

### 3.1 "零依赖 FTS5 trigram"的表述过强

trigram 免分词属实，但有两个已知代价 v2 没提：一是 2 字以下短查询（"GC"）命中噪音大；二是 trigram 索引体积约为原文 3 倍，2,400 万字符语料预计索引 6–8 GB。建议补一句"P1 验收时测索引体积与短查询表现，不达标再换 jieba 方案"，而不是把 trigram 写死。

### 3.2 验收数字缺依据

P0 验收"`questions.json ≥ 8,000 题`"没有推导过程（题库侧可拆题的 md 约 300 篇，篇均题量未抽样）。建议改为：P0 第一步先对 3 份代表性题库跑 `parse_banks.py` 取篇均题量，再定全量验收线；硬编码 8,000 会在验收时引发无谓争议。

### 3.3 派生物磁盘预算要重算

v2 §10 按旧口径"派生再增 6–8 GB"估；基线已到 6.27 GB，加上 OCR 页面图（4,031 页 × ~200KB ≈ 0.8 GB）+ trigram 索引 6–8 GB，**建议改为 8–11 GB，并在 P0 挂一条磁盘水位告警（D < 60 GB 时提醒）**。88.6 GB 余量下仍安全，结论不变。
