# 新 chunker 生产重抽：影子库验证与回滚演练（2026-11-24）

> 状态：**已执行影子验证，未切换生产** · 结论：**当前 chunker 直接重抽不可上线**
>
> 触发：`docs/52 §10` 列为未做项；`docs/44` 只在 659 篇上做过 chunk_v2 负向实验，
> 没有全库重抽 + 回滚演练的完整证据。本次补上：备份 → 影子全量重抽 → 对比 → 回滚演练。
>
> 全程生产 `kb.sqlite` **只读**，逻辑指纹前后一致（§6）。

## 1. 结论先行

用当前 chunker 对全库 1,430 篇内容池文档重抽，**不能切换生产**，三条硬伤：

1. **题量翻 2.48 倍**：19,913 → 49,416 条（去重后 11,848 → 21,687 个题干 hash）。
2. **打标事实丢 29.5%**：`label_facts` 10,194 条里有 **3,005 条**在新题干集合里找不到对应题；
   生产独有的题干 hash 3,629 个（占生产去重题量的 **30.6%**）在重抽后消失。
3. **补答与答案状态被抹平**：`store()` 先删后插，只按 `q_norm_hash` 重挂标签，
   不迁移 `a_text` / `answer_state` / `answer_source`。影子库里 `answer_state` 为 NULL 的有 49,341 条，
   4,233 条 LLM 补答 + 947 条拒答只剩标签重挂带过来的 12 + 11 条。

也就是说：这一刀下去，**题库不是变新，而是变回"没补答、没判边界、标签掉三成"的裸抽取状态**。

## 2. 方法与安全边界

| 步骤 | 做法 | 为什么这样做 |
|---|---|---|
| 备份 | `sqlite3` backup API → `build/backup-2026-11-24-rechunk/kb-before-rechunk.db`（131,112,960 B，SHA256 `f8bcfb2b…d597f`） | 在线备份不阻塞读；页布局会重排，所以回滚比对用逻辑指纹而不是字节 SHA |
| 影子 | 备份再拷一份 → `build/shadow-rechunk-2026-11-24/kb-shadow.db`，`extract --db <影子> --allow-empty-overwrite` | 重抽写影子，生产零写入；`--allow-empty-overwrite` 才是"真重抽"，否则 0 题文档会保留旧题、掩盖退化 |
| 对比 | 生产/影子逐 doc、逐 `q_norm_hash`、按答案状态与启发式噪声统计 | 只看总数会漏掉"东边补、西边丢" |
| 回滚演练 | 在副本上做「换库 → 探针 → 还原」，并校验生产未被改 | 演练不能拿生产当靶子 |

**两个刻意没做的事**：

- **没在生产上跑 `verify_ledger`**：它会写 `build/verify_report.json`（生产的门禁结论文件），
  在影子上跑等于把生产门禁状态改成影子的结果。影子要过门禁必须先 `refresh` 出影子检索库，
  这一步本轮没做（见 §7）。
- **没切换生产、没 `refresh`**：结论已经是不该切，继续切只会把 4,233 条补答和 3,005 条打标当真丢掉。

运行参数：`mianjing_kb.cli extract --db <影子> --allow-empty-overwrite`，1,430 篇，68.5 s，
0 报错，208 篇 0 题，`embed/向量` 未跑（重抽只影响台账库）。

## 4. 题干 hash 与标签的账

| 项 | 数量 |
|---|---|
| 生产去重题干 | 11,848 |
| 影子去重题干 | 21,687 |
| 两边都有（交集） | 8,219 |
| 只在生产（重抽后消失） | **3,629（30.6%）** |
| 只在影子（重抽新增） | 13,468 |
| `label_facts` 总条数 | 10,194 |
| 重抽后成为孤儿的打标事实 | **3,005（29.5%）** |
| 成功重挂到新题的标签行 | 19,394 行（8,219 个 hash 的多 doc 拷贝） |

机制上这是必然：`store()` 的注释写得清楚——"重切会换 qid，打标事实按题干 hash 存活"。
题干只要因为切块边界变了一两个字，`q_norm_hash` 就变，标签跟着丢；补答则完全没有 hash 之外的迁移路径。

## 5. 抽样：既有补漏，也有加噪，不能只看计数

影子独有 30 条里，确实捞回了生产漏掉的真题：

- 「安装 Elasticsearch 需要依赖什么组件吗?」「jvm 内存模型,各个部分的特点?」
- 「什么是 JDK?什么是 JRE?」「SQL优化手段有哪些」

但也混进大量碎句与标题：

- 「操作系统」「学习说明」「培养成本高」「从使用方面来说」
- 「处理器Handler(需要程序员开发)」「栈中存放什么数据,堆中呢?」（无答案）

生产独有 15 条也不都是好题：

- 「return result;」「统⼀成两端都闭反⽽更容易记忆，你说是吧？」

**判断**：新 chunker 是"召回换精度"，不是单纯退化；但精度损失有多大必须人工评测，
不能靠题数或启发式定生死。而无论精度如何，§4 的标签/补答损失是必须先解决的工程问题。

## 6. 回滚演练（副本上，生产未动）

| 步骤 | 耗时 | 结果 |
|---|---|---|
| 从备份还原副本 | 0.05–0.10 s | `integrity_check=ok`，19,913 题 |
| 影子换入副本（模拟发布） | 0.06 s | 可读，49,416 题，`integrity_check=ok` |
| 备份换回副本（模拟回滚） | 0.06 s | 19,913 题，逻辑指纹与备份完全一致 |
| 生产库逻辑指纹 | — | `prod_untouched=true`（题 19,913 / label_facts 10,194 / qid_max 216,077 全对得上） |

结论：**文件级换库 + 回滚路径可用，成本 0.1 s 级**。但要注意两点：

1. 换库只覆盖 `kb.sqlite`；真正的发布还要 `refresh` 重建 `面经库.db` 并 `--reembed`，
   检索库 416 MB、19,913 向量的重建时间不在这 0.1 s 里。
2. 换库期间必须停写（`wlock`）；本次演练未做并发写入压力测试，Windows 多进程竞争仍是
   `docs/52 §10` 的未做项。

## 7. 为什么不切换，以及切换的前提

> 增量替代方案已单独验证：只补「生产 0 题/明显漏题」的 92 篇，标签零损失、补答不变，
> 见 `docs/54`。全库重抽仍不推荐。

不切换的理由已在 §1/§4：这不是"新旧哪个更好"的取舍，而是"新库缺 3,005 条打标、4,233 条补答"的
确定性损失。要让它可切换，至少要先补齐四件事：

1. **题干迁移而不是重挂**：`store()` 对同一 `q_norm_hash` 保留 `a_text/answer_state/answer_source/answered_at`；
   边界变了的题用 simhash 近邻迁移并标记 `carried_over`，让人能审。
2. **补答与 answer_state 重跑链路**：重抽后必须重跑 `answer_state` + `qsavlage` + LLM 补答，
   否则等于把 5,180 条已治理过的答案丢掉。
3. **去重/合并前置**：49,416 行只有 21,687 个 hash，跨 doc 重复 2.28 倍（生产 1.68 倍）。
   不先做 canonical 合并，检索会重复召回。
4. **人工评测闸门**：从生产独有、影子独有各抽 100 条盲评，精度与召回都过线才谈切换。
